## [1.0.0] - 2026-08-19

First release.

### Added

- Solution scaffolding: `.slnx`, five-project Clean Architecture (`Domain`/`Application`/`Infrastructure`/`Presentation`/`Host`), `Directory.Build.props` enforcing nullable reference types and mandatory XML doc comments on public API
- Test suite foundation: `UnitTests` (xUnit), `BehaviorTests` (Reqnroll + `WebApplicationFactory`), `ArchitectureTests` (NetArchTest, mechanically enforcing the Clean Architecture boundary), and standalone fixture repositories (`PassingFixture`/`FailingFixture`/`HangingFixture`/`GitFixture`) for BDD scenarios to run real `dotnet`/`git` commands against
- Bearer authentication: constant-time credential comparison, shared by the MCP server and the dashboard (exchanged for an auth cookie via a login page)
- Path confinement: caller-supplied working directories are canonicalized, symlink-resolved, and confined to a configured root directory; file transfer applies the same policy twice (root→repository, then repository→file)
- Command execution (`dotnet_run`/`git_run` MCP tools): starts a `dotnet`/`git` command and returns a run id immediately; the caller polls `read_run_output` for incremental stdout/stderr and the eventual exit code, with a caller-overridable execution timeout (clamped to a configured maximum) and an output size cap. (Superseded by the per-tool/per-subcommand MCP Settings page below - see its own entry for the current allowlist behavior.)
- Per-repository concurrency locking: commands against different repositories run in parallel; a second command against a repository that already has one in flight is rejected with the conflicting run's id, not queued — shared bidirectionally between `dotnet_run`/`git_run`/`clone_repository`
- Cancellation (`cancel_run` MCP tool): one tool for any in-flight run (including a repository clone), killing the full process tree
- File transfer (`transfer_file` MCP tool): returns a file's contents (base64-encoded) confined to the named repository's own directory (any file, not just build output), size-capped since a tool result is a single response payload
- SQLite-persisted run history (via EF Core) for every run kind, including full-duration CPU/RAM time series per run, surviving service restarts with startup reconciliation of interrupted runs, filterable/searchable across kind/outcome/repository
- Repository management: list/clone/delete of repositories under the configured root, with live git-status (branch, dirty/clean, ahead/behind, and a distinct "remote gone" state when a tracking branch's remote-side branch has been deleted) sampled on a fast background cadence and total size on a separate, slower one; list and clone are also reachable as MCP tools (`list_repositories`, `clone_repository`, the latter accepting an optional initial branch) so the sbx caller can query and provision repositories itself — deletion and everything below stay dashboard-only, since giving the sbx caller that access risks misuse
- Repository detail page: clone source URL (from run history) and full remote list, plus a branch-switch dropdown (local + remote-tracking) that auto-creates a local tracking branch when switching to a remote-only branch
- Per-repository pull/push/force-push/fetch/clean (`git clean -xdf`) actions from the Repositories list — force-push and clean require an explicit popup confirmation; none of the five stream output, reporting only success/failure via a brief icon color flash
- Clone dialog branch selection: once a source URL is entered, remote branches are enumerated (`git ls-remote --heads`) and offered as a dropdown
- Repository detail commit graph: a branch-aware, lane/connector commit graph (most-recent-first, paginated) with branch/tag pills on the commits that carry them, and a checkout-as-detached-HEAD action per commit; detached HEAD is now distinguished from a real branch wherever git status is shown, instead of showing the literal ref name `HEAD`
- Repository detail file tree browser: an Explorer-style expandable/collapsible tree rooted at the repository, with download/rename/delete per file or folder (delete confirmed, rename inline); a new cookie-authenticated `GET /dashboard-files/{name}` endpoint backs downloads, separate from the bearer-token API surface
- Repository detail's Commits and Files sections live in a tab group (only one visible at a time)
- Blazor Server dashboard: dark-mode-only, bearer-token login, Status/History/Repositories top-level views plus routable run-detail/repository-detail subpages, a spawned-process list scoped to each run's own process tree with a kill action, history/repository filter and free-text search
- Icon-based dashboard controls (vendored from Lucide, ISC-licensed) replacing every text-labeled list/row button; destructive-action confirmation and the clone form are both native popup dialogs rather than an in-place button state change or an inline-revealed section
- Host and per-process resource monitoring (`PerformanceCounter`/WMI): host-level CPU/RAM plus per-process CPU/RAM for every process in a run's tree
- Live and historical performance graphs (vendored Chart.js): a rolling window during a run, the full persisted series afterward
- Transport hardening: HTTPS-only Kestrel (the service refuses to start on a plain-HTTP endpoint)
- Product branding: a logo (terminal-prompt `>` chevron on an orange-to-pink gradient), applied consistently across the installer (icon, banner/dialog art, bootstrapper logo) and the dashboard (favicon, header/login logo, accent color, run-kind badge colors)
- WiX Toolset installer: a Burn bootstrapper (`OutOfTheBoxSetup.exe`) chaining a hash-verified .NET 10 SDK and Git for Windows ahead of the MSI; the MSI creates a dedicated least-privilege service account, registers the Windows Service with SCM crash-recovery, opens a firewall rule, and natively supports upgrade/uninstall while structurally preserving the data directory (config + SQLite file) across both; an interactive config page (repository root, bearer token, port) with an auto-generated, upgrade-preserved, operator-overridable bearer token and service-account password, version display (including "upgrading from vX.Y.Z" on upgrades), and a dark theme on its two fully-owned dialog pages within native MSI's real styling limits
- Application-wide error logging (Serilog): a size/age-capped rolling log file in the data directory (`logs/outofthebox-.log`, daily rolling, 10 MB cap, 14-day retention), plus console output; `Error` for failed operator-triggered actions (run/transfer/clone/branch-switch/checkout process-start failures, delete/rename failures, kill-scope WMI failures) and `Warning` for internal-helper failures that degrade gracefully, across every layer of the codebase
- An MCP server (`/mcp`, MCP Streamable HTTP transport, official `ModelContextProtocol`/`ModelContextProtocol.AspNetCore` SDK): this service's sole sbx-facing interface (alongside the dashboard), exposing command execution, file transfer, repository list/clone, and Windows-specific diagnostics as ten self-describing typed tools (`dotnet_run`, `git_run`, `read_run_output`, `cancel_run`, `transfer_file`, `list_repositories`, `clone_repository`, `get_run_resources`, `get_environment_info`, `get_file_lock_info`) — no client-side skill/doc dependency needed to call it. Long-running commands are start-then-poll (`read_run_output`), not blocking or streamed, since MCP tool calls are fundamentally request/response. See [`openspec/changes/archive/2026-08-09-sbx-mcp-server/`](openspec/changes/archive/2026-08-09-sbx-mcp-server/) for the original design rationale
- `get_run_resources` MCP tool: a run's recent CPU/RAM trend (from the trailing ~10-minute window) plus a derived summary - latest CPU%, peak CPU% in the window, and idle-seconds - so a caller can judge whether a still-running `dotnet_run`/`git_run`/`clone_repository` is hung or just slow, instead of guessing from silence in `read_run_output`
- `get_environment_info` MCP tool: this host's installed dotnet/git versions (reusing the same provider behind the dashboard's Status tiles), installed .NET SDKs, installed .NET workloads (best-effort - never fails the call), configured NuGet package sources, and available disk space on the configured root directory's drive - computed fresh on every call, not cached, to diagnose a restore/build failure caused by an environment mismatch rather than a code problem
- `get_file_lock_info` MCP tool: which process(es) currently have a named file open (process id, application name, restartability), via the Windows Restart Manager API (`rstrtmgr.dll`, the same mechanism behind Explorer's own "this file is open in..." dialog) - diagnoses a Windows "file in use" build/test failure, which has no Linux analogue an sbx agent would already know to suspect
- Repository detail commit graph rewrite: one continuous multi-branch SVG overlay (not per-row), correctly rendering forks/merges with curved connectors, highlighting the checked-out commit and merge/fork points, and a routable commit detail page (`/repository-management/{name}/commits/{hash}`) reachable by clicking a commit row, showing full metadata, parent links, and changed files
- Branch checkout directly from a commit's ref pill in the commit graph, and repository/commit-log columns sized to their content instead of fixed widths
- Downloadable HTTPS certificate: the installer now writes a public-only, PEM-encoded `outofthebox.cer` (no private key) alongside the existing password-protected `outofthebox.pfx`, offered for download from the About page (`GET /dashboard-certificate`, cookie-authenticated) with detailed instructions for trusting it both on a Windows PC (import into Trusted Root Certification Authorities) and in the sbx sandbox (system-wide trust, `NODE_EXTRA_CA_CERTS`, or a one-off `curl --cacert` check) — previously an operator had to extract the public certificate from the PFX by hand
- File preview now syntax-highlights recognized code files (C#, JSON, XML/`.csproj`, HTML, CSS/SCSS/LESS, JS/TS, YAML, SQL, shell, PowerShell, Python, Ruby, Go, Rust, PHP, `Dockerfile`, diff, ini/properties, TOML, and more) via a vendored CodeMirror 5 editor with the "darcula" theme and a code-folding gutter (braces/tags/comments/indentation) - read-only, line-numbered, selectable/copyable text, replacing the previous plain unformatted `<pre>` block; an unrecognized extension still gets line numbers and folding, just without color highlighting. File preview also gained inline PDF viewing (`<iframe>`) and audio/video playback (`<audio>`/`<video>`), all content-sniffed by magic bytes the same way image detection already was. The shared `/dashboard-files/{name}` download endpoint now reports each file's real Content-Type (via `FileExtensionContentTypeProvider`) instead of a hardcoded `application/octet-stream`, which these new inline previews depend on and which also makes icon (`.ico`) and other typed downloads more correct generally
- Commit detail subpage: clicking a changed file's row (consistent with how the commit graph's own rows are clicked, not a separate button) now shows that file's syntax-highlighted unified diff (`git show --format= <hash> -- <path>`, reusing CodeMirror's already-vendored diff mode), rather than only its name and change kind; a binary file (no meaningful text diff) shows a clear "not available" state instead of empty or garbled content
- Commit detail subpage's changed-files list now shows each added/modified/deleted file's line counts (`git show --numstat`), color-coded (green added, red removed) and right-aligned in their own column, matching the other dashboard tables' "content column takes the remaining space, the rest shrink to fit" width convention; not shown for a renamed/copied file, where a line count isn't meaningful to attribute to either its old or new path
- Repositories list and repository detail page both now show live git status (clean/dirty dot, branch, ahead/behind counts, and a distinct "remote gone" icon) as a single compact icon column/line, shared between both pages via one new component; the commit detail page shows the same status for the commit's own repository
- Repository detail page now offers the same pull/push/force-push/fetch/clean quick actions the Repositories list already had, not just via the list
- File tree browser gained a "Dirty files only" filter (`git status --porcelain`) that hides clean files/folders and auto-expands any folder containing a dirty file
- Every popup dialog (confirmation, clone, rename, file preview, commit diff) can now be dismissed by clicking anywhere outside it, the same as pressing Escape or its own Cancel/Close control - previously the only way to dismiss one was an explicit in-dialog control
- Commit detail subpage: the page title and heading are now the commit's own subject (previously the hash) so the tab/heading says what a commit actually did at a glance; its author and committer each show a Gravatar picture, Fork-style, keyed by their email - a missing picture (no Gravatar registered for that address) falls back to a generic person icon, detected client-side via the image's own load failure, no extra network round-trip from the server; and each parent commit (a merge has two) now shows its own subject alongside its hash link, not just a bare hash
- Code/diff preview switched from the "darcula" (Rider/IntelliJ-style) theme to a hand-authored one matching Visual Studio/VS Code's well-known "Dark+" color scheme - CodeMirror ships no Visual Studio theme to vendor, so this approximates its actual palette (keyword blue, string orange, comment green, ...) directly in dashboard.css
- Code/diff preview gained a "Wrap lines" checkbox (default on) - the choice is remembered client-side (a browser cookie, not server state) and applied to the next preview opened, in this dialog or any other, without needing to be set again
- Enabled the built-in .NET analyzers (`AnalysisLevel=latest`, `AnalysisMode=Recommended` in `Directory.Build.props` - no new package, they ship with the SDK) alongside the existing `.editorconfig` style rules. Fixed everything it found that wasn't a deliberate convention: explicit `CultureInfo.InvariantCulture` on locale-sensitive integer-to-string conversions (WMI process IDs, per-core counter names, config values, and Serilog's own console/file sinks - so a log file reads the same regardless of the host machine's regional settings) and an explicitly-discarded P/Invoke cleanup result (`RmEndSession`). Suppressed in source (`#pragma warning disable`/`restore`, not `.editorconfig`, since each is narrowly scoped to one already-justified call site) two rules whose "violation" is a deliberate, already-documented choice: `CA5351` (MD5) on Gravatar's own hash-the-email API contract, and `CA1838` (P/Invoke `StringBuilder` parameters) on the Restart Manager interop's own already-correct, rarely-called signature. Disabled two rules that fight this codebase's own established conventions everywhere (`CA1859` return/accept concrete collection types instead of interfaces - conflicts with this codebase's ports-and-adapters encapsulation; `CA1848` use source-generated `LoggerMessage` delegates - not worth it for this service's low-volume logging) and two more scoped to `tests/` only (`CA1707` identifiers must not contain underscores - conflicts with this codebase's `Given_When_Then`-style test naming; `CA1861` prefer a static field over a literal array argument - not worth it for once-per-scenario BDD step methods)
- Three new MCP tools, and a policy reversal: `find_files` (glob search across a repository - `*`, `**`, `?` - matching files and directories alike, capped and truncation-flagged rather than unbounded) and `get_file_info` (a filesystem entry's type, size, attributes, owner, creation/modified/accessed dates, and lock status) are both explicitly described as preferred over `git_run` for file-listing/metadata questions, since a purpose-built tool gives more reliable structured data than parsing `git ls-files`/`ls` output. `delete_path` deletes one file or directory inside a repository, and `delete_repository` deletes an entire repository - both were previously dashboard-only by deliberate design ("giving the sbx caller that access risks misuse"); that decision is now reversed, and every delete (dashboard or MCP) is recorded in run history for the same after-the-fact auditability regardless of caller. All four tools are confined to the named repository's own directory via the same two-level path-confinement policy every other repository-relative-path tool already uses, and report specific, actionable errors (not-found, confinement violation, busy/locked, empty path) rather than a generic failure. The server now exposes fourteen tools in total. See [`openspec/changes/expose-file-management-mcp/`](openspec/changes/expose-file-management-mcp/) for the full design rationale
- Git PAT-based authorization, over MCP and the dashboard: `authorize_git_host` stores a personal access token for a remote host (e.g. `github.com`, `dev.azure.com`) via the host's own configured git credential helper - piped over standard input, never a command-line argument, never logged or persisted by this service - so subsequent `git_run`/`clone_repository` calls against that host authenticate transparently with no change to either tool's own contract; `list_authorized_git_hosts` and `revoke_git_host_authorization` round out the set. A `git_run`/`clone_repository` failure that looks authentication-related now gets a specific note naming `authorize_git_host` as the fix, distinguishing a host with no credential on file from one whose credential stopped working. On the dashboard side, cloning a repository that turns out to need a credential prompts for a PAT and automatically retries once one verifies (looping on an invalid token, cancelling means no clone); the existing pull/push/force-push/fetch quick actions gained the same authentication-failure detection, surfaced only as a tooltip on the already-existing flash-outcome indicator, never a popup; and a new "change credential" action and a needs-credential marker next to a repository's name round out the dashboard surface. The server now exposes seventeen tools in total. See [`openspec/changes/expose-git-credentials-mcp/`](openspec/changes/expose-git-credentials-mcp/) for the full design rationale, including two assumptions flagged as unverified until tested against a real installation (Git Credential Manager's provider-specific OAuth behavior for GitHub/Azure DevOps, and Windows Credential Manager storage under this service's own dedicated service account)
- NuGet feed PAT-based authorization, MCP only: `authorize_nuget_feed` stores a personal access token for a NuGet feed so subsequent `dotnet_run` calls (`restore`/`build`/`test`/`pack`/`push`) authenticate against it transparently, routing each feed URL internally to whichever of two mechanisms applies - an Azure DevOps Artifacts feed (`pkgs.dev.azure.com`, `*.pkgs.visualstudio.com`) is authorized via the Azure Artifacts Credential Provider's non-interactive `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS` mechanism (the token DPAPI-encrypted and persisted by this service itself, since that mechanism has no durability of its own, then re-injected as an environment variable into every `dotnet` spawn alongside `NUGET_NETCORE_PLUGIN_PATHS`); any other feed is authorized by writing a credentialed package source directly into this machine's NuGet configuration via the `NuGet.Configuration` client library, encrypted at rest by NuGet's own mechanism, never touching this service's own database. `list_authorized_nuget_feeds` and `revoke_nuget_feed_authorization` round out the set, working across both mechanisms transparently. No dashboard surface for this one (MCP only, per explicit scope). The server now exposes twenty tools in total. See [`openspec/changes/expose-nuget-credentials-mcp/`](openspec/changes/expose-nuget-credentials-mcp/) for the full design rationale, including the installer-bundling work still outstanding for the Azure Artifacts Credential Provider binary and several assumptions flagged as unverified until tested against a real installation and real feeds
- Background repository fetch: every repository under the configured root now gets a real `git fetch` on its own regular cadence (default every 5 minutes, `RepositoryFetchIntervalSeconds`) independent of any operator/MCP action, so ahead/behind and "remote gone" stay reasonably fresh even for a repository nobody actively works in. Goes through the same per-repository action (and lock, credential-outcome recording, and stats refresh) an operator-triggered fetch already uses - a repository nobody manually touches now also self-detects (and self-clears) a broken credential via this same sweep, not just its ahead/behind data. A busy repository is skipped for that cycle rather than queued; one repository's failure never stops the cycle for the rest. The first cycle waits until the host has fully finished starting (every hosted service's own startup work done, accepting connections) rather than risking running during startup itself, and then runs immediately rather than also waiting a full interval for its first sweep. See [`openspec/changes/add-background-repository-fetch/`](openspec/changes/add-background-repository-fetch/) for the full design rationale
- Network and disk I/O resource graphs, host-wide and per-run, alongside the existing CPU/RAM ones. Disk I/O reads Windows' own `PhysicalDisk`/`_Total` counter (already an all-drives-combined figure, unlike network's per-interface counters that still need summing). Neither can be isolated to one process's tree on Windows at all (no per-process network-only counter exists, and disk I/O is inherently a whole-machine figure), so every run's own graph shows that tick's host-wide reading tagged onto it - the same "no isolated figure is possible, use the host's" precedent already established for a file transfer's CPU/RAM, now extended to every run kind and to network/disk specifically. The Status page's host section is now three rows (CPU alone, scaled to full width, showing 20 minutes; CPU-per-core and RAM; network and disk I/O, 10 minutes each); a run's detail page in History is now two rows (CPU and RAM; network and disk I/O), covering the run's full recorded duration. CPU/RAM no longer show a legend (redundant with their own heading); network and disk I/O do, since each has two lines that can't otherwise be told apart. A run's detail page graphs also now update live while the run is still in flight, reusing the Status page's own live mechanism - previously this page only ever showed a static snapshot of whatever was persisted when it loaded. Unlike every Status-page live graph, a run's own graph has no fixed rolling window and keeps growing for as long as the run stays open; a run viewed before its first sample is recorded transitions from an empty-state message straight to the live graphs the moment one arrives, with no manual reload needed. Also fixed along the way, found live: every graph (not just the new ones) rendered at roughly a third of its actual container width - Chart.js's own `maintainAspectRatio: true` default computed the canvas's width from its CSS-capped height instead of filling the container, which needed both `maintainAspectRatio: false` and a dedicated sized wrapper around each canvas (Chart.js's responsive sizing needs a defined height on the canvas's parent, not the canvas itself) to actually fix. See [`openspec/changes/add-network-disk-resource-graphs/`](openspec/changes/add-network-disk-resource-graphs/) for the full design rationale
- `dotnet_run`/`git_run` subcommand allowlist and a path sanitizer: each tool now rejects any subcommand outside a fixed, known catalog (`CommandSubcommandPolicy`, twenty `dotnet` subcommands and twenty-nine `git` subcommands) before starting anything, closing off arbitrary-subcommand execution the two tools previously allowed unconditionally. A new `IPathSanitizer`/`PathSanitizer` inspects every argument that names a filesystem path (`-o`/`--output`/`--results-directory`, `-p:*Path=`/`-p:*Dir=` MSBuild properties, `git log`/`git diff --output=`) and rejects one that would resolve outside the target repository, applied everywhere a command's own arguments - not just its working directory - could otherwise be used to escape repository confinement
- MCP Settings dashboard page and per-tool/per-subcommand runtime permissions: every one of the (then) twenty MCP tools, plus every individual cataloged `dotnet`/`git` subcommand, now has its own persisted on/off switch (`McpToolCatalog`, `IMcpPermissionStore`, backed by a new `McpToolPermissions` SQLite table, cached in memory so the hot path never awaits a database call), configurable from a new `/mcp-settings` dashboard page grouped into logical fieldsets (dotnet subcommands, git subcommands, run management, repository management, file management, git/NuGet credentials, diagnostics). Every tool/subcommand that creates, deletes, or stores/removes a credential defaults to **disabled** (`delete_repository`, `clone_repository`, `delete_path`, `authorize_git_host`/`authorize_nuget_feed` and their revoke counterparts, plus every newly-cataloged subcommand beyond the original small allowed set) - an operator has to deliberately opt back in; every read-only or already-vetted tool/subcommand still defaults to enabled, so an existing installation's behavior doesn't change until an operator visits the page. A disabled tool/subcommand stays listed in `tools/list` (still discoverable) but a call to it is rejected with a specific, distinguishing error. New `get_mcp_permissions` MCP tool reports every key's current enabled state, since an operator can change permissions at any time mid-session; every other tool's description and rejection messages now point to it rather than claiming a fixed, static allowed set. The server now exposes twenty-one tools in total
- MCP Settings page gained a colored risk icon and hover/focus tooltip on every row: a red warning triangle for anything that can destroy data irrecoverably, reach outside the repository, install/trust something host-wide, or store/expose a credential; a yellow info mark for anything safe but potentially information-revealing (e.g. `list_repositories`, `transfer_file`, `list_authorized_git_hosts`, `git remote`); a green check for everything confined to the repository and fully recoverable through git or a rebuild. The tooltip (`McpPermissionTooltips`, kept in Presentation as display copy rather than a Domain concern, with a completeness unit test guarding it against drifting out of sync with the tool/subcommand catalog) explains what the row actually does, the concrete mechanism behind it, and why it's rated that way, for all sixty-eight catalog keys
- Reduced-motion-aware enter/exit animations across every dashboard list (History/Repositories/Credentials tables, Status's run/process lists, the file tree, the commit graph): a genuinely new row pops in via a CSS keyframe animation keyed off Blazor's own `@key` diffing, so only a truly new row ever plays it, no JS involved; a row an operator explicitly deletes (repository, credential, file/folder) or a run leaving Status's list plays a brief fade-out first instead of just vanishing. Entirely inert under `prefers-reduced-motion: reduce`
- History's Kind filter is now a checkbox dropdown (native `<details>`/`<summary>`, no JS) instead of an always-expanded inline checkbox list, starting fully checked so its "All kinds" summary matches the checkboxes at load
- A "Source code" link to this project's GitHub repository on the About page

- Renamed the project from `BuildAndTestService` to `OutOfTheBox`
- Replaced the originally-planned `install.ps1`/`upgrade.ps1` scripts with the WiX Toolset installer above, on explicit request — native upgrade/uninstall semantics and a proper config UI a hand-rolled script couldn't match
- Split `Program.cs`'s ~115 lines of `builder.Services.Add...` DI registrations (it had grown to 271 lines total) out into five feature-grouped extension methods under `src/OutOfTheBox.Host/ServiceRegistration/` (command execution/MCP, persistence, repository management, resource monitoring, dashboard) - each keeps its own registrations' lifetime rationale (singleton vs. scoped) as a doc comment colocated with them, and `Program.cs` itself is now a readable top-level list of five calls instead of the full wiring. Pure reorganization, no behavior change - the "one place allowed to reference both Infrastructure and Presentation" rule these methods live under is still just Host, per design.md's Layering decision
- Extracted the rest of `Program.cs`'s startup logic (data directory resolution, Serilog setup, Kestrel HTTPS enforcement, EF Core migration/WAL/interrupted-run reconciliation, and the whole middleware/endpoint-mapping pipeline) into six further `WebApplicationBuilder`/`WebApplication` extension methods under a new `src/OutOfTheBox.Host/Startup/` folder, each keeping its own moved-along rationale comments. `Program.cs` is now 62 lines (down from 271) - a top-level-statements list of named calls, not implementation. Confirmed no behavior change via the full `UnitTests`/`ArchitectureTests`/`BehaviorTests` suites (the latter exercises this exact startup path through `WebApplicationFactory<Program>`) plus a live dashboard smoke test
- Disabled `MajorUpgrade`'s `AllowSameVersionUpgrades` in the installer again (back to the WiX default, "no") - it had been turned on so re-running the installer at an unchanged `ProductVersion` (this project's `Version` has stayed 1.0.0 through many rebuilds) still counted as an upgrade, but that also widens the Upgrade table's version range to include the current version itself, which is exactly what ICE61 exists to flag (`WIX1076`, surfaced on every installer build). A same-`ProductVersion` reinstall goes back to not being recognized as an upgrade at all - uninstall then reinstall, or bump `Version`, are the ways to actually replace an existing install
- Extended the built-in-analyzer cleanup above to the installer (`installer/OutOfTheBox.Msi.CustomActions` and its own standalone `.Tests` project both build under the same root `Directory.Build.props`/`.editorconfig`, previously unchecked since the installer isn't part of `OutOfTheBox.slnx`): a real tuple-swap simplification in `SecretResolution`'s Fisher-Yates shuffle, plus the same `CA1707`/`CA1861` exceptions as `tests/` (installer custom actions and their tests share the same "runs once, not in a hot loop" and "underscore-separated test names" reasoning)
- Every hand-authored source file's copyright header now names the AGPL-3.0 license and points to `LICENSE`, instead of a bare "All rights reserved" line
- History/Repositories/Credentials' filter bars are now a two-row grid (every label lines up in row 1, its own control directly below in row 2) instead of each field wrapping its own label+control together, which left neither row lining up when labels' lengths differed; one field per page (Search, Search, Server / Feed) absorbs the bar's remaining width instead of leaving dead space after the last control

### Fixed

- Repository stats silently stopping forever after computing once at startup: a `git.exe` invocation failure (e.g. unreachable for the service account's PATH) inside the background stats sampler was left uncaught, which - since an unhandled exception in a `BackgroundService` stops the entire host by default - could silently kill the whole service, not just the sampler. One repository's stats computation failing can no longer affect any other repository or the sampler itself, let alone the host
- The page-title underline (Status/History/Repositories and their detail subpages) now tracks the heading text's actual width instead of a fixed 44px unrelated to the text

Now caught and logged per tick instead of propagating
- Repository stats could get stuck reading "Computing…" forever after a clone completed, and, separately, changes to a repository's stats made in the background sampler weren't pushed live to an open dashboard session the way an immediate post-action refresh already was - both now update live

- Clicking a commit's parent-hash link on the commit detail page updated the URL but kept showing the previous commit's data - Blazor reuses the component instance across same-route navigations, so the data reload was moved from `OnInitializedAsync` (runs once per instance) to `OnParametersSetAsync` (runs on every navigation)
- The About page's MCP tool list was missing `get_run_resources`, `get_environment_info`, and `get_file_lock_info`, and still said "eight tools"
- Repository deletion could fail with a transient "directory in use"/"not empty" error even though every file inside had already been removed - a Windows filesystem race (AV/indexer handle release lag) between the last file disappearing and the now-empty directory itself becoming deletable. - The History page never updated live - unlike Status, it had no `IRunEventBus` subscription at all, so a run's completion (whether triggered from the dashboard or, as found live-testing against a real install, via an MCP `dotnet_run`/`git_run` call) only ever appeared after a manual reload or an unrelated filter interaction happening to re-query. It now subscribes the same way Status does
- Auditing every dashboard view for the same gap found two more: a repository detail page's own History tab had the identical missing-subscription bug (its run list loaded once and never refreshed), and a run's own detail page had no live subscription at all - opening a still-in-flight run's detail (reachable from either History view) showed a permanently stale snapshot, never reflecting the run's actual completion, exit code, or output even after it finished. Both now subscribe and refresh the same way
- The code/diff preview's mouse wheel and scrollbar didn't work - CodeMirror's own custom scrollbar rendered but never moved anything, and neither did the mouse wheel. Root cause: the height cap and `overflow-y` were applied to the outer `.CodeMirror` wrapper instead of the inner `.CodeMirror-scroll` element CodeMirror itself manages, creating two competing scroll containers whose state never stayed in sync - a well-known CodeMirror pitfall its own docs warn about. Moving the cap to `.CodeMirror-scroll` (its own documented pattern for "auto-height up to a cap") fixes both
- Click-outside-to-close (added just above) could misfire on a click *inside* a dialog: it only checked whether the click's coordinates fell outside the dialog's content box, not which element was actually clicked, so a keyboard-activated click (Enter/Space on a focused control) or a script-dispatched one - both reporting coordinates of 0,0 - read as "outside" no matter where the control actually sat, closing the dialog out from under an in-progress interaction (caught live via the new word-wrap checkbox). Now also requires the click's own target to be the dialog element itself (true only for a genuine backdrop click), not merely coordinates outside its box

- An unusually long commit subject in the commit graph forced the whole table - and with it the page itself - to grow far past the viewport (over 1900px wide in testing), rather than truncating with the ellipsis the column was already styled for: `white-space: nowrap` makes an auto-layout table treat a cell's full unwrapped width as a hard minimum for its column, which `text-overflow: ellipsis` can never actually reach. Capping just that column's contribution to the width computation (`max-width: 0` paired with `width: 100%`) fixes it without touching the shared `.data-table`/`.col-shrink` convention every other dashboard table's fixed-width columns depend on

Dropping `width: 100%` (unnecessary - `max-width: 0` alone was already enough; the flexible column's own un-widthed `<col>` already claims the remaining space, same as every `.col-shrink` sibling column already relies on) fixes both without reintroducing the original overflow
- The "Clean" confirmation dialog's message didn't wrap and got a horizontal scrollbar instead, unlike every other confirmation dialog with shorter text. Root cause: `showModal()` promotes a `<dialog>` to the browser's top layer for visual positioning, but that's a rendering concept only - the element stays exactly where it's written in the DOM for CSS inheritance, and `RepositoryQuickActions.razor`'s own confirmation dialog lives inside the repository list's actions cell, which sets `white-space: nowrap` for its own icon-button row. The dialog silently inherited that nowrap too; a short message (Delete's) never got long enough to visibly hit it. Resetting `white-space: normal` on every dialog (plus `min-width: 0` on its direct children, the standard fix for a flex column child refusing to shrink/wrap) makes dialog content immune to whatever white-space its ancestor in the DOM happens to set, not just this one already-found case
- A commit message containing an emoji or other non-ASCII symbol (common in real-world repositories, e.g. Gitmoji-style conventions) rendered incorrectly - mangled into mojibake instead of the actual character. `dotnet`/`git` were spawned without an explicit output encoding, so .NET fell back to decoding their redirected stdout/stderr using the console's own output code page (on Windows, typically a legacy ANSI/OEM one, not UTF-8) - but git writes commit data as UTF-8 by default regardless of console codepage, so any multi-byte UTF-8 sequence got misinterpreted. Explicitly decoding both streams as UTF-8 fixes every run and git-status lookup that flows through the shared process runner, not just commit messages specifically
- The commit detail page's Author/Committer avatars weren't vertically aligned with their name/email/date text, the name/email/date ran together as one plain line (e.g. "Jane Doe <jane@example.com> on 2026-08-10 12:00:00"), and the email wasn't clickable. The name is now bold, the email a `mailto:` link, the date on its own second line, and the avatar sized to exactly match that two-line block's height via `align-items: stretch` - which surfaced a second, pre-existing bug: the avatar briefly rendered as a ~300px circle instead. Root cause was a classic circular sizing dependency (a percentage-sized `<img>` inside a shrink-to-fit flex item falls back to the CSS spec's default 300x150 replaced-element size, which then became the "fit content" the avatar itself sized to), compounded by flexbox's `aspect-ratio` sizing algorithm being unable to derive an item's cross-axis-driven main size when the flex container's own cross size is itself content-based rather than definite. Switching `.commit-person` from flex to CSS Grid (whose `aspect-ratio` + `align-items: stretch` interaction has no such restriction) and taking the avatar's image/fallback out of normal flow (`position: absolute`) fixes both
- Renaming a repository made its Clone Source revert to "Unknown (not cloned through this service, or history since pruned)", and its entire run history (build/test/git runs, not just the clone) silently disappeared from its History tab - even though nothing was actually lost. Run history is looked up by the repository's resolved absolute path, and renaming only moved the directory on disk; every already-persisted run record still pointed at the old, now-nonexistent path, so nothing under the new name matched it anymore. `RenameAsync` now repoints every matching run record to the new path as part of the rename
- Every `.data-table`'s flexible column (History/a repository's own run-history tab's Detail, Repositories' Name, a commit's changed-files' Path) grew the whole table - and with it the page - past the viewport instead of truncating with an ellipsis, whenever its content was unusually long (a long clone URL, command line, file path, or repository name); only the commit graph's own Subject column had this fixed before, one-off. Generalized that same `max-width: 0` technique (documented on `.ellipsis` itself now) to every table's flexible column at once, scoped to skip the handful of `.col-shrink` columns (e.g. History's Repository column) that also carry `.ellipsis` defensively but still need to size to their typical content rather than collapse to nothing
- `FileTreeComponentTests` (and, this session established, potentially any of the seven dashboard bUnit component test classes) intermittently failed with a `WaitForAssertion` timeout when the full `UnitTests` suite ran - a different specific test each time, never reproducing in isolation. Root cause: bUnit's own 1-second default `WaitForAssertion` timeout, tight enough that a component's render can legitimately exceed it once dozens of these test classes' Blazor renderers are competing for CPU under xUnit's default cross-class parallelism - a scheduling/contention symptom, not a logic bug in any one test. All seven now derive from a shared `DashboardComponentTestContext` base (10-second `DefaultWaitTimeout`) instead of `BunitContext` directly; confirmed clean across five consecutive full-suite runs
- Found from a real deployment's log file: `AntiforgeryValidationException`/`CryptographicException: The key ... was not found in the key ring`, meaning ASP.NET Core's Data Protection key ring - which also encrypts the dashboard's own auth cookie, not just antiforgery tokens - was not reliably persisting across service restarts. No explicit key persistence had ever been configured, so it fell back to an implicit default location tied to a loaded user profile; this service runs under a dedicated least-privilege account that may not have one, the same class of risk already flagged (but, until now, unconfirmed) for git's Windows Credential Manager and NuGet's DPAPI-based encryption. Left unfixed, every service restart would have silently logged out every operator, not just occasionally broken a form post. - Also from that same log: two more real, previously-latent bugs, both fixed. (1) `WorkingDirectoryResolver`'s symlink-resolution step logged a full Warning-level stack trace every time any caller referenced an already-deleted or never-existing repository name (an entirely routine "not found" outcome, not a symlink problem) - `Directory.ResolveLinkTarget` throws `DirectoryNotFoundException` for a nonexistent path rather than returning `null` as this code had assumed; now handled silently, matching every call site's own already-graceful `Directory.Exists` follow-up check. Confirmed against the actual NuGet.Client source rather than guessed again - the real environment variable for a `dotnet` process is `NUGET_NETCORE_PLUGIN_PATHS`, and it takes a semicolon-separated list of full plugin *file* paths, not a directory. - A spawned `dotnet`/`git` command whose own process tree grew deep and fast (confirmed live: a `dotnet_run` against a project that itself runs `dotnet test`, which runs `vstest.console`, which runs `testhost.exe`) could leave a real OS process running indefinitely even after the run was cancelled, timed out, or the service reported it complete. Root cause: `Process.Kill(entireProcessTree: true)` walks a live snapshot of running processes matched by parent-PID and start time - a descendant still being created at the instant of that snapshot can be missed entirely, with no parent left to ever kill it. Every process this service spawns is now also assigned to a Windows job object configured with kill-on-close (`ProcessJobObject`), which Windows itself keeps every future descendant in automatically regardless of nesting depth or timing, closed unconditionally (both on cancellation and normal completion) so nothing a run ever spawned can outlive it
