## Context

See `proposal.md` for motivation. Relevant existing state this design builds on:

- `IRepositoryFileBrowser`/`RepositoryFileBrowser` (`OutOfTheBox.Application`/`Infrastructure.Repositories`) already implements confined list/delete/rename for the dashboard's file tree browser, including `RunRegistry` locking around mutations and `RecursiveDelete`'s retry-on-transient-Windows-lock behavior. `DeleteAsync` in particular is already fully correct, tested (indirectly, via the dashboard) production logic - `delete_path` is a new *caller* of it, not new deletion logic.
- `IRepositoryManager.DeleteAsync` (repository-level) already exists too, called today only from `Repositories.razor`'s delete button. It runs synchronously to completion (not fire-and-forget like `CloneAsync`) and returns `RepositoryActionResult.Accepted(RunId)` once the delete has already finished - the `Run` row it persists (`RunKind.RepositoryDelete`) is the only place the actual outcome (`Completed`/`Failed`, and on failure, the OS error message in `Stderr`) is recorded; `Accepted` itself doesn't carry it.
- `FileTransferMcpTools.TransferFileAsync`/`FileLockDiagnosticsMcpTools.GetFileLockInfoAsync` establish this codebase's two-level path confinement pattern for every repository-relative-path MCP tool: `IWorkingDirectoryResolver.Resolve(repository)` then `.ResolveWithinRoot(repositoryRoot, path)`, each rejected with a distinct, specific `McpException` message.
- `IFileLockInspector.GetLockingProcessesAsync` (built for `get_file_lock_info`) already answers "is this file locked, and by what" - `get_file_info`'s `IsLocked` field reuses it directly rather than reimplementing lock detection.
- Read-only MCP diagnostic tools (`get_run_resources`, `get_file_lock_info`, `get_environment_info`) create no persisted `Run`/history record, by established precedent. Mutating ones (`transfer_file`, `clone_repository`, `dotnet_run`/`git_run`) all do.

## Goals / Non-Goals

**Goals:**
- Let a caller find files by name/extension/pattern, and inspect one entry's real filesystem state, without needing to already know an exact path or resort to `git` (which only sees tracked/committed content, not the actual working tree).
- Let a caller clean up a file, directory, or entire repository it created, without operator involvement for every deletion.
- Every error carries enough specific detail (which boundary was violated, or the underlying OS error) for a caller to actually correct its next call, not just learn that something failed.

**Non-Goals:**
- Not adding move/copy/rename via MCP - not requested, and `RenameAsync` already exists on the same port if a future change wants it; this one stays narrowly scoped to find/inspect/delete.
- Not adding an "undo" for `delete_path`/`delete_repository` - deletion is exactly as permanent via MCP as it already is from the dashboard (both ultimately call the same methods).
- Not trying to out-do `git status`/`git log` for anything git-specific (history, diffs, tracked-vs-untracked) - `find_files`/`get_file_info` answer "what's actually on disk and what does it look like," a real filesystem question `git`'s index-relative view can't answer directly (an untracked or `.gitignore`d file is invisible to `git ls-files`, but very much a real file `find_files` will see).

## Decisions

### Glob matching: `Microsoft.Extensions.FileSystemGlobbing`'s single-path `Matcher.Match`, not its file-walking `Execute`
This is a first-party Microsoft package (no new third-party dependency, same bar `ModelContextProtocol`/`Markdig` were held to) that natively supports `*`, `**`, and `?` - exactly the set requested. Its usual API, `Matcher.Execute(DirectoryInfoWrapper)`, walks the filesystem itself and returns only *file* matches - directories are internal-traversal-only, never reported as results, since the library's primary use case (MSBuild `Include`/`Exclude` globs, `.gitignore`-style filters) is file-oriented. Since the request explicitly needs *directories* in the results too ("list directories and files"), this change instead does its own confined recursive walk (`Directory.EnumerateFileSystemEntries(..., AllDirectories)`, exactly like `ListDirectoryAsync`'s existing single-level walk but recursive) and tests each entry's repository-relative path against the pattern via `Matcher.Match(relativePath)` - a pure string-pattern test with no filesystem opinions of its own, so it works identically for a file's or a directory's relative path. This reuses the library for what it's actually good at (correct `*`/`**`/`?` semantics) without fighting its files-only `Execute` shape.

### `find_files` results are capped, with a `Truncated` flag - same shape as every other unbounded MCP result
`ServiceOptions.McpMaxFindFilesResults` (default 2000) bounds the returned list the same way `OutputCapBytes`/`McpMaxFileTransferBytes` already bound theirs - a pathologically broad pattern (`**/*` on a huge repo) stops collecting once the cap is hit rather than building an unbounded in-memory list or MCP payload; the result records whether it was capped so a caller knows to narrow its pattern rather than trusting an apparently-complete list.

### `get_file_info`'s fields, and how each is sourced
- **Type**: `IsDirectory`, from `Directory.Exists`/`File.Exists` (same check `ListDirectoryAsync`/`DeleteAsync` already use).
- **Size**: `FileInfo.Length` for a file; `null` for a directory - computing a directory's recursive total size is a full walk this codebase already treats as expensive enough to run on a slow background cadence (`RepositoryStatsSampler`'s own size sampling, per its own two-cadence design decision), not something to redo synchronously per metadata call.
- **Attributes**: `File.GetAttributes`/`FileSystemInfo.Attributes` (`FileAttributes` flags - ReadOnly, Hidden, System, Archive, ReparsePoint, ...), returned as their flag names.
- **Dates**: `CreationTimeUtc`/`LastWriteTimeUtc`/`LastAccessTimeUtc` from `FileSystemInfo`.
- **Owner**: `FileSystemAclExtensions.GetAccessControl(...).GetOwner(typeof(NTAccount))` (`System.Security.AccessControl`, part of the Windows-specific reference assemblies for `net10.0-windows`, no new package) - falls back to the raw SID string if the account can't be resolved to a friendly name (e.g. an orphaned/deleted account), and to `null` entirely if the ACL call itself fails (e.g. a permissions problem reading the ACL, distinct from - and not fatal to - reading the rest of the entry's metadata).
- **IsLocked**: reuses `IFileLockInspector.GetLockingProcessesAsync`, files only (`false` for a directory - Restart Manager's own model is file-based).

### `delete_path`/`delete_repository` are thin MCP wrappers around already-existing, already-correct deletion logic
Neither adds new deletion behavior. `delete_path` calls `IRepositoryFileBrowser.DeleteAsync` directly - the same method `RepositoryQuickActions`' dashboard delete button already calls, including its existing `RunRegistry` locking and `RecursiveDelete` retry behavior. `delete_repository` calls `IRepositoryManager.DeleteAsync` directly - same method `Repositories.razor`'s delete button already calls. The only new work is mapping each existing result shape to a proper MCP diagnostic response (see below), not reimplementing deletion.

### `delete_repository`'s diagnostics require a follow-up `Run` lookup; `delete_path`'s don't
`IRepositoryManager.DeleteAsync` returns `RepositoryActionResult.Accepted(RunId)` once the delete has already finished, but `Accepted` itself carries no outcome - the real result (`Completed` vs `Failed`, and on failure, the OS error message) lives only in the `Run` row it persisted. `delete_repository` therefore does one `IRunRepository.FindByIdAsync(runId)` immediately after the call to surface that detail to the MCP caller - a synchronous follow-up read, not a poll (the delete has already finished by the time `DeleteAsync` returns). `IRepositoryFileBrowser.DeleteAsync`, by contrast, already returns a fully-detailed `RepositoryFileActionResult` (`Succeeded`/`Failed(ErrorMessage)`/`Rejected(Reason)`) synchronously and directly - `delete_path` maps it straight to an `McpException` or success result with no extra lookup needed.

### `delete_path` gains its own run-history record; `find_files`/`get_file_info` don't
`IRepositoryFileBrowser.DeleteAsync` (used by both the dashboard and now MCP) previously created no `Run`/history record at all - a real, if minor, pre-existing gap (an operator couldn't tell after the fact who deleted a file and when, dashboard or MCP). Since this change already touches `DeleteAsync` (to add the new `IFileLockInspector` dependency `GetMetadataAsync` needs on the same class) and is explicitly adding external, MCP-reachable delete capability, it also adds history recording directly inside `DeleteAsync` itself (a new `RunKind.RepositoryFileDelete`) - both the dashboard's and MCP's delete calls now get one consistent history trail, rather than the MCP tool bolting on its own separate, parallel recording the way a read-only tool's result never needed. `RenameAsync` is untouched (out of scope - no MCP tool calls it). `find_files`/`get_file_info` stay unrecorded, per the existing read-only-diagnostic-tool precedent (`get_run_resources`, `get_file_lock_info`, `get_environment_info`).

### "Prefer these over `git` for file information" lives in the tools' own `[Description]` text, not just prose docs
An MCP client's only runtime-visible signal for *when* to reach for a tool is its discovered description (and its parameters' own descriptions) - a caller never reads `About.razor` or this proposal before deciding which tool to call. `find_files`'/`get_file_info`'s `[Description]` attributes therefore say directly that they reflect the real, current filesystem state and should be preferred over `git_run` (`git ls-files`/`git status`/etc.) for file-listing or metadata questions, which only reflect git's own tracked/index view.

## Risks / Trade-offs

- **[Risk]** A manual recursive `Directory.EnumerateFileSystemEntries(..., AllDirectories)` walk, unlike `Matcher.Execute`'s own internal walk, doesn't skip directories a narrow pattern could never match under (e.g. `src/**/*.cs` still walks `tests/` even though nothing there can match) - a real, if bounded, extra cost on a very large repository. → Accepted: `McpMaxFindFilesResults` bounds the *result* size, and this project's repositories are development working trees, not the kind of monorepo scale (hundreds of thousands of files) where an unfiltered recursive walk's own cost - not the pattern matching - would start to matter; revisit with directory-level pattern pruning only if a real repository's walk time becomes a problem.
- **[Trade-off]** `get_file_info`'s owner lookup is one more Windows ACL syscall per call - accepted the same way `get_file_lock_info`'s Restart Manager session is: an occasional diagnostic call, not a hot path.
- **[Risk]** Reversing "no delete via MCP" removes a boundary that was originally a deliberate design decision (`mcp-repository-access`'s own spec still says why: dashboard-only, operator-confirmed). → Accepted per direct instruction; every other dashboard-only action (pull/push/branch-switch/checkout/rename) is untouched, and delete's own existing safeguards (path confinement, the per-repository lock, `RecursiveDelete`'s retry-not-silent-failure behavior) all still apply identically when triggered via MCP.

## Migration Plan

Purely additive except for `RunKind.RepositoryDelete`'s doc comment (no longer accurate - it *is* now reachable via MCP) and `IRepositoryFileBrowser.DeleteAsync` gaining history recording. No schema migration needed for the new `RunKind.RepositoryFileDelete` value (`RunKind` persists as a plain integer column via EF Core's default enum-to-int conversion, and a new enum member is purely additive to that mapping). No feature flag - reachability is already gated by the same bearer token every other MCP tool requires. Ship in the next installer build; the About page's MCP tool list gets updated in the same change.
