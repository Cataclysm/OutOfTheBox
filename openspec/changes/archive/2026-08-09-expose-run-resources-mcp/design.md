## Context

See `proposal.md` for motivation. Relevant existing state this design builds on:

- `ResourceHistoryBuffer` (`OutOfTheBox.Application.Monitoring`, a singleton) already keeps a 10-minute rolling window of `ResourceHistoryPoint`s (`Timestamp`, `CpuPercent`, `RamBytes`, plus host-only fields) per series key - `HostResourceSamplerService` writes to it every `ResourceSamplerIntervalSeconds` (~3s default) for the host series and for every currently-tracked run's series (keyed by `runId.ToString()`), and removes a run's series entirely once that run reaches a terminal state. This is exactly the data `LiveResourceGraph.razor` already reads to seed and drive the dashboard's live per-run chart - this change adds a second reader, not a new writer.
- `IRunResourceSampleRepository.GetSeriesAsync(runId)` is a *different*, DB-persisted series (`RunResourceSample` rows), written by the same sampler tick, that survives past a run's termination (used by `run-history`'s own detail views). It was considered as this tool's data source and rejected - see Decisions.
- `IResourceSampler.SampleAsync(...)` (the thing `HostResourceSamplerService` calls each tick) is explicitly documented as "stateful across calls (per-process CPU delta-sampling needs the previous tick's figures)". It was considered for an on-demand "sample right now" tool and rejected - see Decisions.
- The three existing MCP tool classes (`CommandExecutionMcpTools`, `RepositoryAccessMcpTools`, `FileTransferMcpTools`) live in `OutOfTheBox.Presentation/Mcp/`, are plain DI-constructed `[McpServerToolType]` classes registered in `Host/Program.cs`, and call only `Application`-layer ports/singletons - no `Infrastructure` reference, mechanically enforced by `ArchitectureTests`. `read_run_output`/`cancel_run` both look up the run via `IRunRepository.FindByIdAsync` first and throw `McpException($"Unknown run id '{runId}'.")` for a miss - the same check this tool reuses for its own "unknown run id" rejection.

## Goals / Non-Goals

**Goals:**
- Let an MCP caller judge "is this run still doing something" from a single tool call, without it having to interpret raw time-series points itself.
- Add zero new server-side state and zero new background work - read an existing, already-correct, already-populated singleton.

**Non-Goals:**
- Not exposing per-process detail (individual `ProcessId`/`ProcessName` within a run's process tree) or a kill-one-process capability. `ResourceHistoryBuffer` only ever stores a run's *aggregate* CPU/RAM (matching the persisted `RunResourceSample` shape) - individual process breakdown exists only momentarily, inside whichever `ResourceSnapshot` a live dashboard subscriber happens to receive from `IResourceEventBus`'s publish-only fan-out. Surfacing it to MCP would need new state (a "latest snapshot" cache) for a capability the proposal's core problem (hung vs. slow) doesn't need - aggregate CPU already answers that. Deferred to a future change if a concrete need for per-process/kill-one-process shows up.
- Not adding an on-demand "sample right now" tool that calls `IResourceSampler.SampleAsync` directly from the MCP request path. See Decisions.

## Decisions

### Data source: the existing `ResourceHistoryBuffer`, not `IRunResourceSampleRepository` or a fresh `IResourceSampler.SampleAsync` call
Three sources were available; one was chosen.

1. **`ResourceHistoryBuffer.Get(runId.ToString())` (chosen).** In-memory, already exists, already correctly populated, zero new state or DB round trip. Its 10-minute window comfortably covers the "has this been idle for the last few minutes" question this tool exists to answer, and it's evicted on a run's terminal event - which is fine, even desirable: once a run has finished, its resource *trend* is no longer diagnostically interesting (the caller already has the terminal status from `read_run_output`).
2. **`IRunResourceSampleRepository.GetSeriesAsync(runId)` (rejected).** Persisted, so it survives past termination and returns a run's *entire* history rather than a 10-minute window - but that's a mismatch for this tool's purpose (diagnosing an *in-flight* run) and a DB round trip on every poll, for a caller that may poll every few seconds while watching a build. A long-running `dotnet test` could also accumulate hundreds of rows, and returning all of them would bloat the MCP response for no benefit over the windowed in-memory series. Worth revisiting only if a future need specifically wants post-mortem resource history for a *finished* run (e.g. attached to `read_run_output`'s terminal result) - a different problem from this one.
3. **Calling `IResourceSampler.SampleAsync(...)` directly from the tool, on demand (rejected).** `IResourceSampler`'s own doc comment warns it is "stateful across calls (per-process CPU delta-sampling needs the previous tick's figures)" - CPU percentages are computed as a delta between consecutive calls (matching how `PerformanceCounter`/process-CPU sampling works generally: a single point-in-time reading isn't meaningful, only the delta over a known interval is). An MCP-triggered out-of-band call would shift that "previous tick" baseline, shrinking the interval the *next* scheduled sampler tick computes its delta over and skewing that tick's CPU% - a real correctness bug for the dashboard's own live graphs, not just a theoretical concern. Reading the buffer instead of the sampler avoids touching that shared stateful call path at all.

### Derived summary computed by a new small pure Application-layer type, not inline in the MCP tool
The tool needs to turn a list of `ResourceHistoryPoint` into "latest CPU%, peak CPU% in window, seconds since CPU last exceeded an idle threshold" - a handful of edge cases (empty series, a single point, idle-the-whole-window, active-right-now, exactly-at-the-threshold) worth its own direct unit tests rather than only being exercised indirectly through the MCP tool. `ResourceHistoryPoint` itself lives in `Application.Monitoring` (not `Domain` - `ResourceHistoryBuffer` and its point type are Application-layer concurrency-adjacent state, the same reasoning that already keeps `RunRegistry` out of Domain), so a pure function over it cannot live in `Domain` either (`Domain` has zero dependencies, including on `Application`). A new `RunResourceTrend` static class in `Application.Monitoring`, structurally the same kind of addition `CommitGraphLayout` was to `Domain` - pure, no IO, directly unit-testable - is the right home. The idle threshold (a low-CPU-percent cutoff below which the run is considered "not actively working") is a constant on this type, not caller-configurable - this tool is a diagnostic aid, not a monitoring API with SLA-shaped thresholds.

### Read-only: no `kill_process` tool in this change
The dashboard's own "Kill" button (`IProcessMonitor.KillAsync(processId, expectedStartTime, ...)`) already exists and is already safe to call (server-side re-verified against the live process tree and a `StartTime` match, rejecting a stale/reused PID) - but exposing *individual process termination* over MCP is a materially different, larger capability than read-only trend data: it's remote-triggered process control, on a bearer-token-authenticated surface with no finer-grained scoping today. `cancel_run` already covers "stop the whole run", which is the only kill granularity this service's MCP surface has ever offered. Adding kill-one-process is deferred as its own change, to be justified by an actual observed need (e.g. a multi-process run where killing the whole thing loses useful partial results) rather than spec'd speculatively alongside a read-only diagnostic tool.

## Risks / Trade-offs

- **[Risk]** A run whose process tree legitimately does heavy I/O with little CPU (e.g. a slow disk-bound restore) could read as "idle" by a naive CPU-only threshold, even though it's making real progress. → Mitigation: the tool returns the raw RAM figures too (RAM usually keeps changing during real I/O-bound work even when CPU doesn't), and the summary is explicitly framed as a diagnostic aid ("looks idle") for the calling agent's own judgment, not an authoritative hung/not-hung verdict - the spec's wording ("distinguishing it from a run that was busy a moment ago") deliberately stops short of promising certainty.
- **[Trade-off]** The 10-minute window means a run idle for longer than that shows only "fully idle for the whole visible window," not exactly how long beyond 10 minutes. Accepted: at that point the caller has more than enough signal to act (cancel or keep waiting), and extending the window would mean diverging `ResourceHistoryBuffer`'s window size from what the dashboard's own graphs use it for, for a marginal diagnostic gain.

## Migration Plan

Purely additive - one new MCP tool, one new pure-computation type, no schema/config changes, no impact on the three existing MCP tool classes or the dashboard's own consumption of `ResourceHistoryBuffer`. Implement behind the existing `dotnet build`/`dotnet test` gates, verify live against a real running `Host` (a real `get_run_resources` call against an actually in-flight run, observing CPU trend correctly - see tasks.md), ship in the next installer build. No feature flag - reachability is already gated by the same bearer token every other MCP tool requires.
