## Why

`git_run`/`clone_repository` can already run arbitrary git commands against a repository, but every remote operation over HTTPS against an authenticated host (GitHub, Azure DevOps, or any other PAT-based remote) fails today unless a human has already logged into the service account interactively at least once, or manually configured a credential on the host - there is no MCP-reachable way for the sbx caller to authorize git against a remote server at all. GitHub requires PAT (or SSH key) auth for every HTTPS git operation since 2021 - there is no password fallback - and Azure DevOps supports the identical PAT-as-Basic-Auth-password model, so a single PAT-based design covers both without per-host special-casing.

## What Changes

- Add an `authorize_git_host` MCP tool: accepts a host (e.g. `github.com`, `dev.azure.com`) and a PAT, stores it via git's own credential-helper protocol (`git credential approve`, piped over stdin - never a command-line argument, never logged) so every subsequent `git_run`/`clone_repository` call against an `https://{host}/...` remote authenticates transparently with no change to either of those tools. Verifies the credential is actually retrievable (`git credential fill`) before reporting success, rather than trusting the write.
- Add a `list_authorized_git_hosts` MCP tool: lists which hosts have a credential configured (host, when it was authorized, and its current health - whether the most recent network-touching operation against it succeeded or failed for an authentication reason) - never the token itself, which this service never persists or reads back after the initial write.
- Add a `revoke_git_host_authorization` MCP tool: removes a host's stored credential (`git credential reject`) and this service's own record of it.
- All three are synchronous (sub-second, no process tree to poll), confined to no specific repository (credentials are host-scoped, matching git's own credential-matching granularity), and every failure reports a specific, actionable reason - no configured credential helper, git.exe unreachable, or the post-write verification failing - not a generic "failed."
- A `git_run`/`clone_repository` failure that looks like an authentication failure gets an enriched message identifying it as such and pointing at `authorize_git_host` - distinguishing "never authorized this host" from "a credential is on file but stopped working" (a strong signal it expired or was revoked upstream) - rather than only relaying git's raw stderr, which an MCP caller has no reliable way to interpret as specifically auth-related versus any other failure.
- **Dashboard: cloning a repository that requires authentication prompts for a PAT in-dialog**, rather than the clone silently failing with the operator finding out only later (or not at all - today a failed clone is not obviously surfaced anywhere in the UI at all). The clone dialog stays open and watches the started clone; on a failure it classifies as authentication-related, it switches to a "this host needs a PAT" prompt, saves the entered token the same way `authorize_git_host` does (same `IGitCredentialStore`, not a parallel mechanism), and automatically retries the same clone. A PAT that still doesn't work re-prompts with an explicit "that didn't work" message, looping until one succeeds or the operator cancels - cancelling means no clone happens at all, not a partially-completed one left behind.
- **Dashboard: pull/push/force-push/fetch/clean do not get an auto-popup on an authentication failure** - per direct instruction, they keep their existing quick-flash-red outcome reporting unchanged, just with the failure's actual message now surfaced as a tooltip (previously discarded entirely) so an operator can tell an auth failure apart from any other and know to go fix it deliberately, rather than the flow being interrupted by a popup mid-action.
- **Dashboard: a new "change credential" action** (Repositories list row and repository detail page, alongside the existing pull/push/force-push/fetch/clean/rename/delete actions) opens the same PAT-prompt dialog for the repository's own remote host, for updating an expired/revoked PAT without needing MCP at all.
- **A repository whose remote host currently appears to need a working credential is marked with a symbol next to its name**, in both the Repositories list and its detail page - derived from whether the most recent network-touching git operation against that host (pull/push/force-push/fetch/clone) actually failed for an authentication reason, not merely "no credential has ever been stored" (a fully public, anonymous-read remote never needs one at all, and marking every unauthorized host would be noise, not signal).
- **`list_repositories` (MCP) reports the same needs-credential state per repository** - no separate tool; it's a new field on the same result shape the dashboard's own list already renders from, so an MCP caller sees exactly what the operator sees.

## Capabilities

### New Capabilities
- `mcp-git-credentials`: lets an MCP caller store, list, and revoke PAT-based git credentials for a remote host, so `git_run`/`clone_repository` can authenticate against it without operator involvement, and lets an operator do the same interactively from the dashboard when a clone needs a PAT or an existing one has stopped working.

### Modified Capabilities
- `mcp-server`: "Tool discovery lists exactly the tools this service defines" grows to include `authorize_git_host`, `list_authorized_git_hosts`, and `revoke_git_host_authorization` (seventeen tools total).
- `repository-management`: clone gains an in-dialog PAT-prompt-and-retry flow on an authentication failure; pull/push/force-push/fetch/clean's existing flash-outcome reporting gains a failure-detail tooltip; a new dashboard-only "change credential" action is added alongside the existing per-repository actions; the repository list/detail gain a needs-credential symbol next to the name.
- `mcp-repository-access`: `list_repositories`' result gains the same needs-credential field.

## Impact

- **Affected code**: new `IGitCredentialStore` port (`OutOfTheBox.Application`) and `GitCredentialStore` implementation (`OutOfTheBox.Infrastructure.Repositories`); a new `GitHostAuthorization` Domain record (host/timestamp only - never the token, and no username: PAT-only auth, no username parameter anywhere in this capability's surface); a new `GitCredentialsMcpTools.cs` (`OutOfTheBox.Presentation.Mcp`); `ProcessRunRequest`/`IProcessRunner`/`CliProcessRunner` gain an optional stdin parameter (backward-compatible - every existing caller is unaffected), since no existing process-spawning path in this codebase currently writes to a child process's stdin. A new Domain-level `GitAuthFailureClassifier` (pure stderr-pattern matching, no IO) shared by the MCP result-enrichment and the dashboard's clone-retry/quick-action-tooltip/needs-credential logic, so the surfaces can't drift on what counts as "an auth failure." A new shared `PatPromptDialog.razor` (the "get a working PAT for a host, looping on failure, or report cancelled" concern, used both by `CloneDialog` and the new standalone "change credential" action) and a new vendored icon, reused for both the "change credential" action and the needs-credential name marker. A new `GitHostCredentialHealth` Domain record (host, last-auth-failure timestamp, last-auth-success timestamp - separate from `GitHostAuthorization`, since a host can need attention whether or not it was ever explicitly authorized through this capability) drives the needs-credential computation, folded into the existing repository-stats sampling pass (`GitRepositoryStatsProvider` already fetches each repository's remotes on every pass - deriving the `origin` host from that is free, no new network call); `list_authorized_git_hosts` reads both `GitHostAuthorization` and `GitHostCredentialHealth` to report configuration and health together.
- **New persistence**: two small tables - `GitHostAuthorizations` (host, authorized-at) and `GitHostCredentialHealth` (host, last-failure-at, last-success-at) - via the existing `OutOfTheBoxDbContext`/EF Core Migrations pattern. Neither stores the secret itself.
- **No new package dependency** - `git credential approve`/`fill`/`reject` are git's own built-in commands, invoked the same way every other `git` subcommand already is in this codebase.
- **Depends on** Git for Windows' bundled Git Credential Manager being installed and configured (`credential.helper`) - already a chained installer prerequisite for this whole service; `authorize_git_host` checks for a configured helper up front and fails with a specific diagnostic if none is present, rather than a confusing downstream git error.
- Docs updated: the About page's MCP tool list/count, `INSTALL.md` if the credential-helper prerequisite needs calling out explicitly.
