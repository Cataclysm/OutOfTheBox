## Context

See `proposal.md` for motivation. Relevant existing state this design builds on:

- `IProcessRunner`/`ProcessRunRequest`/`CliProcessRunner` (`OutOfTheBox.Application.Execution`/`Infrastructure`) already spawn `dotnet`/`git` child processes for `dotnet_run`/`git_run`/`clone_repository`, and `GitCaptureRunner` (`OutOfTheBox.Infrastructure.Repositories`) already wraps a short-lived `git` invocation for ad-hoc lookups (`RepositoryManager`, `GitRepositoryStatsProvider`). Neither writes to a child process's stdin - every existing `git`/`dotnet` invocation only ever needs command-line arguments and reads stdout/stderr.
- `OutOfTheBoxDbContext`/`IRunRepository` (`OutOfTheBox.Infrastructure.Persistence`) is this service's one existing SQLite-backed persistence path, via EF Core Migrations - the established place a new small table belongs, not a second ad-hoc store.
- `FileManagementMcpTools`/`FileLockDiagnosticsMcpTools` establish this codebase's pattern for a synchronous (non-run-registry, non-pollable) MCP tool: no `Run`/history record, a direct result or a specific `McpException` on failure.
- Git for Windows (bundled by this service's own Burn bootstrapper, per `installer/OutOfTheBox.Bootstrapper`) ships Git Credential Manager and configures `credential.helper` at the system level by default on a fresh install - the actual secret storage backend (Windows Credential Manager, DPAPI-protected under whatever account git runs as) is therefore already present on every machine this service targets, without this change needing to write or audit any of that storage code itself.
- `CloneDialog.razor` (`OutOfTheBox.Presentation.Dashboard`) currently submits, then immediately closes on `RepositoryActionResult.Accepted` without ever learning whether the clone it just started actually succeeds - `RepositoryManager.CloneAsync` is fire-and-forget (a tracked `Run`, not an awaited outcome), so today a clone that fails for *any* reason (auth or otherwise) is invisible in the dialog and not obviously surfaced anywhere else either (a failed clone typically never creates a listable directory, so it doesn't appear in `Repositories.razor`'s own list - only `History`, which an operator has to think to check).
- `RepositoryQuickActions.razor` already returns a `RepositoryGitActionResult.Failed(string? ErrorMessage)` for pull/push/force-push/fetch/clean, but today discards `ErrorMessage` entirely - the flashed-red icon carries zero detail about why.
- `Repositories.razor` already subscribes to `IRunEventBus` (`OnRunEvent`) for list-refresh purposes; the same subscription mechanism is the natural way for `CloneDialog` to learn when its own started clone reaches a terminal state.
- `GitRepositoryStatsProvider`'s existing background sampling pass already runs `git remote -v` for every repository on every pass (to build the detail page's remote list) - purely local, no network round trip. It does *not* otherwise touch the network (branch/status/ahead-behind are all derived from local refs), so there is no existing periodic signal this design could reuse to proactively probe whether a host's credential still works - only the actual outcome of a real network-touching operation (pull/push/force-push/fetch/clone) can answer that.

## Goals / Non-Goals

**Goals:**
- Let an MCP caller authorize `git_run`/`clone_repository` to authenticate against a PAT-based remote (GitHub, Azure DevOps, or any other host using the same Basic-Auth-with-PAT-as-password convention) without operator involvement, and without either tool's own contract changing.
- Never let the token touch a process command line, a log line, this service's own database, or any MCP tool result - the token is write-once, into git's own credential helper, and this service never reads it back.
- Every failure (no credential helper configured, git.exe unreachable, the post-write verification failing) reports specifically what went wrong.
- Let an operator authorize/replace a host's credential interactively from the dashboard - at the point a clone actually needs one (in-dialog, with automatic retry), and at any other time via a dedicated action - using the exact same storage path an MCP caller's `authorize_git_host` call uses, so the two surfaces can never end up with divergent credentials for the same host.
- Give an MCP caller a specific, actionable signal when a `git_run`/`clone_repository` failure looks like an authentication problem, distinguishing "never authorized" from "was authorized, now failing" (the latter being a strong expiry/revocation signal) - not just relaying raw git stderr.
- Mark a repository, both in the dashboard (next to its name) and via `list_repositories`, when its remote host currently appears to need a working credential - derived from an actually-observed failure, not merely the absence of a stored credential, so a fully public/anonymous-read repository is never wrongly flagged.

**Non-Goals:**
- Not proactively probing every repository's remote to keep the needs-credential indicator current - it only updates as a side effect of a real pull/push/force-push/fetch/clone happening to run (dashboard-triggered or via `clone_repository`), the same reactive-only nature `repository-management`'s existing "remote gone" detection already has (also only updates when something real touches the remote). A repository nobody has touched since a credential expired shows stale (still "fine") state until the next real attempt - accepted, not solved, by this change.
- Not updating the needs-credential signal from arbitrary `git_run` calls - reliably attributing an arbitrary command's success/failure to "the one host it targeted" isn't well-defined for `git_run` (unlike `clone_repository`, whose target host is always the supplied source URL, or the dashboard's own pull/push/force-push/fetch, whose target is always the resolved `origin` remote). `git_run`'s own auth-failure message enrichment still *reads* the tracked state (resolving a host via the repository's `origin` remote, the same approximation the "change credential" action uses) - it just never *writes* to it, so a `git_run` call that happens to succeed at something unrelated to auth (e.g. `git log`) can never incorrectly clear a real needs-credential flag.
- Not implementing SSH key-based auth, OAuth device-code flow, or GitHub App installation tokens - PAT-over-HTTPS is the one credential model this change covers; see the rejected alternatives below for why each of those was considered and set aside for now, not ruled out permanently.
- Not tracking PAT expiry or rotating a token proactively - git's credential protocol has no expiry field to inspect; an expired PAT just surfaces as a normal git auth failure on the next `git_run`/`clone_repository` call, diagnosable the same way any other git error already is (now with the enrichment described above).
- Not scoping a credential to a specific repository or path - git's own default credential matching is protocol+host only (`credential.useHttpPath` is off by default and this change doesn't turn it on), and one PAT per host covers the actual use case (every repo on that host shares one credential).
- `revoke_git_host_authorization` stops this service from *using* a credential locally - it does not, and cannot, invalidate the PAT itself on GitHub/Azure DevOps. That's outside this service's control entirely.
- Not adding an auto-popup for pull/push/force-push/fetch/clean on an auth failure - per direct instruction, these stay a passive flash-plus-tooltip; the operator decides when to act via the new "change credential" action, rather than the flow being interrupted mid-action.
- Not solving multi-host repositories (a repository with remotes on two different hosts) specially - the new "change credential" action targets the `origin` remote's host; a repository with no `origin` or an unparseable remote URL simply has no host to infer, and the action reports that rather than guessing.

## Decisions

### Storage: git's own `credential approve`/`fill`/`reject` protocol, not direct Windows Credential Manager P/Invoke
Considered writing directly to Windows Credential Manager via P/Invoke (`CredWrite`/`CredRead`/`CredDelete`), the same low-level-Windows-API style this codebase already uses elsewhere (`PerformanceCounter`, WMI, the installer's own `CertificateGenerator`). Rejected: git itself already defines a portable, documented protocol for exactly this (`git credential approve`/`fill`/`reject`, line-oriented key=value pairs over stdin/stdout) that delegates to whatever `credential.helper` is actually configured - Windows Credential Manager via Git Credential Manager by default, but also correct if an operator ever reconfigures it. Shelling out through the same `IProcessRunner` abstraction every other git interaction in this codebase already uses means zero new P/Invoke surface, and the exact storage backend becomes git's problem, not this service's.

### `IProcessRunner`/`ProcessRunRequest` gain an optional stdin parameter
`git credential approve`/`reject` read their input (`protocol=...`, `host=...`, `username=...`, `password=...`, blank line) from stdin, not arguments - the token specifically **must never** appear as a command-line argument, since this service's own `get_run_resources`/WMI process-inspection tooling (and any local admin's Task Manager) can already enumerate a running process's full command line. `ProcessRunRequest` gains a `string? StandardInput` (default `null`), and `CliProcessRunner` writes it to the child process's `StandardInput` stream (then closes it) when supplied, before awaiting output/exit the same way it already does. Purely additive - every existing caller (`dotnet_run`, `git_run`, `clone_repository`, `GitCaptureRunner`) passes `null` implicitly and is unaffected.

### PAT-only: no username parameter anywhere in this capability's surface
Considered exposing an optional username on `authorize_git_host`/the dashboard's PAT prompt (GitHub/Azure DevOps both technically accept an operator-chosen username alongside a PAT). Rejected by direct decision: GitHub and Azure DevOps PAT authentication are both understood to work with any non-empty username paired with a valid PAT as the password - GitHub's own `actions/checkout` convention (`x-access-token` as a fixed placeholder) and Azure DevOps' documented "the PAT is the password, the username can be anything" both point the same way - so a caller-supplied username adds a real correctness risk (git's credential store matches by protocol+host+**username** - re-authorizing a host with a *different* username than before could leave two separate credentials on file rather than cleanly replacing one, undermining the "re-authorizing replaces the credential" requirement) for no actual benefit. `GitCredentialStore` instead always stores under one fixed, internal, non-exposed placeholder username (a constant, not configurable) - HTTP Basic Auth still needs *some* non-empty username field to construct a valid `Authorization` header, but its literal value is asserted, not yet confirmed against a real request, to be irrelevant to either host as long as it's non-empty and never varies between calls (folded into the Section 7.0 live-verification task alongside the other two unverified assumptions below, rather than assumed permanently true on reasoning alone). This means the (protocol, host) pair alone is always the effective match key, so "replace" semantics hold with no separate reject-before-approve step needed.

### `authorize_git_host` verifies the write via `git credential fill` before reporting success
Git's credential protocol has no built-in "did this actually persist" confirmation for `approve` - a silent storage-backend failure (e.g. a misconfigured helper) would otherwise only surface confusingly, later, as an unrelated auth failure on the next real git operation. `authorize_git_host` therefore immediately follows its `approve` call with a `fill` for the same host and confirms a `password=` line comes back, discarding the value without persisting or logging it - giving a specific "credential write did not verify" diagnostic at authorization time instead of a mysterious clone failure minutes or days later.

### Known-hosts tracking lives in a new small EF Core table, not derived by enumerating the credential store
Git's credential protocol has no "list every host with a stored credential" operation (`fill` only answers for one specific host given up front) - so `list_authorized_git_hosts` needs its own record of which hosts were ever authorized through this tool. A new `GitHostAuthorization(string Host, DateTimeOffset AuthorizedAtUtc)` Domain record, mapped via `OutOfTheBoxDbContext` the same way `Run`/`RunResourceSample` already are, follows this project's one-database-not-two precedent rather than inventing a second store. This table is deliberately host/timestamp only - the token itself is never written to it, matching the "this service never reads the token back" goal above. `revoke_git_host_authorization` removes both the git-side credential (`reject`) and this table's row for that host.

### `list_authorized_git_hosts` reports health (last failure/success) alongside configuration, not just "what's configured"
Once `GitHostCredentialHealth` exists (below, driven by real pull/push/force-push/fetch/clone outcomes) for the needs-credential dashboard marker, `list_authorized_git_hosts` joining against it too is a small, natural addition - an MCP caller managing credentials wants to know both "what did I configure" and "is it actually working" from the one tool that already enumerates hosts, rather than only being able to infer health indirectly by cross-referencing `list_repositories`' per-repository field.

### Needs-credential tracking is a separate `GitHostCredentialHealth` type, not folded into `GitHostAuthorization`
`GitHostAuthorization` answers "what's configured" and only ever gets a row when `authorize_git_host`/the dashboard's PAT save actually succeeds. Needs-credential tracking answers a different question - "does this host currently look broken" - and must cover hosts that were *never* explicitly authorized at all (e.g. a clone attempted cold against a private repo with no prior setup) as well as ones that were. Overloading `GitHostAuthorization` with nullable "observed" fields would conflate two independent lifecycles into one row shape. Instead, `GitHostCredentialHealth(string Host, DateTimeOffset? LastAuthFailureAtUtc, DateTimeOffset? LastAuthSuccessAtUtc)` is a second small table, upserted by exactly the operations that have an unambiguous "this touches network host X" meaning: `RepositoryManager.PullAsync`/`PushAsync`/`ForcePushAsync`/`FetchAsync` (host resolved from the repository's `origin` remote) and `CloneAsync` (host resolved from the supplied source URL) - each classifying its own result via `GitAuthFailureClassifier` and recording success or failure against that host's row. `CleanAsync` never touches the network and is excluded. A host "needs a credential" exactly when `LastAuthFailureAtUtc` is set and is more recent than `LastAuthSuccessAtUtc` (or there is no recorded success at all) - a later success always clears the flag, so a fixed credential stops showing as broken the moment it's actually used successfully, not only when an operator manually acknowledges it. **This table now feeds `list_authorized_git_hosts`'s health field only - see the next section for why the dashboard/`list_repositories` marker moved off it.**

### The dashboard/`list_repositories` needs-credential marker is scoped per repository (`RepositoryCredentialHealth`), not per host
The original design computed a repository's `NeedsCredential` by resolving its `origin` host and looking up `GitHostCredentialHealth` - i.e. one shared health row per host, read by every repository cloned from it. Confirmed live as a real, reported bug: a host with more than one repository (the common real case - several repositories cloned from the same GitHub org, for instance) let one repository's credential failure mark *every* repository on that host as needing a credential, including ones the operator never touched; the same problem ran in reverse on recovery, where fixing the credential and retrying against one repository cleared the marker for every repository on the host, not just the one actually verified. Host-scoped health conflates "is the credential I have configured for this host currently working" (a real, useful, genuinely host-scoped question, and the one `list_authorized_git_hosts` still answers via `GitHostCredentialHealth`, unchanged) with "does *this* repository need attention right now" (which depends on what was actually just run against *that* repository, not its neighbors).

Fixed by adding a second, parallel table: `RepositoryCredentialHealth(string RepositoryPath, DateTimeOffset? LastAuthFailureAtUtc, DateTimeOffset? LastAuthSuccessAtUtc)`, keyed on the repository's resolved absolute path (the same key `Run.RepositoryPath` already uses) rather than its host. `RepositoryManager`'s existing credential-outcome recording (the same call sites listed above) now records into *both* tables on every qualifying pull/push/force-push/fetch/clone: the host-scoped one for `list_authorized_git_hosts`, and the new repository-scoped one for the dashboard marker - two independent, single-purpose signals from the same event, not one repurposed for two questions. `RepositoryManager.RenameAsync` repoints a renamed repository's row the same way it already repoints run history (`IRunRepository.UpdateRepositoryPathAsync`), so a rename doesn't silently drop an in-flight needs-credential mark.

### Needs-credential is computed into the existing repository-stats pass, not queried separately per request
`RepositorySummary`/`GitStatusSnapshot` (the shape both `Repositories.razor` and `list_repositories` already render from) gains a `NeedsCredential: bool` field, computed during `GitRepositoryStatsProvider`'s existing sampling pass: `RepositoryCredentialHealth` is looked up directly by the repository's own path, which this pass already has - no host resolution needed for this lookup at all (only whether an `origin` remote exists, to short-circuit a repository that could never have had an outcome recorded against it). This reuses the exact same "computed on the existing cadence, refreshed event-driven right after a run against that repository finishes" mechanism `IsDirty`/`IsRemoteGone`/ahead-behind already use, rather than adding a second, separately-timed lookup path.

### The needs-credential marker lives next to the repository's name, not in the existing git-status icon column
Per direct instruction. `GitStatusIndicator` already owns the compact git-status column (branch/dirty/ahead-behind/remote-gone) - needs-credential is deliberately kept out of it and placed on the name cell/heading instead, in both `Repositories.razor`'s list and `RepositoryDetail.razor`, reusing the same vendored icon the new "change credential" action uses (visually pairing the problem indicator with its fix).

### `list_repositories`' MCP result gains the field directly - no new tool
Once `RepositorySummary` carries `NeedsCredential`, `list_repositories` (which already serializes that exact shape today) exposes it automatically - the same "the MCP surface and the dashboard read from one shared shape" precedent `mcp-repository-access`'s existing fields (size, git status, active/idle) already follow. No separate "get repository credential status" tool is needed or added.

### No `Run`/history record for any of the three new tools
Unlike `delete_path`/`delete_repository` (per `expose-file-management-mcp`), these tools don't fit the `Run` model at all - no repository, no process tree, no stdout/stderr in the usual sense, nothing to poll. `GitHostAuthorization.AuthorizedAtUtc` already answers "when was this host authorized" for audit purposes without forcing a mismatched shape into `RunKind`. If dashboard visibility for configured hosts is wanted later, it can read this same table directly - out of scope for this change (kept narrow, matching this project's usual first-pass scoping).

### A shared, pure `GitAuthFailureClassifier` in `OutOfTheBox.Domain`, one implementation for both surfaces
Both the MCP result-enrichment and the dashboard's clone-retry/tooltip logic need to answer the same question - "does this stderr text look like a git authentication failure?" - from the same input (a completed git invocation's captured stderr). A single Domain-level pure function (`bool IsLikelyAuthFailure(string? stderr)`, pattern-matching git's own well-known message shapes: `fatal: Authentication failed for`, `remote: Invalid username or password`, `fatal: could not read Username for ... terminal prompts disabled`, HTTP 401/403 wording, and similar) is the only way to guarantee the MCP-facing message and the dashboard's decision to prompt agree on what counts as "auth-related" - two independent regex sets would drift the moment either one is tuned. This is inherently a heuristic (git doesn't expose a structured "this was an auth error" flag), so it errs toward specific known phrasings rather than a broad catch-all, to avoid mis-classifying an unrelated failure (bad URL, network down, disk full) as an auth problem and prompting for a PAT that was never the issue.

### Clone-with-retry lives entirely inside `CloneDialog`, not spread across `Repositories.razor`
`CloneDialog` already holds the submitted url/name/branch in scope, which the retry needs unchanged on every attempt. Rather than closing on `Accepted` and handing off to the parent page to somehow notice and react to a later failure, the dialog instead switches to a "Cloning…" sub-state and subscribes to `IRunEventBus` filtered to the returned run id (mirroring `Repositories.razor`'s own existing subscription, not a new event mechanism) until that run reaches a terminal state:
- **Completed** - closes and raises `OnCloned`, exactly like today.
- **Failed, classified as an auth failure** - switches to a "this host needs a PAT" sub-state (host parsed from the submitted URL - see below), delegating to the shared `PatPromptDialog` (below) for the actual prompt/save/verify/retry-message loop; on a working PAT, resubmits the identical clone and returns to "Cloning…".
- **Failed, not an auth failure** - shows the existing generic error text in-dialog (today this case isn't handled at all - the dialog has already closed by the time a genuine mid-clone failure occurs, so this is a real, if secondary, fix alongside the auth-specific flow) and lets the operator edit and resubmit manually, same as an `InvalidName`/`AlreadyExists` rejection already does.
- **Cancelled via the PAT prompt** - closes the dialog entirely. No further retry, and no attempt to clean up whatever the failed clone attempt left behind - a clone that fails before completing typically leaves no target directory at all (git's own default behavior), so there's nothing to remove in the common case; if that assumption turns out wrong for some failure shape, cleanup is a small addition to the cancel path, not a design change.

### `PatPromptDialog`: one reusable component owning "get a working PAT for a host," used by both the clone flow and the standalone action
Extracted as its own dialog (matching this project's existing "one shared dialog instance per concern" pattern - `ConfirmDialog`, `RenameDialog`) rather than duplicated inside `CloneDialog` and the new standalone action. `ShowAsync(host, initialMessage?)` returns once the operator either saves a credential that verifies (`IGitCredentialStore.AuthorizeAsync`, the exact same call `authorize_git_host` makes) or cancels - the loop-on-failure ("that didn't work, try again") lives entirely inside this component, so neither caller needs to reimplement it. A failed verification re-shows the same dialog with an explicit "That token didn't work - it may be invalid, or missing the required scope" message and an empty field, not a silent retry.

### Host is parsed from the clone URL / the repository's `origin` remote, not asked for separately
Asking the operator to type both a URL and a host separately invites them to disagree (a typo'd host wouldn't actually match what the clone/push targets). A small `GitRemoteUrlParser.TryGetHost(string url, out string host)` (Domain-level, pure string parsing - handles both a normal `https://host/...`/`http://host/...` URL via `Uri.TryCreate` and the SCP-like `user@host:path` form `git@github.com:org/repo.git` uses, which isn't a valid absolute URI) derives the host automatically: from the submitted clone URL for the in-dialog flow, and from the target repository's `origin` remote (already available via `IRepositoryManager`'s existing remote-listing) for the standalone "change credential" action. A repository with no `origin` remote, or one whose URL doesn't parse, has no host to infer - the action reports that specifically rather than guessing or silently no-op'ing.

### Quick-action failure detail: a tooltip, not a popup - per direct instruction
`RepositoryQuickActions.RunGitActionAsync` already has `RepositoryGitActionResult.Failed(string? ErrorMessage)` in hand and previously discarded it. It now feeds the flashed icon's `title` attribute, so hovering a red flash shows the real error - classified through the same `GitAuthFailureClassifier`, an auth failure gets a specifically-worded tooltip ("Authentication failed - use the credential action to update it") rather than raw git stderr. This is a passive, hover-only surface precisely because the instruction is explicit: mark the action failed, do not interrupt the operator with a dialog they didn't ask for.

### The new "change credential" action lives inside `RepositoryQuickActions`, not a separate component
It's the same shape of action as the five it already renders - one icon button, no navigation implication, identical behavior whether reached from the Repositories list or the repository detail page - so it belongs in the component whose own doc comment already exists specifically to keep list/detail from drifting on this class of action, rather than a sixth near-duplicate. Unlike pull/push/etc., its click handler doesn't run a git action directly - it resolves the repository's `origin` host (above) and opens the shared `PatPromptDialog` for it, closing with no further action once the dialog reports Saved or Cancelled (there's no "outcome" to flash - success just means the credential is now current, not that anything ran against the repository itself).

### Rejected alternative: OAuth device-code flow
A device-code flow (the tool returns a URL+code, a human completes it in a browser, the service polls and captures the resulting token) avoids the token ever crossing the MCP channel at all - a genuinely stronger security property. Rejected for this change specifically because it needs a human present at authorization time, which defeats the sbx-agent-driven workflow this service exists for, and because GitHub/Azure DevOps device-flow registration (an OAuth app per provider, client id/secret management) is meaningfully more implementation surface than "accept a token, hand it to git." Revisit if a future requirement needs unattended authorization without any secret ever reaching the MCP channel.

### Rejected alternative: SSH key-based auth
Would sidestep PAT lifetime/scope questions entirely, but needs this service to generate/manage a keypair, register the public key with each remote (a manual step on GitHub/Azure DevOps regardless), and configure per-host SSH config (`~/.ssh/config` `Host` blocks, known_hosts trust) - meaningfully more moving parts than PAT-over-HTTPS for a first pass, and both target hosts already support the exact same PAT model this change implements. Worth a future change if SSH-only remotes ever need to be supported.

## Risks / Trade-offs

- **[Risk]** The token crosses the MCP JSON-RPC channel once, at authorization time - the same trust boundary as every other tool argument (bearer-token-authenticated callers only), not a new one, but worth stating explicitly since it's a secret, not routine data. → Mitigated by: never logging it (no Serilog line at any level includes the raw argument), never echoing it in the tool's own result, and piping it to git via stdin specifically so it never appears in a process command line this service's own diagnostics (or any local tool) could otherwise read back.
- **[Trade-off]** No expiry tracking means a caller only discovers a PAT has expired when a real git operation fails - accepted per the Non-Goals above; revisit only if this becomes a recurring real friction point, not preemptively.
- **[Risk]** Depends on Git for Windows' credential helper being present and correctly configured - already true today for any interactive git auth on this host, but `authorize_git_host` checking `git config --get credential.helper` up front (rather than only discovering the gap via a failed `approve`) keeps the failure mode specific and immediate.
- **[Risk]** `GitAuthFailureClassifier` is a heuristic over git's own free-text stderr, not a structured signal - a git version/locale producing different wording than the patterns it knows about would under-classify (falls back to "generic failure," never wrongly triggers a PAT prompt) rather than over-classify. Accepted: a missed auth-failure classification degrades to today's existing behavior (generic failure, no retry loop), not a regression; a false-positive classification would be the worse failure mode (prompting for a PAT that was never the problem), so the pattern set stays intentionally conservative.
- **[Trade-off]** The clone-retry loop is entirely operator-paced (each retry requires typing a new PAT and clicking Save) with no attempt cap, per direct instruction ("until the user gives a valid one or cancels") - accepted as intentional, not a runaway-loop risk, since nothing retries without an explicit operator action in between.
- **[Risk, confirmed and fixed]** Git Credential Manager has provider-specific behavior for `github.com`/`dev.azure.com` specifically - by default it prefers an interactive OAuth browser flow for those two hosts over plain Basic Auth, even when a Basic Auth credential has been separately `approve`d. Confirmed live (not just theorized): without a fix, GCM's account-picker UI kept popping on every subsequent git operation against a host authorized this way. Fixed by `authorize_git_host` setting `git config --global credential.https://<host>.provider generic` (GCM's own documented escape hatch) before approving. That fix in turn caused a second, follow-on regression, also confirmed live and fixed: cloning a repository with no credential configured at all started hanging until timeout instead of failing fast, because GCM's "generic" provider doesn't carry the same non-interactive-session detection its default host-aware provider does. Fixed by unconditionally setting `GIT_TERMINAL_PROMPT=0`/`GCM_INTERACTIVE=never` on every git invocation this service spawns (`CliProcessRunner`), not scoped to credential operations alone - see `CHANGELOG.md` for both fixes.
- **[Risk, unverified]** This service runs as a dedicated least-privilege Windows Service account (per the installer's own existing design), not an interactively-logged-in user - Windows Credential Manager's DPAPI-backed storage is normally scoped to a loaded user profile, which a service account does not automatically get unless the service is configured to load one. Whether `git credential approve`/`fill` behave correctly under that account as-is, or need the service's own account configured with a loaded profile (or GCM's file-based `store` helper used instead of the Windows-Credential-Manager-backed one specifically for this service account), is likewise unconfirmed until tested against the real service process, not just an interactive `dotnet run`.
- **[Trade-off]** The needs-credential indicator can be stale (shows "fine" for a repository nobody has recently pulled/pushed/fetched against even though its credential has since broken) - accepted per the Non-Goals above, matching the existing "remote gone" indicator's own identical staleness characteristic; not a new class of imprecision this change introduces.
- **[Risk, confirmed and fixed]** The dashboard/`list_repositories` needs-credential marker was originally host-scoped (one shared `GitHostCredentialHealth` row per host, read by every repository cloned from it). Confirmed live: removing a host's credential and retrying a pull against one repository marked *every* repository on that host as needing a credential, including untouched ones; re-authorizing and retrying then cleared the marker for all of them, not just the one actually verified. Fixed by scoping the marker to the repository itself (`RepositoryCredentialHealth`, keyed on repository path) - see "The dashboard/`list_repositories` needs-credential marker is scoped per repository" above.

## Migration Plan

Purely additive. New EF Core migration for `GitHostAuthorizations`, `GitHostCredentialHealth`, and (added after the host-scoping fix above) `RepositoryCredentialHealth` (schema-additive, no existing table touched). No feature flag - reachability is gated by the same bearer token every other MCP tool requires, same as `expose-file-management-mcp`'s delete tools; the dashboard-side prompts are reachable by any operator who can already reach the dashboard at all (same auth boundary as every other dashboard action). Ship in the next installer build; the About page's MCP tool list gets updated in the same change, along with a new vendored icon (Lucide, matching the rest of this project's icon set) shared by the "change credential" action and the needs-credential name marker.
