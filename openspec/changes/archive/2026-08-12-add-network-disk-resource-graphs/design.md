## Context

See `proposal.md` for motivation. Relevant existing state this design builds on:

- `HostResourceSampler` (Infrastructure, `[SupportedOSPlatform("windows")]`) already samples host CPU (`Processor`/`% Processor Time`, `_Total` and per-core instances) and host network (`Network Interface` category, summed across every instance - that category has **no `_Total` instance**, unlike `Processor`) via `PerformanceCounter`. Per-process CPU/RAM (used for a run's own aggregate) comes from `Process.TotalProcessorTime`/`WorkingSet64` directly, not a counter.
- `HostResourceSamplerService` ticks every few seconds, writes the host tick into `ResourceHistoryBuffer` (an in-memory rolling window backing the Status page's live graphs) and, per tracked run, both a buffer entry and a persisted `RunResourceSample` row (`run-history`).
- A file transfer already gets a `RunResourceSample` row tagged with that tick's **host-level** CPU/RAM, not a per-process figure, since a transfer spawns no process tree of its own - the established precedent this change's network/disk tagging directly extends to every run kind, not just transfers.
- `RunHistoryGraph.razor` (a run's detail page) reads the full persisted series via `IRunResourceSampleRepository.GetSeriesAsync` and feeds two charts (CPU, RAM) via `IChartInterop.SetSeriesAsync`, once. `LiveResourceGraph.razor` (Status page, and each expandable run card) reads `ResourceHistoryBuffer` instead, seeds via `SetSeriesAsync`, then extends incrementally via `PushPointAsync` on each `IResourceEventBus` tick.
- `IChartInterop.CreateLineChartAsync`'s `showLegend` parameter already exists and is already wired through to Chart.js's `plugins.legend.display` in `chart-interop.js` - turning a chart's legend off/on was already a one-line call-site change before this proposal, not new plumbing.

## Goals / Non-Goals

**Goals:**
- Give an operator visibility into network and disk I/O, host-wide and per-run, wherever CPU/RAM are already shown.
- Reuse every existing pattern (host-tagging for figures no process tree can isolate, the buffer/persistence split, the interop abstraction) rather than inventing a parallel mechanism for the two new figures.

**Non-Goals:**
- Not exposing network/disk via `get_run_resources` (MCP) - out of scope, dashboard-only per direct instruction. `McpRunResourcePoint`/`McpGetRunResourcesResult` are untouched.
- Not attempting genuine per-process network or disk isolation - see Decisions below for why that's not meaningfully possible on Windows at all, not merely deferred.
- Not adding a Network/Disk I/O row to a run's *live* (Status page, expanded card) graph - only the host section of Status, and a run's full-duration history page, per the exact layout requested. `LiveResourceGraph`'s non-host branch still only ever shows CPU/RAM.

## Decisions

### Network and disk are tagged onto every run from the host reading, not derived per-process - a hard platform constraint, not a simplification
Windows has no per-process, network-only performance counter at all - the closest thing, `Process`/`IO Read Bytes/sec`+`IO Write Bytes/sec`, is combined disk+network+every-other-I/O, not network-specific, and isn't sampled by this change either (using it and labeling it "Network" would be dishonest). Disk I/O sampled via `PhysicalDisk` is inherently a whole-machine category with no per-process breakdown at all. Given that, the only honest option for a *per-run* network/disk figure is exactly the one this codebase already established for a transfer's CPU/RAM: use the host-wide reading, tagged onto the run's own point/row, clearly understood as "what the whole machine was doing at this tick," not an isolated per-run measurement. This was a direct, explicit choice (confirmed against the alternative - genuinely-isolated but mislabeled disk+network I/O - and rejected in favor of staying honest about what's actually measurable).

### `PhysicalDisk`/`_Total`, not per-drive enumeration and summing
Unlike `Network Interface` (no `_Total` instance - `HostResourceSampler` already has to enumerate every NIC instance name and sum `Bytes Sent/sec`/`Bytes Received/sec` across them), `PhysicalDisk` **does** have a `_Total` instance that Windows itself already sums across every physical drive. Reading `Disk Read Bytes/sec`/`Disk Write Bytes/sec` against instance `"_Total"` directly gives the "crunch all drives together" figure with no enumeration or summing logic needed - simpler than the network counters it sits alongside, not parallel complexity.

### New fields default/nullable rather than required, to avoid touching every existing call site
`HostResourceSample`'s two new disk fields are positional-record parameters with `= 0` defaults appended at the end - every pre-existing positional-argument construction (mostly tests) keeps compiling unchanged. `RunResourceSample`'s four new network/disk properties are plain nullable (`double?`), not `required` - existing object-initializer call sites are unaffected, and nullability is also the honest representation for a row persisted before this change (genuinely no recorded value, not a real zero). `ResourceHistoryPoint`/`ResourceHistoryBuffer.Add` follow the same optional-parameter pattern already established for the existing per-core/network fields.

### The live buffer's retention goes from 10 to 20 minutes; a new `Get(seriesKey, window)` overload keeps every other graph at 10
Per direct instruction, only the Status page's host CPU graph should show 20 minutes; every other live graph (RAM, per-core, network, disk, and any per-run live graph) stays at 10. Rather than maintaining two differently-windowed buffers, `ResourceHistoryBuffer.WindowDuration` (its actual retention) becomes 20 minutes, and `Get` gains an optional `window` parameter that further restricts the returned points to "no older than `window` before now," without evicting anything from the buffer itself. The host CPU graph calls `Get(SeriesKey)` (the full 20-minute retention); every other graph explicitly passes `Get(SeriesKey, TimeSpan.FromMinutes(10))`. `IChartInterop.CreateLineChartAsync` gained a matching `liveWindow` parameter (defaulting to 10 minutes) so `chart-interop.js`'s client-side trim (previously a single hardcoded `WINDOW_MS` constant applied to every chart) can differ per canvas too - otherwise the host CPU chart's server-seeded 20 minutes of data would immediately get trimmed back down to 10 by the very first live push.

### Legend visibility follows the existing "single line vs. two lines" rule, extended to the two new charts
Already established for CPU/RAM/per-core (off) vs. Network (on, two lines) before this change - Disk I/O (also two lines, Read/Write) follows the identical reasoning, no new rule needed.

### Layout: explicit rows, not left to flex-wrap
Both `LiveResourceGraph`'s host section and `RunHistoryGraph` already used (or, for `RunHistoryGraph`, now use) multiple explicit `.resource-graphs` flex-row containers rather than one container and letting `flex-wrap` reflow naturally - the established reason (documented inline at each call site already) is that natural reflow doesn't guarantee a *specific* pairing/row assignment across viewport widths, which the requested layout (CPU alone in its own full-width row; a specific pairing in each subsequent row) genuinely requires. A lone flex item with `flex: 1 1 320px` (already the shared `.resource-graph` rule) naturally stretches to fill its row when it has no sibling, which is what makes "CPU scaled to full width" free - no new CSS class was needed for that specifically.

### A run's history graph now also subscribes live, reusing `LiveResourceGraph`'s own mechanism rather than a parallel one - added per direct follow-up instruction
`RunHistoryGraph` originally seeded once via `SetSeriesAsync` from the persisted series and never updated again - correct for a completed run, but meant an operator watching a still-in-flight run's own detail page saw a permanently frozen snapshot from whichever moment they'd loaded the page, the same class of staleness already fixed once for the page's own header fields (outcome/exit code/output) via an `IRunEventBus` subscription. The fix reuses `LiveResourceGraph`'s exact pattern: inject `ResourceHistoryBuffer`/`IResourceEventBus`, subscribe once, and on each tick read `HistoryBuffer.Get(RunId.ToString())`'s latest point and `PushPointAsync` it if newer than the last one pushed. Crucially, `CreateLineChartAsync`'s `liveWindow` is left `null` (unbounded) on all four of this component's charts - unlike every Status-page graph, which always passes an explicit rolling window, a run's own graph is meant to show its *entire* duration, growing for as long as the run stays in flight, per direct instruction ("growing the dataset is okay, no fixed time slot desired"). This is what motivated `chart-interop.js`'s own default flip (see above) from "10 minutes unless told otherwise" to "never trim unless told to."

The subscription is unconditional (set up in `OnAfterRenderAsync`'s `firstRender` branch regardless of whether any data exists yet), for two reasons: (1) it needs no explicit teardown condition - once a run reaches a terminal state, `HostResourceSamplerService.OnRunEvent` already removes its `ResourceHistoryBuffer` entry, so the subscription's own `Get` calls simply stop returning anything new and it becomes a permanent no-op for the rest of the page's lifetime, without needing to know the run's own outcome at all; (2) a run viewed within its very first tick or two - before `HostResourceSamplerService` has recorded anything for it - would otherwise be stuck showing the empty-state message forever once samples did start arriving, since nothing would ever re-check. `OnTick` handles that case by re-querying the persisted series (not the live buffer) the first time it observes `_hasData` is still false, reusing the exact same seeding code path `OnAfterRenderAsync` already uses rather than a second, buffer-fed one - the DB write and the buffer write both already complete, in `HostResourceSamplerService.TickCoreAsync`, before the event this subscription reacts to is ever published, so both are guaranteed to already reflect the new sample by the time this code runs.

### Chart width bug found and fixed: `maintainAspectRatio` needs to be `false`, and its parent needs a defined height
Confirmed live (not theorized): every graph rendered at roughly a third of its actual container width, most visibly the Status page's now-full-width host CPU row, which still only filled a narrow strip on the left. Root cause was Chart.js's own default `maintainAspectRatio: true` (aspect ratio 2:1) combined with the existing `.resource-graph canvas { max-height: 160px; }` rule: Chart.js computed the canvas's *width* from that constrained height times the aspect ratio (≈320px) rather than filling the actual, often far wider, flex-laid-out container. Fixed with `maintainAspectRatio: false` in `chart-interop.js`'s chart options - but that alone isn't sufficient, since Chart.js's own documented responsive-sizing contract requires the canvas's *parent* (not the canvas itself) to have a defined height for it to fill in both dimensions independently. `max-height` on the canvas element gave Chart.js nothing on the parent to measure. Fixed properly by introducing a dedicated `.resource-graph-canvas-wrap` wrapper (`position: relative; height: 160px;`) around every `<canvas>` in both `RunHistoryGraph.razor` and `LiveResourceGraph.razor`, replacing the old canvas-level `max-height` rule - this is the standard, documented Chart.js pattern for "fill width responsively, fixed height," not a one-off workaround.

## Risks / Trade-offs

- **[Trade-off]** Network/disk figures on a run's graph reflect the *whole machine's* activity at each tick, not that run's own isolated usage - inherent to the platform constraint above, not a bug. Mitigated the same way the existing transfer-CPU/RAM precedent already is: consistently documented (in code comments, and this proposal) as host-level, not per-run-isolated.
- **[Trade-off]** The buffer's memory footprint roughly doubles (20 vs. 10 minutes of retention per series) - accepted as negligible; each point is a handful of primitive fields, and the number of concurrently-tracked series (host plus in-flight runs/transfers) is small for this project's single/few-operator scale.
- **[Trade-off]** A run's own history graph has no cap on how large its client-side dataset can grow while the run stays open - an exceptionally long-running run (hours) left open on this page would accumulate a correspondingly large in-browser point count. Accepted per direct instruction ("growing the dataset is okay, no fixed time slot desired") - this page is opened deliberately to watch one specific run, unlike the Status page's always-mounted host graphs, so the operator controls how long that tab stays open, and Chart.js's own rendering cost for a session-scale point count (thousands, not millions, even for a multi-hour run at a several-second sampling cadence) is not a practical concern at this project's scale.

## Migration Plan

Additive - one new EF Core migration (`AddColumn`, nullable, on `RunResourceSamples`), no existing table/column touched or renamed. No feature flag - graphs simply gain two more, no separate reachability surface to gate. Ship in the next installer build.
