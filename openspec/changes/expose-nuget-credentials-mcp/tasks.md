NuGet has no documented environment variable that relocates its default user/machine settings resolution the way git's does; `Settings.LoadDefaultSettings(root: null)` (what `NuGetFeedCredentialStore`'s generic-feed mechanism calls) always resolves against the real `%AppData%\NuGet\NuGet.Config` on this machine. A `McpNuGetCredentials.feature` BehaviorTests scenario for the generic-feed mechanism would therefore either (a) genuinely write into the real developer/CI machine's own NuGet configuration as a side effect of running `dotnet test`, or (b) require adding a testability seam to production code (e.g. an injectable settings-loading strategy) that the design doesn't otherwise need. Per this task's own instruction ("if it doesn't, this needs its own design note before proceeding, not a silent workaround"), flagging this back rather than picking either silently - see the applied-change writeup for the options. The Azure DevOps Artifacts mechanism's own credential-provider-not-installed path is covered instead in UnitTests (9.2), since it doesn't touch real IO at all.
