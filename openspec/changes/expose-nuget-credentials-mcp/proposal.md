## Why

`dotnet_run` can already run `restore`/`build`/`test`/`pack`/`push` against a repository, but any of those fail today against a private NuGet feed (a GitHub Packages feed, an Azure Artifacts feed, or any other PAT-authenticated `nuget.org`-protocol feed) unless a credential for that feed already happens to exist in this machine's NuGet configuration - there is no MCP-reachable way for the sbx caller to authorize NuGet against a feed at all, mirroring the gap `expose-git-credentials-mcp` closed for git remotes. Azure DevOps Artifacts feeds specifically are best authorized via Microsoft's own Azure Artifacts Credential Provider (the "VSS credential provider") rather than a plain stored password, per explicit direction - it is Microsoft's documented, supported mechanism for exactly this non-interactive scenario, and some Azure DevOps org policies expect it. GitHub Packages and any other generic PAT-authenticated feed keep using NuGet's plain stored-password convention, which NuGet's own credential resolution already understands natively.

## What Changes

- Add an `authorize_nuget_feed` MCP tool: accepts a feed URL and a PAT, and stores it so that subsequent `dotnet_run` calls (`restore`, `build`, `test`, `pack`, `push`, or any other subcommand that triggers a restore) authenticate against that feed transparently - no change to `dotnet_run`'s own parameters. The caller does not choose a mechanism; the tool classifies the feed URL and routes it internally:
  - **Azure DevOps Artifacts feeds** (`pkgs.dev.azure.com`, `*.pkgs.visualstudio.com`) go through the **Azure Artifacts Credential Provider**, using its documented non-interactive `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS` environment-variable mechanism - since that variable is only ever process-scoped, this service durably stores the PAT itself, DPAPI-encrypted, and re-injects it as an environment variable into every `dotnet_run`-spawned process alongside a `NUGET_CREDENTIALPROVIDERS_PATH` pointing at this service's own bundled copy of the credential provider.
  - **Every other feed URL** (GitHub Packages, any generic NuGet v3 feed) is written as a credentialed package source into this machine's NuGet configuration, using NuGet's own client library so the password is encrypted at rest by NuGet's own mechanism, in-process - never a command-line argument, never logged, never written to this service's own database.
  - Either way, the write is verified (read back and confirmed to match what was just written) before reporting success, rather than trusting the write.
- Add a `list_authorized_nuget_feeds` MCP tool: lists which feed URLs have a credential configured and when each was authorized, regardless of which mechanism backs it - never the token itself, which this service never returns from any tool result.
- Add a `revoke_nuget_feed_authorization` MCP tool: removes a feed's stored credential (from whichever mechanism backs it) and this service's own record of it.
- All three are synchronous (in-process, no process tree to poll), confined to no specific repository (a feed's credential is machine-wide), and every failure reports a specific, actionable reason - an invalid feed URL, the NuGet configuration being unwritable, the Azure Artifacts Credential Provider not being installed, or the post-write verification failing - not a generic "failed."
- A public/unauthenticated feed (`nuget.org`, etc.) is completely unaffected - `dotnet_run` already restores against it today with no credential, and this change doesn't touch that path.

## Capabilities

### New Capabilities
- `mcp-nuget-credentials`: lets an MCP caller store, list, and revoke PAT-based credentials for a private NuGet feed, so `dotnet_run`'s `restore`/`build`/`test`/`pack`/`push` calls can authenticate against it without operator involvement.

### Modified Capabilities
- `mcp-server`: "Tool discovery lists exactly the tools this service defines" grows to include `authorize_nuget_feed`, `list_authorized_nuget_feeds`, and `revoke_nuget_feed_authorization`.

## Impact

- **Affected code**: new `INuGetFeedCredentialStore` port (`OutOfTheBox.Application`) and `NuGetFeedCredentialStore` implementation (`OutOfTheBox.Infrastructure.Repositories`); a new `NuGetFeedAuthorization` Domain record (feed URL/timestamp, plus an encrypted-password column populated only for Azure DevOps Artifacts entries - never the plaintext token); a new pure `AzureArtifactsFeedClassifier` (`OutOfTheBox.Domain`); a new `NuGetFeedCredentialsMcpTools.cs` (`OutOfTheBox.Presentation.Mcp`). `ProcessRunRequest`/`IProcessRunner`/`CliProcessRunner` gain an optional environment-variables injection point (mirroring the git-credential change's own stdin addition), and `CommandExecutionMcpTools.DotnetRunAsync`'s spawn path uses it to inject `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS`/`NUGET_CREDENTIALPROVIDERS_PATH` when at least one Azure DevOps Artifacts feed is authorized - a no-op otherwise.
- **New package dependency**: `NuGet.Configuration` (the official NuGet client library), added to `Directory.Packages.props` and referenced from `OutOfTheBox.Infrastructure`, for the non-Azure-DevOps mechanism only. The Azure DevOps Artifacts mechanism needs no new package - it uses `System.Security.Cryptography.ProtectedData` (BCL) directly for its own DPAPI encryption.
- **New persistence**: one small table - `NuGetFeedAuthorizations` (feed URL, authorized-at, and a nullable encrypted-password column used only by the Azure DevOps Artifacts mechanism) - via the existing `OutOfTheBoxDbContext`/EF Core Migrations pattern. The non-Azure-DevOps mechanism still never writes the secret here; the Azure DevOps mechanism is a deliberate, narrow exception - see design.md's Decisions for why it's unavoidable.
- **New installer impact**: the Azure Artifacts Credential Provider binary needs to be bundled by this project's own installer (mirroring how Git for Windows + Git Credential Manager is already a chained Burn bootstrapper prerequisite for the git-credential change) so `NUGET_CREDENTIALPROVIDERS_PATH` has something real to point at.
- **No dashboard/UI changes** - MCP tools only, per explicit scope for this change. No needs-credential marker, no PAT-prompt dialog, no auth-failure-message enrichment on `dotnet_run` - see design.md's Non-Goals. (`dotnet_run` does gain credential-*injection* wiring, described above - a different, necessary kind of change from the failure-message enrichment that stays out of scope.)
- Docs updated: the About page's MCP tool list/count.
