## Context

See `proposal.md` for motivation. Relevant existing state this design builds on, and diverges from where noted:

- `expose-git-credentials-mcp` (still active, not yet archived) established the shape this change follows for its MCP surface (Domain record → Application port → Infrastructure implementation → EF Core metadata-only persistence → Presentation MCP tools, attribute-discovered) and its non-negotiables (never let the token appear as a process command-line argument or in a log). Its `IGitCredentialStore`/`GitCredentialStore` is git-specific top to bottom - there is no generic `ICredentialStore` abstraction in this codebase to extend, so this change builds a parallel structure, not an extension.
- Unlike git, NuGet has no single external CLI-driven credential-helper protocol equivalent to `git credential approve`/`fill`/`reject`. Two separate, real mechanisms are relevant here, per explicit direction to use the Azure Artifacts Credential Provider ("VSS credential provider") for Azure DevOps Artifacts feeds specifically, while still covering GitHub Packages and other generic PAT-based feeds:
  - **Azure Artifacts Credential Provider** (`CredentialProvider.Microsoft`, https://github.com/microsoft/artifacts-credprovider) is a NuGet credential-provider plugin Microsoft publishes specifically for Azure DevOps Artifacts feeds. NuGet's restore pipeline auto-discovers and invokes credential-provider plugins found under a known plugin path (or `NUGET_CREDENTIALPROVIDERS_PATH`) when a source needs auth and no credential is already resolved. The provider supports a documented non-interactive mode for exactly this "no human present" scenario: the `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS` environment variable, a JSON blob (`{"endpointCredentials":[{"endpoint":"<feed url>","username":"<optional>","password":"<PAT>"}, ...]}`) it reads before ever attempting an interactive/browser-based flow. This is Microsoft's own supported mechanism for CI/headless scenarios against Azure DevOps Artifacts, and was explicitly requested over the alternative below - some Azure DevOps org policies also expect it rather than a plain stored password. (A plain NuGet-configuration password, as used for the generic path below, technically also works for many Azure DevOps Artifacts feeds - but isn't the mechanism asked for here, and isn't guaranteed to work under stricter org policies.)
  - For every other feed (GitHub Packages, generic NuGet v3), NuGet's own client library (`NuGet.Configuration`, the same one `dotnet nuget`/`nuget.exe`/MSBuild's restore pipeline are themselves built on) exposes `Settings`/`PackageSourceProvider`/`PackageSourceCredential` types that read and write the exact NuGet configuration file(s) `dotnet restore` already consults, encrypting the password at rest via NuGet's own `EncryptionUtility` (Windows: DPAPI-backed, `ProtectedData`-based) when `storePasswordInClearText` is left `false`. Calling this library in-process avoids spawning a child process for the write entirely.
- `OutOfTheBoxDbContext`/EF Core Migrations (`OutOfTheBox.Infrastructure.Persistence`) is this service's one existing SQLite-backed persistence path - the established place a new small table belongs, per the git-credential change's own precedent.
- `ProcessRunRequest`/`IProcessRunner`/`CliProcessRunner` (`OutOfTheBox.Application.Execution`/`Infrastructure`) already gained an optional `StandardInput` parameter in the git-credential change, for the identical reason a similar addition is needed here: a secret needs to reach a spawned process without ever being a command-line argument. That change is the direct precedent for this one adding an environment-variables injection point instead (stdin doesn't apply here - the Azure Artifacts Credential Provider reads an environment variable, not stdin).
- No existing MCP tool or Domain type in this codebase references NuGet at all today (confirmed by search), and no DPAPI/`ProtectedData` usage exists anywhere in `src/` today either (also confirmed) - this change is the first to use `ProtectedData` directly, for the Azure DevOps Artifacts mechanism's own durable storage need (see Decisions).
- `dotnet_run`'s `arguments` parameter (`CommandExecutionMcpTools.DotnetRunAsync`) is a fully generic `dotnet` argument list - a caller already passes `["restore"]`/`["build"]`/etc. directly. This change adds no new `dotnet_run` parameter and no change to its argument contract - only to what happens inside its existing spawn path (environment variables added to the child process, invisible to the caller's own request/response shape).
- A public/unauthenticated feed (`nuget.org`, etc.) needs no credential at all and `dotnet_run` already restores against one today with zero involvement from this capability - neither mechanism below is consulted unless a feed URL has actually been authorized.

## Goals / Non-Goals

**Goals:**
- Let an MCP caller authorize `dotnet_run`'s `restore`/`build`/`test`/`pack`/`push` calls to authenticate against a PAT-based private NuGet feed - both Azure DevOps Artifacts feeds (via the Azure Artifacts Credential Provider) and any other feed using NuGet's standard username+password-as-PAT convention (GitHub Packages, generic NuGet v3) - without operator involvement, and without `dotnet_run`'s own request/response contract changing.
- Never let the token touch a process command line or a log line. For the generic-feed mechanism, also never let it touch this service's own database (write-once into NuGet's own configuration, encrypted at rest by NuGet's own mechanism). For the Azure DevOps Artifacts mechanism, this service necessarily becomes the durable store (see Decisions) - the token is DPAPI-encrypted before it is persisted, and read back only to verify the write or to build the environment variable a `dotnet_run` spawn needs.
- Every failure (invalid feed URL, the NuGet configuration being unwritable, the Azure Artifacts Credential Provider not being installed, the post-write verification failing) reports specifically what went wrong.
- Continue to require zero configuration for a public/unauthenticated feed - neither mechanism is consulted, and `dotnet_run`'s existing behavior against `nuget.org`-style feeds is completely unaffected.

**Non-Goals:**
- Not adding a dashboard UI surface of any kind - no PAT-prompt dialog, no needs-credential marker, no "change credential" action. Per direct instruction: MCP tools only, for this first cut.
- Not wiring `dotnet_run`'s *failure messages* to detect a NuGet-auth-looking failure and point at `authorize_nuget_feed`, the way `git_run`/`clone_repository` gained auth-failure enrichment in the git-credential change. NuGet restore failures are MSBuild/NuGet diagnostic output (`NU1301`, `NU1101`, 401/403 wording buried in a much larger build log), not a short stderr stream from a single well-understood command - building a reliable classifier for that is materially more work than `GitAuthFailureClassifier`'s git-stderr pattern matching, and isn't needed for the core capability to be useful on its own. Revisit as a separate future change if this turns out to be a recurring friction point. **This is distinct from the credential-*injection* wiring `dotnet_run` does gain** (below) - that wiring is necessary for the Azure DevOps Artifacts mechanism to work at all, not an enrichment of failure text.
- Not tracking per-feed health (a `NeedsCredential`-equivalent signal) the way `GitHostCredentialHealth` does for git hosts. That signal is only meaningful if something reactively writes to it on every real network-touching operation against a feed - `dotnet_run`'s `restore`/`build`/`test`/etc. have no equivalent unambiguous single-feed target (a restore can touch several configured feeds in one call), so this change ships `authorize`/`list`/`revoke` only, with no health tracking. Matches this project's convention against speculative, unused surface.
- Not verifying either mechanism's PAT actually authenticates against the real feed over the network (no service-index request, no `NuGet.Protocol` dependency). Verification is local-only for both mechanisms: reading back what was just written/stored and confirming it matches. This catches "the write silently didn't persist" without a network round trip in either mechanism's synchronous MCP call path.
- Not supporting a feed-scoped, caller-chosen username for either mechanism. A fixed, internal, non-exposed placeholder username is used in both, consistent with GitHub Packages' and Azure Artifacts' own documented "any non-empty (or absent) username works when the password is a valid PAT" convention - flagged as an unverified assumption below.
- Not bundling arbitrary future NuGet credential-provider plugins generically - only the one Azure Artifacts Credential Provider binary this change needs.

## Decisions

### Storage is a dual mechanism, chosen per feed URL pattern - not one design for every feed
`NuGetFeedCredentialStore.AuthorizeAsync` classifies the supplied feed URL via a new pure `AzureArtifactsFeedClassifier.IsAzureDevOpsArtifactsFeed(Uri)` (`OutOfTheBox.Domain`, mirroring `GitRemoteUrlParser`'s existing pure-parsing precedent): host equals `pkgs.dev.azure.com`, or ends with `.pkgs.visualstudio.com`, case-insensitive. A match routes through the Azure Artifacts Credential Provider mechanism; anything else routes through the NuGet-configuration-write mechanism. The MCP surface stays exactly three tools either way - the caller never chooses or sees which mechanism applies.

### Azure DevOps Artifacts feeds: Azure Artifacts Credential Provider via `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS`
Per explicit direction, rather than writing a plain NuGet-configuration password for these feeds too (which - see Context - would often also work, but isn't the supported/requested mechanism and isn't guaranteed under stricter Azure DevOps org auth policies). Considered shelling out to the credential provider's own CLI-style invocation directly instead of relying on NuGet's restore pipeline to auto-invoke it - rejected: the whole point of the provider is that NuGet's own restore machinery discovers and calls it automatically once `NUGET_CREDENTIALPROVIDERS_PATH` and `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS` are set correctly on the child process; this service never has to speak the plugin protocol itself.

### Durable storage for the Azure DevOps Artifacts mechanism: DPAPI (`ProtectedData`) directly, in this service's own EF Core row - a deliberate, narrow exception to "never persist the secret in our DB"
`VSS_NUGET_EXTERNAL_FEED_ENDPOINTS` is read once per child process at spawn time - it has no durability of its own. For `authorize_nuget_feed` to mean anything beyond "works for the next few minutes," this service itself must be the durable store for these specific PATs, re-supplying them as an environment variable on every future `dotnet_run` spawn. This is a genuine, explicit divergence from the git-credential change's (and this change's own generic-feed mechanism's) "never persist the secret in our own database" position - unavoidable given the mechanism explicitly requested, not an oversight. Mitigated the same way NuGet's own `EncryptionUtility` mitigates the generic-feed mechanism's at-rest exposure: `System.Security.Cryptography.ProtectedData.Protect`/`Unprotect` (DPAPI, user or machine scope matching whatever this service's process token provides) encrypts the token before it is ever written to `OutOfTheBoxDbContext`; only ciphertext exists in the database at rest, decrypted in-process only for the two moments that need plaintext (post-write verification, and building the environment variable for a `dotnet_run` spawn) and never logged.

### `dotnet_run` gains environment-variable injection - new, necessary wiring, distinct from failure-message enrichment
`ProcessRunRequest` gains an optional `IReadOnlyDictionary<string, string>? EnvironmentVariables` (default `null`), and `CliProcessRunner` sets each entry on the child `ProcessStartInfo.EnvironmentVariables` before starting - purely additive, mirroring the git-credential change's identical `StandardInput` addition and its "every existing caller passes null implicitly, unaffected" property. `CommandExecutionMcpTools`'s `dotnet` spawn path (only `dotnet`, never `git`) asks `INuGetFeedCredentialStore` for currently-authorized Azure DevOps Artifacts feeds immediately before each spawn; if there are none, no environment variables are added (zero behavior change for a caller with no such feeds authorized). If there are one or more, it decrypts them in-process, builds the `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS` JSON and a `NUGET_CREDENTIALPROVIDERS_PATH` pointing at this service's own bundled credential-provider install path (below), and passes both as `ProcessRunRequest.EnvironmentVariables`. Neither value is ever logged; `get_run_resources`/WMI process inspection does not expose a child process's environment block the way it exposes its command line, so this is a materially smaller exposure surface than a command-line argument would be - see Risks for the honest caveat on that claim.

### Credential-provider discoverability is checked before accepting an Azure DevOps Artifacts authorization
Mirrors `authorize_git_host`'s "checks for a configured credential helper up front" decision. `authorize_nuget_feed` checks the bundled Azure Artifacts Credential Provider binary actually exists at its known install path before accepting an Azure-DevOps-pattern feed authorization, and fails with a specific diagnostic if not - rather than accepting a write that can never actually work and letting the gap surface only as a confusing downstream restore failure.

### Installer bundling of the Azure Artifacts Credential Provider
The provider ships as prebuilt archives from Microsoft (`microsoft/artifacts-credprovider` releases). This change vendors the relevant release archive into this project's own installer payload (mirroring how Git for Windows + Git Credential Manager is already a chained Burn bootstrapper prerequisite for the git-credential change) and extracts it to a fixed, service-controlled install path at install time - not a per-user `~/.nuget/plugins` location, since this service runs under a dedicated least-privilege account whose profile may not be loaded (the same concern already flagged for git's Windows Credential Manager and this change's own generic-feed DPAPI usage). `CommandExecutionMcpTools`'s injected `NUGET_CREDENTIALPROVIDERS_PATH` points directly at that fixed location, so plugin discovery never depends on any profile-scoped default path at all. The exact WiX/Burn mechanics for vendoring and extracting a third-party binary are new to this codebase and unverified until attempted - see Risks.

### Which NuGet configuration gets written, for the generic-feed mechanism: the machine/user default, not a per-repository `nuget.config`
Unchanged from the original design: `Settings.LoadDefaultSettings(root: null)`, the same resolution `dotnet nuget add source` uses with no `--configfile` override - one `authorize_nuget_feed` call covers every repository this service manages.

### Feed URL is the sole match key for both mechanisms - one fixed, internal placeholder username, never caller-supplied
Mirrors the git-credential change's "PAT-only, no username parameter" decision. For the generic-feed mechanism, the package source's `Name` attribute is derived deterministically from the normalized feed URL, so re-authorizing the same URL always updates the same entry. For the Azure DevOps Artifacts mechanism, the feed URL is the JSON `endpoint` key in `VSS_NUGET_EXTERNAL_FEED_ENDPOINTS`, and the EF Core row is keyed by the same normalized URL - re-authorizing replaces the stored ciphertext for that row rather than adding a second one. Both mechanisms' placeholder username value is asserted, not yet confirmed against a real GitHub Packages/Azure Artifacts request - folded into this change's live-verification task.

### Known-feeds tracking lives in one small EF Core table, covering both mechanisms
A single `NuGetFeedAuthorization(string FeedUrl, DateTimeOffset AuthorizedAtUtc, byte[]? EncryptedPassword)` Domain record, mapped via `OutOfTheBoxDbContext` the same way `GitHostAuthorization`/`Run`/`RunResourceSample` already are. `EncryptedPassword` is populated only for Azure DevOps Artifacts entries (`null` for generic-feed entries, whose secret lives only in the NuGet configuration, never in this table). `list_authorized_nuget_feeds`/`revoke_nuget_feed_authorization` re-derive which mechanism applies from the feed URL itself via `AzureArtifactsFeedClassifier` each time, rather than persisting a separate discriminator column - the classification is a pure function of the URL, so a second column would only be redundant, not more correct.

### No `Run`/history record for any of the three new tools
Unchanged: these are synchronous, in-process operations with no process tree, no stdout/stderr, nothing to poll.

## Risks / Trade-offs

- **[Risk]** The token crosses the MCP JSON-RPC channel once, at authorization time - the same trust boundary as every other tool argument, matching the git-credential change's identical risk acceptance. → Mitigated by: never logging it, never echoing it in the tool's own result, and never constructing a child process command line that would contain it.
- **[Risk]** The Azure DevOps Artifacts mechanism injects the decrypted PAT into a spawned `dotnet` process's environment block. A child process's environment variables are not exposed via WMI's `Win32_Process` class the way `CommandLine` is (no `EnvironmentVariables` property), so this is a materially smaller exposure surface than a command-line argument - but it is not zero: a sufficiently privileged local process (one able to open a handle to the child and read its PEB, or attach a debugger) can still recover it. Accepted as a real, honestly-stated trade-off inherent to the mechanism explicitly requested - the Azure Artifacts Credential Provider's own documented non-interactive story has no lower-exposure alternative for a fully headless service.
- **[Risk]** This change persists a DPAPI-encrypted secret in this service's own database for the Azure DevOps Artifacts mechanism - a deliberate, narrow exception to the principle the git-credential change and this change's own generic-feed mechanism otherwise hold to. → Mitigated by: encryption happens before the value ever reaches EF Core, decryption happens only in-process for verification or environment-variable construction, and the exception is scoped to exactly the one mechanism that structurally requires it (a process-scoped environment variable has no durability of its own).
- **[Risk, unverified]** This service runs as a dedicated least-privilege Windows Service account, not an interactively-logged-in user. Both `ProtectedData` (used directly, for the Azure DevOps Artifacts mechanism) and `NuGet.Configuration`'s `EncryptionUtility` (used internally, for the generic-feed mechanism) are DPAPI-backed, which is normally scoped to a loaded user profile a service account does not automatically get - the same unverified risk the git-credential change flagged for Windows Credential Manager. Unconfirmed until tested against the real service process. If it does not work correctly, the fallback differs per mechanism: the generic-feed mechanism can fall back to `storePasswordInClearText: true` (NuGet's own documented escape hatch); the Azure DevOps Artifacts mechanism would need a different at-rest protection scheme entirely (e.g. a machine-scoped DPAPI flag, or a service-managed key) - a design amendment to make if and when this is confirmed, not preemptively.
- **[Risk, unverified]** The exact WiX/Burn mechanics for vendoring the Azure Artifacts Credential Provider's release archive and extracting it to a fixed install path are new to this codebase (Git for Windows is an external chained prerequisite the installer merely requires be present/installs via its own upstream installer, not a binary this project vendors and extracts itself) - unconfirmed until attempted. If it proves materially harder than expected, the fallback is documenting a manual one-time operator install step (matching how `git config --global credential.helper` is a documented manual fallback today) rather than blocking the whole change on installer automation.
- **[Risk, unverified]** GitHub Packages' and Azure Artifacts' exact accepted-username conventions for PAT-as-password authentication are asserted from documented convention, not yet confirmed against a real authenticated restore against either - folded into live verification.
- **[Risk]** Some Azure DevOps organizations disable PAT-based authentication entirely (Entra ID/OAuth-only policies) - even a correctly-configured Azure Artifacts Credential Provider would then fail non-interactively, since its own interactive/browser fallback is unusable under this headless service. Outside this service's control entirely, the same class of risk the git-credential change accepted for "cannot invalidate the PAT upstream."
- **[Trade-off]** Verification is local-only for both mechanisms (read-back-and-compare, not a real network round trip against the feed) - a written credential that round-trips correctly but is itself wrong (a typo'd or already-revoked PAT) still reports success, only surfacing as a failure on the next real `dotnet_run` restore. Accepted as consistent with the git-credential change's own equivalent choice.

## Migration Plan

Purely additive. New EF Core migration for `NuGetFeedAuthorizations` (feed URL, authorized-at, nullable encrypted-password - schema-additive, no existing table touched). New `NuGet.Configuration` package reference added to `Directory.Packages.props`/`OutOfTheBox.Infrastructure.csproj` for the generic-feed mechanism; no new package for the Azure DevOps Artifacts mechanism (`ProtectedData` is BCL). New installer payload: the vendored Azure Artifacts Credential Provider archive, extracted at install time to a fixed path. No feature flag - reachability is gated by the same bearer token every other MCP tool requires. Ship in the next installer build; the About page's MCP tool list gets updated in the same change.
