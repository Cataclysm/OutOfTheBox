**Cross-reference**: this design's Goals/Decisions describe MCP as additive alongside REST - that was the plan when written, and remains an accurate record of why MCP was built the way it was. REST was subsequently removed entirely (`openspec/changes/sbx-remove-rest-api/`), so any Decision below that reasons about "the REST API" is now describing something that no longer exists; the underlying MCP design choices themselves (start/poll instead of blocking, the buffering component, tool granularity, hosting inside `Presentation`/`Host`) are unaffected and still current.

## Context

See `proposal.md` for motivation. Relevant existing state this design builds on: `dotnet-command-execution`/`git-command-execution`/`file-transfer`/`repository-management` are already implemented against `Application`-layer ports (`IProcessRunner`, `RunRegistry`, `IRunEventBus`, `IRepositoryManager`, `IWorkingDirectoryResolver`) consumed today only by `Presentation`'s minimal-API endpoint classes (`RunEndpoints`, `FileTransferEndpoints`, `RepositoryEndpoints`) and by the Blazor dashboard. `Presentation` has zero reference to `Infrastructure` (mechanically enforced by `ArchitectureTests`); the REST endpoints reach `Infrastructure` implementations only through DI-injected `Application` interfaces. This change adds a second `Presentation`-layer consumer of those same ports — it does not touch `Domain`, `Infrastructure`, or the persistence schema.

Research performed for this design (web search, since the MCP ecosystem and its .NET SDK are young and evolving faster than training knowledge can be trusted for): MCP's Streamable HTTP transport (the current, non-deprecated remote transport) has the calling client POST JSON-RPC to a single endpoint; the server may answer with a plain JSON response or upgrade that response to an SSE stream to deliver multiple messages — including `notifications/progress` — before the final result. Claude Code supports Streamable HTTP for remote MCP servers directly. The official C# SDK ships as `ModelContextProtocol` (core) + `ModelContextProtocol.AspNetCore` (ASP.NET Core hosting: `AddMcpServer().WithHttpTransport()`, `MapMcp()`), with a v1.x stable line and a v2.0 preview in flight as of this writing — the exact version to pin is an implementation-time decision (tasks.md), not fixed here.

## Goals / Non-Goals

**Goals:**
- Add MCP as a second, fully additive entry point to this service's existing capabilities, reachable by the sbx-side Claude Code instance with far less protocol overhead than today's curl/SSE pattern.
- Preserve the one property that actually matters about today's SSE-based interface — the caller can see a long-running `dotnet`/`git` command's output incrementally and choose to cancel it early — without betting that on an MCP feature whose real behavior in Claude Code's client isn't confirmed.
- Keep the change confined to `Presentation` (new tool-handler classes) and `Host` (composition-root wiring); no `Domain`/`Infrastructure`/`Application` port changes beyond what's strictly needed to support polling (see Decisions).

**Non-Goals:**
- Not replacing or deprecating the REST+SSE API. It keeps serving whatever calls it today; this change adds a second interface, not a migration.
- Not implementing MCP's OAuth 2.1 authorization framework. That framework exists for multi-tenant/public MCP servers with dynamic client registration — this is a private, operator-controlled, point-to-point link between one sbx sandbox and one Windows host, the same trust boundary the REST bearer token already assumes.
- Not exposing MCP "resources" (a separate MCP primitive for addressable, subscribable content) for run output. Tools with an explicit poll call are simpler to reason about and test, and the research below found no evidence Claude Code's client does anything with `resources/subscribe` that a poll tool wouldn't also achieve.
- Not implementing MCP "sampling" or "elicitation" (server-initiated requests back to the client) — nothing in this capability set needs the server to ask the model a question mid-tool-call.

## Decisions

### Incremental output: a `read_run_output` poll tool, not MCP progress notifications
This is the decision the proposal flagged as the open risk to resolve, not defer. Findings from research: MCP progress notifications (`notifications/progress`) carry a `progress`/`total` numeric pair and a short `message` string, sent as out-of-band SSE messages tied to a `progressToken` while a tool call is outstanding — but every source examined describes them as being for **client-side UI feedback** (a percentage or status line), not as a documented channel for delivering incremental *content* back into the calling model's own context. No source found describes a client reliably feeding progress `message` text into the LLM's reasoning the way it would treat actual tool-call output. Relying on this for the core "watch dotnet test run and decide whether to cancel" value proposition would be betting the feature's correctness on unverified, UI-oriented client behavior.

**Decision**: `dotnet_run`/`git_run`/`clone_repository` return immediately with a run id (status "running"), exactly mirroring what the REST API's `X-Run-Id` header already does before its SSE stream starts. A new `read_run_output` tool call lets the caller fetch output produced since an offset, plus current status, and repeat that call as many times as it wants — the same fundamental access pattern the REST API's SSE stream gives today, just expressed as an explicit, structured tool call instead of an implicit stream the caller has to keep an open connection for. This is guaranteed correct under MCP's baseline request/response guarantee, independent of how any particular client chooses to handle progress notifications. Progress notifications MAY still be sent alongside (a coarse "still running, N seconds elapsed" ping) as a UI nicety for clients that do render them — but nothing depends on them.

Alternative considered: expose run output as an MCP **resource** (`runs://{id}/output`), subscribable via `resources/subscribe`, letting the server push updates. Rejected for this round: it's a second MCP primitive with its own lifecycle (subscribe/unsubscribe, resource templates) to implement and test, for a benefit (server-push instead of client-poll) that matters less here than it sounds — a coding agent deciding whether to keep waiting on a build is already going to re-check periodically regardless of push vs. pull, since it has other reasoning to do between checks. Worth revisiting only if a future round finds real evidence Claude Code's client makes meaningfully better use of resource subscriptions than of a poll tool.

### One shared `read_run_output`/`cancel_run` pair, not per-capability variants
`dotnet_run`, `git_run`, and `clone_repository` all funnel into the same `RunRegistry`-backed run id space the REST API already shares across `dotnet`/`git`/repository-clone. Rather than three separate "read this dotnet run's output" / "read this clone's progress" tools, one `read_run_output` and one `cancel_run` tool, parameterized only by run id, cover every run kind reachable through MCP. This is also why `mcp-repository-access`'s `clone_repository` deliberately does not get its own polling tool, and why `cancel_run` is specified to accept a clone's run id even though the REST cancel endpoint historically refuses one (`repository-management`'s existing "not the REST cancel endpoint" requirement) — that REST-side restriction was about keeping the REST cancel endpoint's scope narrow when it was first added, not a considered policy against ever cancelling a clone. MCP starts with one cancellation tool covering everything it can start; carrying the REST-side restriction forward would just be needless asymmetry.

### MCP server lives inside `Presentation` and `Host`, not a new project
Tool-handler classes (structurally parallel to `RunEndpoints`/`FileTransferEndpoints`/`RepositoryEndpoints`) go in `Presentation`, calling only the same `Application` ports those REST endpoints already call — no new `Infrastructure` dependency, so the existing `Presentation`-has-no-`Infrastructure`-reference architecture rule (`ArchitectureTests`) is satisfied without a rule change. `Host`'s `Program.cs` composition root adds `AddMcpServer().WithHttpTransport()` and `app.MapMcp()` alongside its existing minimal-API/Blazor registration, on the same Kestrel instance and port the REST API and dashboard already use — one process, one listener, one HTTPS certificate, not a second service to install/monitor/firewall-open separately. A new sixth project was considered and rejected: the MCP SDK dependency is no heavier than `Microsoft.AspNetCore.Mvc.Testing` or any other `Presentation`-referenced package, and splitting it out would only add another `ArchitectureTests` boundary to maintain for no isolation benefit (this code has exactly the same dependency shape as the REST endpoints it sits beside).

### MCP authentication reuses the existing bearer token via a static `Authorization` header
The same credential `service-authentication` already validates for the REST API is required on MCP requests too, checked the same way (constant-time comparison) before a tool call executes — see `mcp-server`'s spec. MCP's Streamable HTTP transport carries ordinary HTTP headers, so this needs no protocol-level accommodation; it's the same authentication filter pattern already used for the REST endpoints, applied to the new MCP route. OAuth 2.1 (MCP's own newer authorization framework, aimed at public/multi-tenant MCP servers needing dynamic client registration and consent flows) is explicitly not implemented — wrong shape for a private, operator-provisioned point-to-point link, and would require running or delegating to an authorization server for no corresponding benefit here.

### `read_run_output`'s offset-based polling needs a small addition to run output buffering
Today's SSE path has exactly one consumer per run (the HTTP response stream itself) and doesn't need to retain output once delivered. `read_run_output` needs output retained and replayable from an arbitrary offset, for a caller that may start polling after the run began and may poll at any cadence. This needs a per-run in-memory output buffer (bounded by the same output size cap `dotnet-command-execution` already enforces, so this adds no new unbounded-growth risk) that both the existing SSE path and the new poll path can read from — likely a small addition to or wrapper around the existing `IProcessOutputSink`/`RunRegistry` machinery rather than a new persistence concept. This is the one piece of this change that touches shared execution-engine plumbing instead of being purely additive at the `Presentation` layer; tasks.md should treat it as its own step so it gets focused review and test coverage, and it needs to be built so the *existing* REST/SSE path's behavior and tests are unaffected — buffering is additive to what already happens, not a replacement of it.

### File content over `transfer_file`: base64-encoded blob, with a configured size cap
MCP tool results are single response payloads (no raw-byte-stream primitive the way an HTTP file download is); the standard way to return binary content from an MCP tool is a base64-encoded blob in the result. Base64 inflates size by roughly a third, and an MCP response is not designed to be an arbitrarily large payload the way an HTTP stream comfortably is — hence `mcp-file-transfer`'s explicit "reject rather than truncate" size-cap requirement, distinct from the REST `file-transfer` endpoint (which streams and has no comparable size concern). The exact cap value is a configuration decision for tasks.md, not fixed here; it should default conservatively (large enough for typical build artifacts/logs, small enough not to blow up a tool-result payload) and be operator-configurable the same way `OutputCapBytes` already is.

## Risks / Trade-offs

- **[Risk]** The MCP C# SDK is young (mid-major-version-transition as of this design) — APIs used here may shift before this is implemented. → Mitigation: pin an exact stable version at implementation time (tasks.md), not now; treat any breaking SDK change discovered during implementation as an implementation-time adjustment, not a reason to revisit this design's shape.
- **[Risk]** Claude Code's actual behavior calling a remote Streamable HTTP MCP server with a static bearer header has not been verified against a real Claude Code instance in this project (only documented client capability was checked). → Mitigation: tasks.md should include an explicit live end-to-end check (a real sbx-side Claude Code instance calling the deployed MCP endpoint), the same "verify live, don't just trust a clean build" discipline already established for the REST API and installer work in `sbx-dotnet-command-service`.
- **[Risk]** Two authenticated network entry points (REST + MCP) onto the same execution engine modestly widens the attack surface versus one. → Mitigation: both share the exact same bearer credential and the exact same underlying confinement/locking logic — this is one trust boundary reachable two ways, not two independently-secured surfaces to keep in sync.
- **[Trade-off]** The start/poll shape means a caller that wants to "just wait for the result" has to loop `read_run_output` itself, rather than one call blocking until done. Accepted deliberately (see Decisions) — a Claude Code agent polling a tool between other reasoning steps is a normal, cheap pattern, and the alternative (a single blocking call) reintroduces the exact "no incremental visibility" problem this design set out to avoid.

## Migration Plan

No migration in the data sense — this is additive. Rollout is standard for this project: implement behind the existing `dotnet build`/`dotnet test` gates, verify live against a real running `Host` (including a real MCP client call, per the risk above), ship in the next installer build. No feature flag is planned — the MCP endpoint being reachable is gated by the same bearer token as everything else, so there's no meaningful "half-rolled-out" state to guard against; an operator who doesn't want it reachable can simply not open network access to it (the REST API has the same property today).

## Open Questions

- Exact `ModelContextProtocol`/`ModelContextProtocol.AspNetCore` version to pin, and whether stateless or stateful MCP session mode is the better fit here (stateless is the newer SDK default and this service's tools are all naturally statelessly-authenticated per-call, but a session concept could let future work reduce the bearer-token overhead per call) — deferred to tasks.md/implementation, doesn't change any spec or the shapes decided above.
- Whether `skills/dotnet-command-service/SKILL.md` should be split into a REST section and an MCP section, or whether a second skill file is clearer — a documentation-authoring call to make once the tools' real shape (post-implementation) is in hand, not a spec-level decision.
