**Investigation note (affects 9.9's and 9.10's test implementation, not production behavior):** an `HttpClient` awaiting a `POST /run/git` response (even with `ResponseHeadersRead`) against a request that's genuinely blocked behind a native process tree (`git.exe` → `sh.exe` → the blocking hook's child) was observed, intermittently and not fully root-caused, to not become observable to the caller until the whole request completes - confirmed via temporary server-side instrumentation that `RunRegistry.TryAcquire` itself still succeeds within single-digit milliseconds of the request arriving server-side, so this is a client/transport-observation quirk (suspected scheduling interaction, not a service-side delay - ruled out thread-pool starvation and TLS-layer explanations specifically). Worked around by never awaiting that specific response for synchronization: the git run is fired fire-and-forget, and a **separate** `HttpClient` (reusing the same blocked client for a second concurrent request was itself observed to queue behind it) polls with cheap, disposable probe requests until the lock is observed held (BDD 9.9) or the conflict payload's `runId` is captured (BDD 9.10's cancellation target). None of this affects real deployment (a real sbx caller normally isn't racing its own request against a second one on the same `HttpClient` instance) - it's specific to how this test harness synchronizes two requests against one in-process `WebApplicationFactory`.
