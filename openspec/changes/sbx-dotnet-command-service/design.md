## Context

Greenfield project (repo currently empty apart from openspec scaffold). Host is Windows with .NET 10 SDK installed. Caller is a Claude Code instance running in a remote sbx sandbox, reaching this host over the network — not localhost. A human operator also uses the same host's browser (or one on the local network) to view status/history and manage the repository inventory. See proposal.md for motivation; specs/dotnet-command-execution, specs/git-command-execution, specs/artifact-transfer, specs/repository-management, specs/service-authentication, specs/run-history, and specs/service-dashboard for required behavior.

`git-command-execution`, `artifact-transfer`, and `repository-management` were all added to this change before any of it was implemented (Sections 1–8 already shipped only `dotnet-command-execution`, `service-authentication`, and their shared infrastructure) — they extend the same in-progress plan rather than modifying delivered behavior.

## Goals / Non-Goals

**Goals:**
- Single Windows-hosted process that survives reboots and serves requests continuously.
- Execute arbitrary `dotnet` and `git` argument lists safely with respect to process-spawning (no shell interpretation), path confinement, and credential-gated access — neither CLI's argument list is restricted or filtered by content.
- Stream stdout/stderr back to the caller incrementally as a command runs, with a final event carrying the exit code, so a caller polling a long `dotnet test` run sees live progress instead of a multi-minute silent wait.
- Transfer a build artifact file from a repo back to the caller, confined so it can never read a file outside that specific repo's own directory.
- Run commands against different repos in parallel; allow at most one in-flight `dotnet`/`git` command per repo at a time, regardless of which of the two it is; let artifact transfers proceed independently of that lock.
- Let the caller cancel an in-flight run (command or transfer) by run id, through one shared endpoint.
- Durably persist every run of every kind (`dotnet` command, `git` command, artifact transfer, repository clone, repository delete) with its kind, repo, kind-appropriate detail, timestamps, outcome, and output/metadata, so history survives a restart — and make it filterable by kind/outcome/repo and free-text searchable.
- Give a human operator a live-updating, pleasant web view of current status and history for every run kind — no manual refresh, no hand-crafted API calls — including filter/search controls over history, organized into distinct views/subpages rather than one dense page.
- Let the operator see every repository the service knows about with live size/git-status/active stats, filter/search that list, clone a new one in, and delete one that's no longer needed — entirely from the dashboard, with no REST surface the sbx caller can reach for any of it.
- Version the software with standard SemVer, starting directly at `1.0.0` (no pre-1.0 versions), and surface the running name/version both programmatically (`/version`) and visibly in the dashboard.
- Package `Host` as a single self-contained deployable (no separate .NET runtime install needed for the service's own hosting, no separate database server) and ship a double-click WiX installer that handles everything else — including installing the .NET SDK and Git for Windows themselves if the host doesn't already have them, since the service's actual purpose (spawning `dotnet`/`git` against target repos) needs the SDK on `PATH` regardless of how `Host` itself is packaged.
- Make install/upgrade/uninstall a native MSI experience (Programs and Features, standard upgrade/rollback semantics) that never touches configuration or persisted history.
- A full automated test suite (unit + BDD) that builds and runs with the plain .NET 10 SDK CLI (`dotnet build`, `dotnet test`) — no IDE, no separate test runner.
- Clean Architecture layering (Domain / Application / Infrastructure / Presentation) with the dependency direction mechanically enforced, not just documented, so the boundary can't silently erode over time.
- A Claude Code skill documenting the full API contract for the sbx-side caller — `dotnet`, `git`, artifact transfer, and cancellation — so it doesn't need to reverse-engineer auth/streaming/cancellation from the specs or trial and error.

**Non-Goals (v1):**
- A job queue that auto-serializes a second command behind a busy repo's lock — a second request for a busy repo is rejected immediately, not queued/waited-on server-side.
- Multi-user auth (roles, per-caller keys) — single shared credential only, for both the API and the dashboard.
- Sandboxing `dotnet.exe`/`git.exe` themselves (e.g. restricted user, container) beyond path confinement and process-argument safety. MSBuild can run arbitrary build-time code (custom targets/tasks) and git can run arbitrary code via hooks — this service does not attempt to prevent either; it trusts the caller to the same degree the caller is trusted to run `dotnet`/`git` at all.
- Restricting which `git` subcommands or flags are permitted — no allowlist/denylist, by explicit request; the caller is trusted to the same degree as for `dotnet`. This extends to a repository clone's source URL too — no allowlist there either.
- Browsing or listing a repo's directory tree via `artifact-transfer` — the caller must already know the exact relative file path it wants; no directory-listing endpoint in v1.
- A REST/bearer-token surface for repository management — clone/delete/list are dashboard-only, authenticated by the dashboard's own login, never reachable by the sbx sandbox caller.
- Soft-delete, trash, or any recovery path for a deleted repository — deletion is immediate and permanent; the dashboard's confirmation step is a UX safeguard, not a data-recovery mechanism.
- Per-repo storage quotas or automatic cleanup of large/idle repositories — the Repos view surfaces size so an operator can judge this manually; the service doesn't act on it.
- History retention/archival policy (pruning old runs, size-based rotation, or downsampling old resource-sample series) — v1 keeps everything indefinitely, at full sample resolution, in the SQLite file.
- Horizontal scaling / multi-instance deployment — the in-memory run registry, SQLite file, and Blazor Server circuits all assume a single process on a single host.
- A GUI/MSI installer or downgrade support — install/upgrade are PowerShell scripts, and upgrading to an older version is not a supported path (schema migrations are forward-only).
- Automated installation of the Claude Code skill into the sbx sandbox's own environment — that's a separate machine this repo doesn't control; the skill is authored and shipped here, but installing it on the sbx side is a manual step for whoever sets that environment up.
- Fully automated coverage of real-deployment concerns (real Windows Service install, real firewall, real TLS cert, a real second machine acting as the sbx caller) — those remain a manual End-to-End Verification checklist; `dotnet test` covers everything short of an actual deployed instance.

## Architecture

Clean Architecture (Onion-style): `Domain` at the center, `Application` wrapping it, and an outer ring split into two independent slices — `Presentation` and `Infrastructure` — that each depend inward on `Application` but **never on each other, with no exception**. A fifth project, `Host`, sits outside all of the rings as the composition root: it's the only project allowed to reference both outer-ring slices, and its only job is wiring them together and running the process. `Presentation` and `Infrastructure` are otherwise unaware of each other's existence, including for DI registration.

- **`OutOfTheBox.Domain`** — entities (`Run`, `RunResourceSample`, `RepositorySummary`), the `RunKind` state (DotnetCommand/GitCommand/ArtifactTransfer/RepositoryClone/RepositoryDelete), the `Outcome` state (Running/Completed/TimedOut/Cancelled/ValidationFailed/NotFound/AlreadyExists/Interrupted), and pure business rules with zero IO/framework dependency: CPU%/RAM aggregation math, and the "is this already-resolved path contained under that already-resolved root" decision (the actual filesystem canonicalization and symlink resolution is IO, so it's Infrastructure's job to resolve both paths and hand the two resolved strings to this Domain rule) — reused unchanged for the working-directory confinement check, artifact-transfer's two-level file confinement check, and repository clone/delete's target-name confinement check. No NuGet dependency beyond the BCL — nothing here can reference ASP.NET Core, EF Core, WMI, or `PerformanceCounter`.
- **`OutOfTheBox.Application`** — use-case orchestration and the ports (interfaces) Infrastructure implements: `IRunRepository` (list/filter/search plus by-id lookup), `IRunResourceSampleRepository`, `IProcessRunner`, `IArtifactTransferService`, `IRepositoryManager` (list/clone/delete), `IRepositoryStatsProvider` (size + git status), `IProcessMonitor`, `IResourceSampler`, `IRunEventBus`, `IResourceEventBus`, `IClock`. Also owns the services that coordinate them — run start/cancel orchestration, the in-memory per-repo lock registry (shared by `dotnet` runs, `git` runs, and repository clone/delete; not acquired by artifact transfers — pure in-memory state, no external dependency, so it belongs here rather than Infrastructure), and kill-scope verification. Also owns the `ServiceOptions` configuration-shape type (root directory, bearer token, timeouts, output cap, SQLite path): the POCO itself has to live somewhere both `Presentation` and `Infrastructure` can see without depending on `Host`, and `Host` binds real `IConfiguration` values into it at startup. Depends only on Domain.
- **`OutOfTheBox.Infrastructure`** — concrete implementations of every Application port: real `System.Diagnostics.Process` spawning (one generalized runner parameterized by executable — `dotnet.exe` or `git.exe` — rather than a separate class per CLI, reused for repository clone), WMI process-tree discovery, `PerformanceCounter`/`GlobalMemoryStatusEx` sampling, file-stream artifact transfer with two-level path resolution, recursive directory deletion and size enumeration, lightweight git-status querying, EF Core + SQLite persistence and migrations, the in-memory event-bus implementations, the system clock. Depends on Application + Domain only.
- **`OutOfTheBox.Presentation`** — a Razor Class Library (so it can carry `.razor` components and its own `wwwroot`, e.g. Chart.js) plus plain classes: the minimal API endpoint definitions as `IEndpointRouteBuilder` extension methods (SSE `dotnet` run, SSE `git` run, artifact transfer, cancel, `/version` — **no** endpoints for repository management, which is dashboard-only), the Blazor Server dashboard components/pages (Status/History/Repos top-level views, run-detail and repo-detail subpages, history and repo-list filter/search controls, the clone/delete controls calling `IRepositoryManager` directly, the name/version branding element), and auth-cookie/bearer middleware classes. Depends on Application + Domain only — it is not an executable and has no `Program.cs` of its own; it exposes extension methods (`MapCommandExecutionEndpoints(...)`, `MapArtifactTransferEndpoints(...)`, `AddDashboardServices(...)`) for `Host` to call.
- **`OutOfTheBox.Host`** — the actual executable: `Program.cs` builds the `WebApplication`, calls `Presentation`'s registration/mapping extension methods, registers `Infrastructure`'s concrete types against `Application`'s interfaces in the DI container, configures Kestrel/HTTPS, and calls `UseWindowsService()`. `Host` references all four other projects; no other project references `Host`. It contains no business or presentation logic of its own — if it's more than DI registration, config binding, and framework wiring, that code belongs in one of the four inner projects instead.

Splitting the composition root out as its own project (rather than letting `Presentation`'s `Program.cs` do double duty, as many ASP.NET Core Clean Architecture templates do) is what makes "`Presentation` and `Infrastructure` never reference each other" a literal, exception-free rule instead of one with a carved-out escape hatch — and it's what the operator asked for directly.

This is more structure than a service this size strictly needs, but it buys two concrete things beyond "looks clean": Domain/Application logic becomes unit-testable without spinning up EF Core, WMI, `PerformanceCounter`, or Kestrel at all, and the boundary is something a test suite checks on every build instead of something a code reviewer has to remember to look for.

## Decisions

**Framework: ASP.NET Core 10 minimal API, hosted as a Windows Service, from `Host`.**
`Host` calls `Microsoft.Extensions.Hosting.WindowsServices`' `UseWindowsService()` so the process runs under the Windows Service Control Manager, instead of relying on a logged-in console session or Task Scheduler. Alternative considered: run as a plain console app in a scheduled task — rejected because SCM doesn't depend on a user session existing and gives a place to configure restart-on-crash (see Packaging below — SCM does not restart on crash by default; it must be configured).

**Packaging: self-contained, single-file, win-x64 publish for `Host` itself.**
`dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true` produces one `.exe` that bundles the .NET 10 runtime, so `Host`'s own ability to start and serve the dashboard/API never depends on what SDK/runtime state happens to be installed on the machine (including if the SDK the installer put there — see below — is later removed by something else entirely). `IncludeNativeLibrariesForSelfExtract` is required because the SQLite provider ships a native library (`e_sqlite3.dll`); without it, single-file publishing would fail to resolve that native dependency at run time. Trimming (`PublishTrimmed`) is deliberately **not** enabled: Blazor Server and EF Core are reflection-heavy, and trimming them has a real risk of removing code that's only reached dynamically, causing runtime failures that are hard to catch pre-deployment — the resulting binary is larger (roughly 100+ MB) but reliable, which matters more for a service that's rarely redeployed. Native AOT was considered and rejected for the same reason as trimming, more severely: Blazor Server's interactive-server render mode has limited/immature Native AOT support as of .NET 10, so self-contained single-file is the practical ceiling for "self-contained" here, not full AOT. **This decision is orthogonal to, not superseded by, the installer bundling the .NET SDK below** — the SDK is a *functional* prerequisite (the spawned `dotnet build`/`test` processes this service exists to run need it on `PATH`, no matter how `Host` itself is packaged), not a *hosting* prerequisite for `Host`; keeping `Host` self-contained means the dashboard/API stay up even in a hypothetical where the SDK is later uninstalled out from under it.

**Data/config directory is separate from the install directory, so upgrade never touches configuration or history.**
The published `.exe` and its install directory (e.g. `C:\Program Files\OutOfTheBox`) are treated as disposable/replaceable. Configuration (`appsettings.json`, read from a data-directory file at a path given by the `OUTOFTHEBOX_DATA_DIR` environment variable set on the Windows Service's own registry entry) and the SQLite database file both live under a fixed per-machine data directory (e.g. `C:\ProgramData\OutOfTheBox\`) created once at install time and never touched by upgrade *or* uninstall. This is what makes "upgrade = replace the files" true: the new binary starts up, reads the same config from the same data directory, runs any pending EF Core migrations against the same SQLite file, and continues where the old binary left off — no config re-entry, no data migration step for the operator to remember. Extending "untouched by upgrade" to also mean "untouched by uninstall" is a deliberate, explicit choice (see the MSI decision below) — an operator who uninstalls expecting a clean slate and later reinstalls gets their history back, which is the safer default for something that's expensive to reconstruct and cheap to leave behind.

**Install/upgrade/uninstall via a WiX Toolset installer (bootstrapper + MSI), not hand-rolled PowerShell scripts.**
This reverses an earlier decision in this same document, which rejected WiX as disproportionate tooling for a single-operator internal service. On reflection (explicit operator request, prioritizing installation being genuinely pleasant over minimizing build-toolchain surface), the calculus changed: a real MSI buys native Programs-and-Features upgrade/uninstall semantics, a proper config-collection UI, and — critically, once bundling the .NET SDK became part of the ask — a natural place to chain prerequisite installers, none of which a hand-rolled script does as well or as safely.

Two pieces, built with WiX Toolset v5 (SDK-style projects, build via plain `dotnet build` — no Visual Studio, consistent with every other project in this repo):

- **A Burn bootstrapper** (`OutOfTheBoxSetup.exe`, the thing an operator actually double-clicks) chains, in order, three packages: (1) the **.NET 10 SDK** — detected via a registry/product search, downloaded from Microsoft's official redistributable and silently installed only if a compatible version isn't already present; needed because the spawned `dotnet build`/`test` processes this service exists to run need the SDK on `PATH`, a functional requirement that exists regardless of `Host`'s own self-contained packaging (see the Packaging decision above); (2) **Git for Windows**, same detect-then-install-only-if-missing pattern, needed for the same reason `git` was always an implicit prerequisite, now made an explicit, handled one; (3) **the OutOfTheBox MSI** itself. Burn's own detect-and-skip behavior means a machine that already has both installed does a fast, no-op check and goes straight to the MSI — this isn't "always reinstall the SDK," it's "guarantee it's there."
- **The MSI** installs the self-contained `Host` publish output (exe + `wwwroot`) to the install directory. Config (repo root directory, bearer token, port) is collected as MSI properties (`REPOROOTDIR`/`BEARERTOKEN`/`PORTNUMBER`) via a custom `WixUI` dialog (`ConfigDlg`, spliced into the stock `WixUI_Minimal` sequence between the Welcome and Verify-Ready pages), reachable both when the MSI is run directly *and* when installed via the Burn bootstrapper - the latter needed `bal:DisplayInternalUICondition="WixBundleAction = 6"` on the chained `MsiPackage`, since Burn's standard bootstrapper application otherwise runs a chained MSI package at a reduced UI level by default and `ConfigDlg` would never show at all. This was a real, user-reported gap (not caught by any automated check, since `wix msi validate`/ICE have nothing to say about Burn's runtime UI-level behavior), found only once someone actually ran the bootstrapper on a real machine and saw "no choices, just Install or Cancel." The `bal:` namespace was already imported for `WixStandardBootstrapperApplication`; `DisplayInternalUICondition` is a v3-era `DisplayInternalUI` concept relocated into that extension for v4+ rather than remaining a plain `MsiPackage` attribute (confirmed via WiX's own FAQ and a maintainer response, not the non-existent v4+ `MsiPackage` attribute an earlier attempt had already ruled out) - scoped to `WixBundleAction = 6` (`BOOTSTRAPPER_ACTION_INSTALL` specifically) so it fires only for an actual install/upgrade, never uninstall/modify/repair, where a config-collection dialog makes no sense. Verified against the compiled bundle via `wix burn extract`, not just "the build succeeded": its `BootstrapperApplicationData.xml` (UTF-16 encoded - a first extraction attempt read it as UTF-8 and found nothing, a false negative worth remembering) carries `<WixBalPackageInfo PackageId="OutOfTheBoxMsiPackage" DisplayInternalUICondition="WixBundleAction = 6" />` exactly. **The bearer token (and, transparently, the service account's own logon password) don't require the operator to supply anything**: a managed custom action (`installer/OutOfTheBox.Msi.CustomActions`, a genuine compiled `.CA.dll`, not a hand-authored script) resolves each with the same three-way precedence - an explicit command-line value always wins; otherwise a value persisted from a prior install (found via `RegistrySearch` into `HKLM\SOFTWARE\OutOfTheBox`, populated during `AppSearch`, well before the custom action or the dialog run) is reused, so upgrades never rotate the token out from under the operator; only when neither is available is a new cryptographically random value generated (`RandomNumberGenerator`, not a weaker PRNG - this is a real security credential). `ConfigDlg`'s bearer-token field is pre-filled with whichever of those three the custom action resolved to, and remains directly editable - an operator's edit becomes the value that's persisted (and thus preserved) going forward, taking precedence over everything else the next time. This precedence rule is worth being precise about because getting it backwards is a real, easy-to-miss bug: the first draft of this custom action checked the persisted value before an explicit override, which would have silently discarded an operator's deliberate "change the token during this upgrade" request - caught by reasoning through that exact scenario, not by any tool, and given permanent regression coverage afterward via a small, `Session`-independent, directly unit-tested `SecretResolution.Resolve` function (`installer/OutOfTheBox.Msi.CustomActions.Tests`). Either way, the collected values are written directly into the Windows Service's own `Environment` registry value (`HKLM\SYSTEM\CurrentControlSet\Services\OutOfTheBox\Environment`, a multi-string of `NAME=value` lines) — reusing the standard ASP.NET Core environment-variable configuration override `Program.cs` already supports, rather than a custom action rendering a JSON file. This also carries `OUTOFTHEBOX_DATA_DIR`, so `Program.cs`'s existing data-directory config-loading mechanism finds the right path with no new code needed; the installer just becomes another way to set the same environment variables an operator could otherwise set by hand. The WiX Util extension's `util:User` element declaratively creates the dedicated least-privilege service account (see the generic-passthrough risk below for its exact rights) with `util:ServiceConfig` configuring SCM crash-recovery (SCM does not restart a crashed service by default, this has to be set explicitly regardless of which tool sets it); the WiX Firewall extension's `firewall:FirewallException` declaratively opens the configured port; native `ServiceInstall`/`ServiceControl` elements register the Windows Service; a `Launch` condition re-checks `git` is resolvable (defense in depth in case the MSI is ever run directly, bypassing the bootstrapper that's supposed to have already guaranteed it) and fails loudly with a clear message if not; `MajorUpgrade` handles version-to-version upgrade natively (WiX sequences the old version's removal and the new version's install, superseding the hand-rolled stop-verify-copy-start script that used to do this); native uninstall removes the installed files, the Windows Service, and the dedicated service account, but — per the Data/config directory decision above — never touches the data directory, so an operator's history and configuration survive an uninstall the same way they survive an upgrade. **`ResolveSecrets` itself needed a genuine fix once actually run on a real machine** (17.9a's own COM-API table verification never executes a custom action, only checks it's correctly wired up to run): a fully current Windows 11 24H2 test install failed with `SFXCA: Failed to get requested CLR info. Error code 0x80131700`, despite .NET Framework 4.8.1 being present - not a missing-prerequisite problem. Root cause was `OutOfTheBox.Msi.CustomActions.csproj` never shipping a `CustomAction.config`: `WixToolset.Dtf.CustomAction`'s own `PackCustomAction` MSBuild target only embeds `@(Content)` project items into the `.CA.dll` SFXCA package, nothing generates one automatically, so `SfxCA.dll`'s in-process CLR host was left to guess which runtime to load - a decades-old WiX/DTF quirk, not something specific to this environment (the identical error message and identical fix trace back to WiX's own issue tracker from 2010). Fixed by adding the file with `useLegacyV2RuntimeActivationPolicy="true"` alongside `<supportedRuntime version="v4.0" />`, marked `<Content Include="CustomAction.config" />` (not `None` - that item type is never picked up by the packaging target). **A second real-machine round (Windows Server 2025 Datacenter) surfaced three more gaps once `ResolveSecrets` actually succeeded and the install reached further than before**: (1) the bootstrapper's license screen showed generic "I agree to the license terms and conditions" boilerplate despite `LicenseUrl=""`, which WiX's own docs say should suppress it - it doesn't, at least not in this version, so the actual fix was extracting the compiled `HyperlinkTheme.xml`/`.wxl` (from `obj/.../wix-ir/`, not guessed at) into local `Theme.xml`/`Theme.wxl` copies with the EULA controls deleted, wired in via `ThemeFile`/`LocalizationFile` (both `Theme`/`LicenseUrl` still had to stay set to satisfy WiX's own "must have a value" schema check even though a custom theme overrides what's rendered); (2) `banner-493x58.bmp`'s dark violet gradient (from the earlier branding pass) made `VerifyReadyDlg`'s own stock black title text - which sits directly on top of it, an overlap that was invisible when the banner was WiX's original light default art - unreadable. A first fix lightened the banner instead; the operator rejected it directly ("restore it. the banner was fine. remove the TEXT that overlays the banner") - the banner's own look wasn't the thing to change. A second, lighter-weight removal attempt (a standalone `<ControlCondition>` mirroring the standalone `<Publish Dialog="...">` pattern already used elsewhere in this file) failed WiX's own schema validation (`WIX0005`) - `<UI>` doesn't accept a bare `ControlCondition`. With both surgical options exhausted and the operator explicitly preferring it, `VerifyReadyDlg` got the same full-rewrite treatment `CancelDlg`/`ProgressDlg` were deemed not worth (see the "Installer dark theme" decision above) - a new `VerifyReadyThemedDlg`, its Control/Publish content extracted via `wix msi decompile` against this project's own build rather than reconstructed from memory, reusing `panel-370x270.bmp` (generated back in 17.9c for this exact purpose and never wired up). Every reachable path into the stock dialog - not just `ConfigDlg.Next`, but also `WelcomeDlg`'s patch-install case and, more importantly, `MaintenanceTypeDlg`'s Repair/Remove buttons, the actual Programs-and-Features entry points - had to be found (by querying the compiled `ControlEvent` table directly, not assumed) and retargeted; (3) the service failed to start on an otherwise-successful install - Event Viewer: "This service account does not have the required user right 'Log on as a service.'" The dedicated-service-account decision above always assumed this right was "granted automatically" by `ServiceInstall`; that assumption was simply wrong - `CreateService` never grants `SeServiceLogonRight` programmatically, only the interactive Services GUI does, as an unrelated side effect. Fixed with `LogonAsService="yes"` on `util:User`, which calls `LsaAddAccountRights` directly. All three verified against compiled output (`wix burn extract` for the theme, `wix msi decompile` for the `LogonAsService` attribute, direct visual inspection of the regenerated banner), not just "the build succeeded." **A third round reported the exact same license symptom, verbatim, after both of the above were confirmed fixed** - the honest next step, before re-diagnosing anything, was a genuinely from-scratch clean rebuild (every `bin`/`obj`, the shared `artifacts/` directory, `Host` republished) to rule out a stale local build before assuming the operator's environment was at fault. The clean build reproduced identically, which forced a real re-investigation rather than a third guess - and it found the actual, complete root cause: **`WelcomeDlg` (the dialog every prior check had been run against) is not WixUI_Minimal's fresh-install entry point at all**. `WelcomeEulaDlg` is (`InstallUISequence`'s own `Action="WelcomeEulaDlg" Condition="NOT Installed"` row - never checked before, since an earlier attempt to query that table failed on a shell-quoting bug and was silently never retried). It carries WixUI_Minimal's stock placeholder license RTF verbatim (`Lorem ipsum dolor sit amet...` - the literal phrase reported from the very first bug report), and its own `Install` button ends the dialog sequence directly once the checkbox is checked, never routing through `ConfigDlg` at all regardless of any `ControlEvent` wiring - which retroactively explains the *original* "no choices, just Install or Cancel" report too; Burn's reduced-UI-level fix (above) was real but was never the whole story. Fixed via a standalone `<InstallUISequence><Show Dialog="override WelcomeEulaDlg" Condition="0" /></InstallUISequence>` - `override` is the exact access modifier WiX's own `WIX7009` error names for this class of conflict, the v4+ replacement for v3's `Overridable="yes"`. Redirecting `WelcomeDlg`'s own row to also cover `NOT Installed` hit a *second*, unrelated conflict (`WIX0091`, against the library's own internal duplicate declaration of that row), so rather than fight it too, a brand-new `<Show Dialog="ConfigDlg" Condition="NOT Installed" />` entry was added instead - a fresh install now launches directly into config collection, no intermediate Welcome screen. Verified against the compiled `InstallUISequence` table directly. **With the dialog bug no longer aborting every install, the service itself finally started for the first time - and crashed immediately**: `SQLite Error 1: 'no such table: Runs'` in `ReconcileInterruptedAsync`, called right after `Database.Migrate()` succeeds in the same scope - the exact "empty `SqliteFilePath` means every connection gets its own throwaway anonymous database" gotcha this project had already documented from dev-time smoke testing, but never before hit on a real install, because no install had ever gotten this far. The bundled `appsettings.json` ships `SqliteFilePath: ""` by design (so a test's in-memory config override is never shadowed by a bundled default) - and the installer's `Environment` registry value, which sets every other operator-facing setting, simply never set this one at all. Every real installation would have crashed exactly this way from the start; the dialog bugs above just meant no install had ever run long enough to prove it. Fixed by adding `OutOfTheBox__SqliteFilePath=[DATADIRFOLDER]outofthebox.db` to that same `Environment` value - `outofthebox.db` was already the filename `INSTALL.md`'s upgrade-rollback guidance assumed existed, even though nothing had ever created it there. **That fix didn't actually work - the operator reported the identical crash again.** The real bug was one level deeper: the `Environment` `RegistryValue`'s single `Value` attribute joined all five `NAME=value` pairs with a literal tab character, but a Windows Installer `multiString` value doesn't split on tabs - the engine's actual convention is the literal `[~]` sequence between entries. Reading the compiled `Registry` table's raw character codes one at a time (not just the rendered string, which *looked* like separate entries) showed `[~]` only at the very start and end, with a raw tab sitting between each pair - meaning the whole thing was being written as **one single registry string**, not five distinct `REG_MULTI_SZ` array entries. This means none of the five environment variables - not just `SqliteFilePath`, but `OUTOFTHEBOX_DATA_DIR`, `RootDirectory`, `BearerToken`, and the Kestrel port too - had ever actually been reaching the running process correctly since this line was first authored back in Section 17.9; it went unnoticed because no install had ever run far enough to prove any of it working end-to-end, and the standard "verify against the compiled table" check had only ever confirmed the row *contained the right text*, not that the text was *correctly encoded as multiple strings*. Fixed by switching to WiX's proper multi-entry authoring - five `<MultiString Value="..." />` child elements under one `<RegistryValue Type="multiString">` (the current element name; the similarly-named but deprecated v3 `MultiStringValue` was tried first and rejected by the compiler) - re-verified the same way, at the same raw-character-code level, this time finding `[~]` correctly between every entry and no stray tabs anywhere. **The dark theme itself (see the "Installer dark theme" decision below) was reversed on direct request** once the operator actually saw it running - "dark theme in WiX does not look good... let's move for a light style" - which simplified several of the fixes above in the process: `ConfigDlg`/`InvalidConfigDlg` dropped their custom Background/TextStyle entirely for the standard banner-strip-plus-plain-body convention (also fixing a real bug the dark version had - its near-white label text, chosen to read against the dark panel, was equally unreadable against the resulting plain white one), and `VerifyReadyThemedDlg` was removed outright in favor of the stock `VerifyReadyDlg`, since a light banner makes the original overlap problem moot. `banner-493x58.bmp`/`dialog-493x312.bmp` were regenerated light with the brand mark deliberately positioned clear of each dialog's own native stock text (left column for the dialog art, right strip for the banner - the two sit at opposite ends because their respective native text is native-anchored to opposite sides). Now shown as its own line under the (enlarged, 96x96) product logo, vertically centered against it as one block.

`install.ps1`/`upgrade.ps1` are removed entirely, superseded by the bootstrapper/MSI above.

**Process execution: `System.Diagnostics.Process` with `UseShellExecute = false`, arguments passed via `ArgumentList` (not a concatenated string).**
This guarantees the OS never invokes `cmd.exe`/shell parsing on the argument list — each array element becomes one literal argv entry to `dotnet.exe`, which is what the spec's "no shell interpretation" requirement depends on. Wire `OutputDataReceived`/`ErrorDataReceived` handlers so each line is forwarded to the output stream (below) as it is produced, instead of buffering to end-of-process.

**Git command execution: a second endpoint, `POST /run/git`, reusing the same process-running infrastructure generalized by executable.**
`ProcessRunRequest` gains an `Executable` field (`"dotnet"` or `"git"`); the class formerly named `DotnetProcessRunner` is generalized to `CliProcessRunner`, fixing the executable per call site rather than accepting it from the caller — `RunEndpoints`'s `POST /run` handler always passes `"dotnet"`, its new `POST /run/git` handler always passes `"git"`, so the caller's argument list still can never name an arbitrary executable, only arguments to whichever CLI that endpoint is for. This avoids a second, near-duplicate Channel/`OutputDataReceived`/tree-kill implementation for git, since the only thing that actually differs between the two endpoints is which literal string becomes argv[0] plus which capability spec governs its "no restrictions" behavior. Alternative considered: a fully generic `POST /run` accepting a caller-supplied executable name — rejected, because it would let a caller run any executable on the host (`cmd.exe`, `powershell.exe`, arbitrary binaries), which is exactly the shell-command-execution risk both `dotnet-command-execution` and `git-command-execution` explicitly exclude; fixing the executable server-side per endpoint keeps that guarantee literal and checkable in code review, not just a documented intention.

**Git and dotnet commands share one per-repo lock and one cancellation endpoint; artifact transfers don't participate in the lock.**
`RunRegistry` (Application.Concurrency) is unchanged in shape — it was already keyed by resolved repo root, not by command kind — but is now explicitly shared across both `POST /run` and `POST /run/git`: acquiring the lock for a `git` run blocks a `dotnet` run against the same repo and vice versa, since both mutate/read the same physical directory and neither should assume the other isn't concurrently touching it. `POST /run/{runId}/cancel` is likewise shared unchanged across both run kinds (and, per below, artifact transfers too) — cancellation was already keyed by run id, not by what's being cancelled. Artifact transfers deliberately do **not** call `RunRegistry.TryAcquire` — a transfer only reads files a prior command already produced, so serializing it behind the same lock a `dotnet build` holds would block a caller from fetching an artifact from a repo that's mid-build on something unrelated (e.g. a different project in a multi-project repo), for no correctness benefit; the trade-off (a caller could technically read a file mid-write) is accepted since the sbx-side workflow this supports is "run a command to completion, then fetch what it produced."

**Output delivery: Server-Sent Events (SSE) over the same HTTPS connection.**
The command-execution endpoint responds with `Content-Type: text/event-stream` and writes one SSE event per stdout/stderr line as `Process.OutputDataReceived`/`ErrorDataReceived` fire, then a final `done` event carrying the exit code once the process exits. Chosen over WebSocket because the caller (Claude Code in the sbx sandbox) has no persistent WS client — it shells out to a plain HTTP client (`curl -N` or equivalent) and reads output as it's flushed; SSE is a normal chunked HTTP response, needs no handshake, and passes through ordinary HTTP infrastructure. The named event types (`stdout`, `stderr`, `done`, `error`) give the caller unambiguous framing to tell a data line apart from the terminal exit-code event, which is what the "distinguish never-executed from completed" requirement in spec.md depends on. Alternative considered: raw chunked `text/plain` — rejected because it has no event boundaries, so the caller would have to guess where stdout/stderr/exit-code fields start and end.

**Execution timeout with process-tree kill; caller-overridable, server-clamped.**
The default timeout is 10 minutes, configured on the host. The caller may include an optional timeout in the request, which is used instead of the default for that run — the caller (Claude Code in the sbx sandbox) knows the shape of the command it's issuing (a quick `dotnet --version` vs. a large `dotnet test` run) better than a single host-wide default can. Whatever value is used (caller-supplied or default), it's clamped to a configured maximum (e.g. 60 minutes) before being applied, so a caller can shorten its effective timeout freely but can never request an effectively-unbounded one — this keeps the "runaway process exhausts host resources" risk bounded regardless of what a caller asks for. On timeout, kill the process (and child processes `dotnet` may spawn, via `Process.Kill(entireProcessTree: true)`), emit an `error` event with reason `timeout`, and close the stream. Without a timeout at all, a hung `dotnet test` run ties up a server thread/handle and an open connection indefinitely.

**Per-stream output is still size-capped.**
Even though output streams incrementally rather than buffering fully, cap total bytes emitted per execution (e.g. 5 MB); beyond that, stop forwarding lines, emit a truncation flag on the `done`/`error` event, and let the process keep running to completion (or be killed by the timeout) without holding unbounded memory for already-sent lines.

**Path confinement via canonicalization, not string prefix checks alone.**
Resolve the caller-supplied relative path against the configured root with `Path.GetFullPath`, then verify the result's full path starts with the root's full path plus a trailing separator (not just a string prefix, which would let `C:\repos-evil` pass a naive check against root `C:\repos`). Reject symlink/junction traversal by resolving the final path (`Directory.ResolveLinkTarget` or equivalent) before the containment check.

**Artifact transfer: `POST /artifacts`, two-level path confinement, run id issued before the body streams, no per-repo lock.**
Request body names `Repo` (resolved under the configured root exactly like `StartRunRequest.WorkingDirectory`) and `Path` (resolved under that *specific resolved repo directory*, using a second `PathConfinementPolicy.IsContained` check against the repo's own root rather than the service-wide root) — two applications of the same Domain rule, not two different mechanisms, so a request can escape neither the configured root nor the named repo. Chosen as `POST` (not `GET`, despite being conceptually a read) because it has a side effect worth being deliberate about — a history record is created — and because it needs to return an `X-Run-Id` header before the body streams, the same pattern already used by `POST /run`/`POST /run/git`; a GET endpoint with a side-effecting response is the kind of thing an eager proxy/prefetcher could trigger accidentally. The response body is the raw file bytes (`Results.File`/`PhysicalFile`-equivalent streaming, not SSE-framed) with the resolved file's content type, since a binary artifact has no natural line-oriented framing the way process stdout does. Missing-file and confinement-violation are distinct outcomes (not-found vs. rejected) so a caller can tell "wrong path" from "right path, nothing there yet."

**Auth: single shared bearer token from configuration, constant-time comparison.**
Read the expected token from an environment variable / configuration provider (never hardcoded). Compare using `CryptographicOperations.FixedTimeEquals` to avoid timing side-channels. Chosen over a full identity provider because there is exactly one trusted caller (the sbx sandbox) — a shared secret matches the actual trust model; anything heavier is unjustified complexity for v1.

**Transport: HTTPS required, bound to a specific interface/port.**
Because the credential and command arguments (and now, streamed output) cross a real network link between two machines (not loopback), the endpoint requires TLS — plain HTTP would leak the bearer token and command output to anyone on-path. Certificate can be a private/self-signed cert pinned by the sbx-side client for v1, since both endpoints are under the same operator's control (not public internet). Bind Kestrel to a specific port and, at the OS firewall level, restrict inbound connections on that port to the sbx sandbox's IP. Disable response buffering for the SSE endpoint so Kestrel flushes each event immediately rather than batching.

**Concurrency: parallel across repos, locked per repo via an in-memory registry.**
Maintain a `ConcurrentDictionary<string, RunInfo>` keyed by the canonicalized repo root (the same resolved path used for path confinement), where `RunInfo` holds the run id, the `Process` handle, and a `CancellationTokenSource`. On request start, atomically `TryAdd` the repo key; success acquires the lock and starts the process, failure means a run is already in flight for that repo and the new request is rejected immediately with 409-style conflict carrying the existing run's id. The entry is removed on any terminal state (completed, timed out, cancelled), releasing the repo for the next request. `TryAdd`'s atomicity is what prevents a race between two simultaneous requests for the same repo both believing they acquired the lock. Alternative considered: queue the second request and run it once the first finishes — rejected because it hides latency from the caller (a "run" call could silently block for an unrelated run's duration) and complicates cancellation semantics (cancel which one, the running or the queued?); an explicit reject-with-conflict keeps the caller in control, and the new cancellation API gives it a way to unblock a repo on purpose.

**Cancellation: run id assigned at start, cancel endpoint kills the process tree (or stops the transfer stream).**
Every accepted `dotnet`/`git`/transfer run is assigned a run id (e.g. a GUID) at the moment it's accepted — the repo lock is acquired for `dotnet`/`git` runs; an artifact transfer is registered without acquiring any lock — returned to the caller via an `X-Run-Id` response header emitted before the response body starts (headers can be flushed before a chunked body, so the caller has the id even though the body streams for the run's full duration). The same authenticated `POST /run/{runId}/cancel` endpoint, shared across those three REST-reachable run kinds, looks up the run id in the same registry; for a `dotnet`/`git` run it calls `Process.Kill(entireProcessTree: true)` — the same mechanism the timeout path already uses — which causes the in-flight SSE stream to observe process exit and emit a terminal `error` event with reason `cancelled`; for an artifact transfer it cancels the token driving the file stream, stopping the copy and marking the transfer's history record cancelled. Either way the registry entry is removed, releasing the repo lock where one was held. If the run id is unknown or already terminal — which, deliberately, includes any repository-clone run id, since those have no REST surface at all (see `specs/repository-management`) — the cancel endpoint returns 404 and touches nothing; cancelling an in-flight clone is instead a separate in-process Blazor action calling the same underlying `RunRegistry.TryCancel`, just never exposed over HTTP. Cancellation is therefore best-effort and reuses existing kill/terminal-event plumbing rather than introducing a second termination pathway per run kind.

**Persistence: SQLite via EF Core, one `Runs` table covering all five run kinds, write-through from the same start/terminal hooks as the registry.**
A single `Runs` table: `Id` (run id, PK), `Kind` (`DotnetCommand`/`GitCommand`/`ArtifactTransfer`/`RepositoryClone`/`RepositoryDelete`), `RepoPath`, `Arguments` (JSON-encoded array, nullable — populated for `DotnetCommand`/`GitCommand` only), `ArtifactPath` (nullable — populated for `ArtifactTransfer` only), `ArtifactSizeBytes` (nullable, set on a successful transfer's terminal update), `SourceUrl` (nullable — populated for `RepositoryClone` only), `StartedAt`, `CompletedAt` (nullable), `Outcome` (`Running`/`Completed`/`TimedOut`/`Cancelled`/`ValidationFailed`/`NotFound`/`AlreadyExists`/`Interrupted` — `NotFound` applies to `ArtifactTransfer` and `RepositoryDelete`; `AlreadyExists` applies only to `RepositoryClone`, when the target name is already taken), `ExitCode` (nullable, only meaningful for `DotnetCommand`/`GitCommand`/`RepositoryClone`, all three of which run a real process), `Stdout`, `Stderr`, `Truncated`. One table (not one per kind) keeps "list/filter/search history" a single query instead of a union across tables, matching the run-history spec's requirement that filtering/search work uniformly across kinds. A row is inserted with `Outcome = Running` at the same point the in-memory registry entry is created (repo lock acquired and process started for a command or clone; transfer or delete registered), and updated in place when the run reaches a terminal state — the same code path that removes the registry entry also writes the terminal row update, so there is one place that defines "a run is over," not two, for any kind. EF Core (over raw `Microsoft.Data.Sqlite`/Dapper) is chosen for its migration story (schema changes as the run record shape evolves) and because write volume is low (two writes per run: insert + one update) — ORM overhead is irrelevant at this scale. SQLite itself (over a client-server DB) is chosen because it's a single embedded file needing no separate service to install, run, secure, or back up, matching a single-host, single-writer deployment — and matching the "self-contained" packaging goal (see Packaging decisions below), it lives in the same per-machine data directory as configuration, untouched by binary upgrades. On service startup, any row still `Outcome = Running` from before the restart is reconciled to `Interrupted` (the in-memory registry that would confirm it's still running was lost on restart, so its true state is unknown) — this applies uniformly regardless of kind.

**History filtering and search: `IRunRepository` query method takes optional kind/outcome/repo filters plus a free-text term, translated to one parameterized SQL `WHERE` clause via EF Core LINQ, not separate query paths per filter combination.**
A single repository method (e.g. `ListAsync(RunQuery query)`, where `RunQuery` bundles `Kinds`, `Outcomes`, `Repo`, and `SearchText`, all optional) composes an EF Core `IQueryable` by conditionally `.Where()`-ing on each non-null filter, so any combination of filters (including none) is one code path rather than a combinatorial set of hand-written queries. Free-text search matches `RepoPath`, `Arguments` (as JSON text), and `ArtifactPath` via SQL `LIKE` — acceptable at this scale (no dedicated full-text index) given the table's expected size matches the already-accepted "no retention policy" growth profile, and a `LIKE` scan over indexed-enough row counts for a single-operator internal tool isn't a real performance concern. The dashboard's history view calls the same repository method the query API would, so there's exactly one place "what filters/search exist" is implemented.

**Dashboard: Blazor Server, backed by an in-process run-event bus for live updates + SQLite for history queries.**
The dashboard is a Blazor Server app hosted in the same ASP.NET Core process (no separate frontend project/build step, no SPA framework). A singleton `IRunEventBus` (in-process pub/sub — e.g. a `Channel<RunEvent>` fanned out to subscribers, or a plain C# event) is published to from the same code paths that already touch the run registry: run started (any kind), output line produced (`dotnet`/`git` runs only — a transfer has no stdout/stderr to publish), run reached terminal state (any kind). Blazor components for the current-status view subscribe to this bus on `OnInitialized`, call `InvokeAsync(StateHasChanged)` on relevant events, and unsubscribe on `Dispose` — this is what makes the dashboard "live" without polling. The history view instead queries the `Runs` table directly (via EF Core) since past runs don't change; it doesn't need the event bus. Chosen over a plain HTML+SSE dashboard (as sketched for command output) because Blazor Server's component model and built-in SignalR transport make a richer, multi-view UI (status list + history list + per-run detail) substantially less code than hand-rolling equivalent client-side JS/DOM updates, and the operator explicitly asked for "pleasant," which favors a real component-based UI over minimal hand-built HTML. Trade-off accepted: Blazor Server requires a persistent SignalR connection per open dashboard tab (WebSocket, or long-polling fallback) — acceptable given the same HTTPS port/firewall rule already carries the SSE traffic, and there's only ever one or a few operators, not many concurrent viewers.

**Dashboard auth: same shared bearer token, exchanged for an auth cookie via a login page.**
Blazor Server circuits don't naturally carry a bearer header per request the way the API does, so the dashboard has a small login page where the operator enters the same configured token; on success the server sets a standard ASP.NET Core auth cookie (validated the same way — `CryptographicOperations.FixedTimeEquals` against the configured value — just entered once per browser session instead of per request). This keeps a single credential as the entire trust boundary (per the existing auth decision) rather than introducing a second, separate dashboard credential.

**Dashboard theme: dark-only, no toggle.**
Ship a single dark CSS theme (no `prefers-color-scheme` branching, no toggle component) — the operator asked for dark-only, and skipping a light theme entirely removes a whole axis of UI work/testing for a one-operator internal tool.

**Brand mark: one image asset, reused everywhere, no separate design system.**
A single logo (a terminal-prompt `>` chevron on an orange-to-pink gradient box) is rendered once, at every resolution actually needed (multi-res `.ico` for the bootstrapper exe and MSI Add/Remove Programs icon, WixUI's fixed-dimension banner/dialog bitmaps, a small PNG for the bootstrapper's inline logo slot, and a PNG for the dashboard's favicon/header/login), rather than commissioning distinct art per surface — this is a one-operator internal tool, not a product with a design team, so "the same mark, consistently sized" is enough to make install and dashboard feel like the same product without justifying a broader branding investment. The dashboard's `--accent` CSS variable was retuned to the mark's own warm gradient color (previously an unrelated blue) specifically so the dashboard's accent and the installer's brand mark read as intentionally related, not coincidentally different products that happen to share a name.

**Dashboard restyle: extend the same brand tokens dark-theme-wide, not a redesign.**
On direct request ("presentation sells a product... invest enough effort into this, but do not over-do it"), the dashboard's existing dark palette (`--bg`/`--bg-raised`/`--border`/`--text`) was kept exactly as-is - the brief was "follow the logo's design ideas," not "replace the theme" - and the logo's two gradient tones were threaded through as CSS-only additions: a warm `--gradient-brand` (orange→pink) for the one primary-action button style, active/hover nav underlines, and the small accent bar under every page `<h1>`; a cool `--brand-violet` used once, for the login page's hero glow, so it stays a secondary accent rather than competing with the warm one. Run-kind badges (`kind-dotnetcommand`/`kind-gitcommand`/etc.) got distinct low-saturation tinted pills for at-a-glance scanning of a mixed run list — the one place color communicates information rather than just branding. Chart.js's own light-theme defaults (`Chart.defaults.color`, grid line color) were overridden globally in `chart-interop.js`, since left alone its default tick/legend text is barely visible against a dark background — a real, previously-unnoticed readability gap, not a stylistic choice; the two chart series (CPU/RAM) were given the same warm/cool brand split as everything else. A handful of previously entirely unstyled elements (the `<dl>`/`<dt>`/<dd>` stat blocks on the repo/run detail pages, the "Clear filters"/"Start clone" buttons, `<button>` in general) were brought up to the same button/card language for consistency — these weren't a deliberate prior design choice, just gaps. Two things were deliberately *not* done, to keep this a restyle rather than a redesign: no icon library, no light theme, no animation beyond simple hover/focus transitions; and a since-reverted attempt to color-code the Repos view's Active/Idle badge was dropped when it collided with `ReposComponentTests`' exact-substring markup assertion (`kind-badge">Active`) - not worth loosening a real test invariant for a cosmetic nicety. Verified live: `dotnet run` against a real (temporary) data directory, logged in via the real cookie flow, and fetched Status/History/Repos over HTTP to confirm every page still renders 200 with the expected markup - not just "the build succeeded" or bUnit alone, since bUnit's simulated render pipeline doesn't catch CSS-loading or real-cookie-auth issues. 124/124 UnitTests (including all bUnit component tests), 5/5 ArchitectureTests unchanged.

**Installer dark theme: "dark chrome, light inputs," and only where WiX actually allows it.**
On direct follow-up request ("make the installer style dark like the dashboard"), scoped upfront via a direct question to the user rather than guessing, because there's a real, hard ceiling here unlike the dashboard: MSI dialogs are genuine Win32 dialogs, and Edit/PushButton/CheckBox controls are OS-drawn - there is no MSI table for "edit box background color," so pixel parity with the Blazor dashboard is categorically not achievable without abandoning native MSI UI for a fully custom Bootstrapper Application (rejected as disproportionate, same reasoning as every other "is this worth the tooling investment" call in this section). The user picked the offered middle option: darken every reachable dialog's background/static text, leave native input controls native. `ConfigDlg`/`InvalidConfigDlg` (fully owned) got the full treatment - a full-dialog background `Bitmap` control (first-declared, so it paints behind everything else), three `TextStyle` rows referencing `dashboard.css`'s own text colors via MSI's `{\StyleId}` prefix mechanism, `Transparent="yes"` on every static Text control. `WelcomeDlg`/`ExitDialog` needed nothing - WixUI_Minimal's "dialog style" layout already covers ~90% of their area with the existing branded `WixUIDialogBmp`. **A real, tried-and-failed attempt to extend this to WixUI_Minimal's own stock dialogs** (`CancelDlg`, `ProgressDlg`) surfaced a genuine WiX constraint worth remembering: redeclaring a `<Dialog>`/`<Control>` with the same Id as one pulled in from a referenced extension's wixlib is a hard `WIX0091` duplicate-symbol linker error, not a supported override - there is no partial-override mechanism for an individual stock dialog short of hand-authoring the entire dialog set. Given that, and given `VerifyReadyDlg` alone has ~25 controls and ~40 `ControlEvent` rows spanning disk-space and modify/repair/update states this installer never exposes a path to, every other stock dialog keeps its default light styling - not worth the regression risk for a screen seen for a few seconds. **This specific call was revisited later** (see the "second real-machine round" paragraph below) once `VerifyReadyDlg`'s stock black title text turned out to sit directly on top of the branded dark banner, unreadably - unlike `CancelDlg`/`ProgressDlg`, this dialog is reached on *every* install, and the operator explicitly asked for the text fixed rather than the banner changed, so the regression-risk calculus tipped the other way for this one dialog specifically. `CancelDlg`/`ProgressDlg` and the rest remain untouched - the reasoning above still applies to them. The background art itself needed its own real fix: `System.Drawing`'s `PathGradientBrush` showed visible concentric banding at the radii/opacities in play (a genuine GDI+ limitation), worked around by compositing many thin low-alpha `FillEllipse` layers instead of a single interpolated gradient. Verified against the compiled MSI via the Windows Installer COM API (`Binary`/`TextStyle`/`Control` tables, including a sanity check that `CancelDlg` was left exactly stock after the reverted override attempt) and `wix msi validate`.

**Product display name: "Out of the Box" (spaced) everywhere an operator reads it; "OutOfTheBox" (identifier) everywhere code/scripts reference it.**
On direct request, after the operator noticed the installer showing "OutOfTheBox" as a raw PascalCase identifier rather than a name a human would actually write. The dividing line: anything visually *displayed* to an operator as the product's name - `Package`/`Bundle`/@Name (which cascades automatically through every stock WixUI_Minimal dialog via the built-in `[ProductName]` substitution: Welcome/VerifyReady/Progress/Exit/Cancel text, Programs and Features, the taskbar/window title), `ServiceInstall`/@DisplayName (services.msc; not @Name, the actual SCM service key other things reference by exact string match), the firewall rule's own @Name (the Windows Firewall UI's rule list), `ConfigDlg`/`InvalidConfigDlg`'s own Title/Text (now also just `[ProductName]` references rather than a second hardcoded copy), the dashboard's header/login/page-title text, and the `/version` endpoint's `name` field (kept in sync with the dashboard by design, per the "sourced from the same value" decision above) - all became "Out of the Box." Everything a script, another human-authored config file, or code parses/matches by exact string - the `OutOfTheBox.*` project/namespace names, `SOFTWARE\OutOfTheBox`/`Services\OutOfTheBox` registry paths, the `OUTOFTHEBOX_DATA_DIR`/`OutOfTheBox__*` environment variable names, `svc-outofthebox`, `INSTALLFOLDER`'s actual `C:\Program Files\OutOfTheBox` path, every file name including `OutOfTheBoxSetup.exe` - stayed exactly as-is; renaming any of those would be an unrelated, much riskier structural change for zero benefit (nobody reads a registry key path as "the product's name"). The dashboard's own copy lives in one place (`VersionInfo.DisplayName`, a single constant every page/endpoint reads) rather than being duplicated as a literal string per file, the same "one source of truth" reasoning `VersionInfo.Current` already existed for.

This first pass missed the two WixUI brand bitmaps (`banner-493x58.bmp`, `dialog-493x312.bmp`): unlike every other case above, "OutOfTheBox" there is baked into the image's pixels, not a property an MSI dialog control substitutes at runtime, so `[ProductName]` cascading never touched it. Missed because only the dashboard's small `logo.png` (a pure graphic mark, no text) was checked before generalizing to every brand asset; caught by the operator looking at the actual installer ("dialog-493x312 still contains the internal name"). Fixed by regenerating both bitmaps - same gradient, same composited `logo-96.png` icon, "Out of the Box" redrawn in its place - rather than trying to patch just the text region, since a full regeneration is no harder and carries no risk of a visible seam. The lesson generalizes: a "does X appear anywhere in the UI" audit needs to check every distinct asset individually, not extrapolate from the first one that happens to be clean.

**Status view: processes grouped under their owning run, every run row carries a kind badge.**
The spawned-process list is not one global flat table; each in-flight command run's card/row expands to show only the processes in that run's own tree (an artifact transfer's or a delete's card never has a process sublist, since neither spawns one), keeping the per-run correspondence in the requirement obvious at a glance and keeping any single run's list short. Every run row/card across Status and History carries a kind badge (`dotnet`/`git`/`artifact`/`clone`/`delete`), since a mixed list of five run kinds needs to be visually distinguishable at a glance, not just inferable from the presence/absence of fields. (See the "Dashboard navigation" decision below for the view/subpage structure this sits inside.)

**History filter/search UI: controlled inputs bound to the same `RunQuery` the repository method takes, debounced text search, no separate "advanced search" page.**
Kind is a multi-select (checkboxes or a multi-select dropdown, since an operator might want "dotnet and git, not artifact transfers"); outcome and repo are single-value dropdowns/text inputs; the free-text box is debounced (a few hundred ms) before re-querying, rather than firing a query per keystroke. All four bind into one `RunQuery` component state object that's passed to `IRunRepository.ListAsync` on every change — the same method and the same query shape the backend list endpoint uses (see the History filtering and search decision above), so there's no separate "browser-side filtering of an already-fetched page" logic to keep in sync with the server-side one.

**Host CPU sampling: `System.Diagnostics.PerformanceCounter` against the `Processor` category.**
Read `\Processor(_Total)\% Processor Time` for the total figure and `\Processor(N)\% Processor Time` for each logical core (`N` from `0` to `Environment.ProcessorCount - 1`). `PerformanceCounter` is Windows-only, which is fine (this service is Windows-only throughout), and is the documented, supported way to read these counters without P/Invoke. Known quirk: a freshly-constructed `PerformanceCounter`'s first `NextValue()` call always returns `0` (no prior sample to diff against) — the background sampler must discard the first reading per counter rather than publish it as real data. Alternative considered: `NtQuerySystemInformation`/`GetSystemTimes` P/Invoke — more brittle (partly undocumented for per-core), rejected in favor of the supported counter API.

**Host RAM: `GlobalMemoryStatusEx` P/Invoke; service RAM: `Process.GetCurrentProcess().WorkingSet64`.**
`GlobalMemoryStatusEx` (a single Win32 call) returns total and available physical memory directly, cheaper and more immediate than a `PerformanceCounter` (no discard-first-sample quirk). The service's own memory figure is just its own `WorkingSet64` — no extra mechanism needed.

**Spawned-process tree discovery: WMI (`Win32_Process`) walked by `ParentProcessId`, rooted at each tracked run's `Process.Id`.**
`System.Diagnostics.Process` doesn't expose a process's parent or children directly. Query `Win32_Process` (via the `System.Management` package) for `ProcessId`/`ParentProcessId`/`Name`, and recursively collect descendants starting from each in-flight run's root PID (already known from the `RunInfo` registry entry) — the same tree this walk discovers is what `Process.Kill(entireProcessTree: true)` already tears down internally for the timeout/cancel paths, so the dashboard's tree view and the kill mechanics stay conceptually aligned. Alternative considered: `CreateToolhelp32Snapshot`/`Process32Next` P/Invoke — functionally similar, more code, rejected in favor of the managed WMI wrapper since polling every few seconds for a handful of processes is not performance-sensitive enough to justify avoiding WMI's overhead.

**Per-process CPU%: manual delta-sampling of `Process.TotalProcessorTime`, not a WMI perf class.**
For each PID in a discovered tree, keep the last-sampled `TotalProcessorTime` and timestamp; on the next tick, `CPU% = (ΔTotalProcessorTime / (Δwallclock × Environment.ProcessorCount)) × 100`. This is the standard .NET technique for per-process CPU and avoids WMI instance-name disambiguation problems that `Win32_PerfFormattedData_PerfProc_Process` has when multiple processes share a name (e.g. two `dotnet.exe`). RAM per process is `Process.GetProcessById(pid).WorkingSet64`, sampled at the same tick.

**Resource sampling cadence: a single background `PeriodicTimer`, fanned out through an `IResourceEventBus`, mirroring the run-event pattern.**
A hosted background service ticks every few seconds (configurable, default matches the requirement's "at least every few seconds"), samples host CPU/RAM, service RAM, and each tracked run's process tree in one pass, and publishes a snapshot to an `IResourceEventBus` that dashboard components subscribe to (same subscribe/`StateHasChanged`/unsubscribe pattern as `IRunEventBus`) — reusing the established live-update mechanism rather than inventing a second one, and keeping the sampling itself off the SignalR/request path.

**Kill action: in-process Blazor method call, not a REST endpoint.**
Unlike run cancellation (which must be reachable by the remote sbx caller, a non-browser HTTP client, and is therefore a real `POST /run/{runId}/cancel` endpoint), the process-kill button is only ever triggered by an operator already inside an authenticated Blazor circuit — the component's click handler calls an injected `IProcessMonitor.KillAsync(pid)` service method directly, server-side, with no additional network endpoint. This keeps the network-facing authenticated surface exactly as large as it otherwise would be (`POST /run`, `POST /run/git`, `POST /artifacts`, `POST /run/{runId}/cancel` — four endpoints total) rather than adding a fifth; repository management (below) follows this same precedent for the same reason.

**Repository management (list/clone/delete): in-process Blazor calls into `IRepositoryManager`, the same pattern as the kill action — not REST endpoints.**
The sbx sandbox caller never needs to clone or delete a repository (it works with repos that already exist); only the human operator does, from inside an authenticated Blazor circuit. Following the exact precedent set by the kill action above, `IRepositoryManager.CloneAsync(...)`/`DeleteAsync(...)`/`ListAsync()` are called directly from Blazor component code-behind, server-side, with no new bearer-token HTTP endpoint. This is a deliberate, explicit boundary (see `specs/repository-management`'s "reachable only from the authenticated dashboard" requirement): it keeps the sbx-facing API surface exactly the four endpoints it already has (`dotnet` run, `git` run, artifact transfer, cancel) and avoids having to reason about what it would mean for a remote, non-operator caller to be able to delete a repository.

**Repository clone reuses the generalized `CliProcessRunner` and `RunRegistry`, exactly like a `git` run — just triggered from Blazor instead of an HTTP handler.**
`IRepositoryManager.CloneAsync(url, name)` resolves `name` under the configured root (via the same confinement primitive, rejecting escape or an already-existing target), calls `RunRegistry.TryAcquire` keyed on that resolved (not-yet-existing) path — `RunRegistry` doesn't care whether the directory exists, only that the key string is unique, so no change to its contract is needed — then runs `CliProcessRunner` with `Executable = "git"` and `Arguments = ["clone", url, resolvedPath]`, publishing to `IRunEventBus`/writing to the `Runs` table exactly as `POST /run/git` does, with `Kind = RepositoryClone`. The only difference from a normal `git` run is the caller (a Blazor component method, not `RunEndpoints`) and that the target doesn't exist until the clone succeeds. This reuse is why clone shows up in Status/History "for free," satisfying the live-dashboard-visibility requirement without new plumbing.

**Repository delete: a plain recursive filesystem delete, still lock-guarded through `RunRegistry` for correctness, not just as a formality.**
`IRepositoryManager.DeleteAsync(name)` resolves and confines `name` the same way, calls `RunRegistry.TryAcquire` for that repo (rejecting with a conflict if a `dotnet`/`git` run or another clone/delete already holds it — the same "reject, don't queue" behavior as everywhere else), then calls `Directory.Delete(path, recursive: true)`, and releases the lock in a `finally` regardless of outcome. Acquiring the lock (not just checking whether it's held) closes the TOCTOU race a check-then-act approach would have — a command starting in the gap between "checked, repo was idle" and "delete actually ran" would otherwise be deleted out from under. Recorded with `Kind = RepositoryDelete`; since there's no real "in-flight" phase worth streaming (a directory delete, even a large one, doesn't produce incremental output the way a process does), the run is still assigned an id and inserted `Running` then immediately updated terminal, purely so it appears in history and briefly in Status like everything else, not because it needs SSE-style incremental delivery.

**Repository enumeration: top-level directories directly under the configured root, no metadata file, no separate registry.**
A "repository" is defined structurally, not by an explicit list the operator maintains — every immediate child directory of `ServiceOptions.RootDirectory` is one. This matches how `dotnet-command-execution`'s working-directory resolution already treats a "repo-relative path" and needs no new configuration or persisted list to keep in sync with what's actually on disk; listing repositories is just `Directory.EnumerateDirectories(root, "*", SearchOption.TopDirectoryOnly)`.

**Repository stats: size and git status sampled on a slow background cadence plus event-driven recompute, not the fast few-second resource-sampler loop; "active" is free, sourced live from the existing lock/event-bus state.**
Total directory size (a full recursive `EnumerateFiles`/sum-of-`Length` walk) and git status (`git rev-parse --abbrev-ref HEAD`, `git status --porcelain`, and an ahead/behind count against the upstream if one is configured — internal, unstreamed, quick invocations of the same `git.exe`, not modeled as a `Run`) are both IO-heavier and lower-value-per-sample than CPU/RAM, so they're driven by a separate, slower `PeriodicTimer` (e.g. every 60s) rather than piggybacking on `IResourceSampler`'s few-second cadence. Both are also recomputed immediately whenever a run against that specific repo (of any kind) reaches a terminal state — the natural moment its state might have changed — so a `git pull` or a `dotnet build` that adds `bin`/`obj` output is reflected promptly rather than waiting up to 60s. "Active" needs no sampling at all: it's just "does `RunRegistry` currently hold this repo's key," which is already exactly what drives `IRunEventBus`'s run-started/run-terminal publishes, so the Repos view's active/idle indicator subscribes to the same bus Status already does.

**Dashboard navigation: three top-level views (Status/History/Repos) plus routable per-item subpages (`/history/{runId}`, `/repos/{name}`), not modal dialogs or inline-expanding rows.**
Each subpage is its own Blazor `@page` route with a route parameter, not a `<Modal>`/accordion-expansion component — giving each a bookmarkable/shareable URL and a simpler component boundary (a list component never needs to know how to render full run/repo detail; it only links to the subpage that does). This is what keeps a list view from becoming the "one dense page" the operator explicitly asked to avoid: a list row shows only identifying summary fields, and anything more specific is a navigation away.

**Dashboard branding: service name and running version shown in a persistent header/footer, sourced from the same value `/version` reports.**
A small shared layout component (outside the three top-level view components, present on every route including subpages) reads the version once (from `Assembly.GetExecutingAssembly().GetCustomAttribute<AssemblyInformationalVersionAttribute>()`, populated from the `Directory.Build.props` `<Version>` at build time) and renders "Out of the Box v{version}" — trivial, but doing it in the shared layout rather than per-view avoids repeating it three times. ("Out of the Box" is the product's human-readable display name; "OutOfTheBox" without spaces is the codebase/repo/file-name identifier - see the Product display name decision below.)

**Versioning: standard SemVer, set once via a single `<Version>` in `Directory.Build.props`, starting directly at `1.0.0` — no `0.x` pre-release versions, and no incremental bumping through development.**
Per explicit instruction, this project skips the usual "start at 0.1.0 and work up" convention entirely: `<Version>1.0.0</Version>` is added to `Directory.Build.props` once (a one-line, one-time task, not something touched every section) and stays the version for the entirety of v1 development and its eventual first release — there's no process defined here for when/how to bump it for a hypothetical v1.1.0 or v2.0.0, since that's a future-release concern out of scope for getting v1 built. `Directory.Build.props` is the single source of truth (not a separate `version.json` or a hardcoded string in `Program.cs`) so every project's assembly metadata picks it up automatically via the standard MSBuild `Version`→`AssemblyVersion`/`FileVersion`/`InformationalVersion` derivation, and both `/version` and the dashboard's branding element read it via reflection rather than each hardcoding it separately.

**Kill scope enforcement: verify the target PID is inside a currently-tracked process tree before killing, always, server-side.**
`IProcessMonitor.KillAsync(pid)` re-walks (or checks against the last-sampled) tree membership for `pid` against the set of currently tracked run root PIDs before calling `Process.GetProcessById(pid).Kill(entireProcessTree: true)`; if `pid` isn't found under any tracked root, the call is rejected. This check happens in the server-side service method itself, not just in the UI (the UI simply shouldn't offer buttons for out-of-scope processes) — because the enforcement point spec.md requires ("SHALL reject a termination request for any other process id, regardless of what id is supplied") is about the action being scoped, not about hiding the button. Killing the target with `entireProcessTree: true` (not just the single PID) is what satisfies "terminate that process together with its own descendants."

**Per-run aggregation: sum already-sampled per-process figures across each run's tree, computed in the same sampler tick.**
Each `PeriodicTimer` tick already computes per-process CPU%/RAM for every PID in a run's discovered tree (for the process list). The run's aggregate CPU% and RAM are just the sum of those already-computed per-process values for that tick — no separate sampling mechanism, so aggregation is "free" given the process-level sampling already required for the process list.

**Artifact transfers get a resource-sample series too, sourced from host-level figures instead of a process-tree aggregate.**
A `dotnet`/`git` run's `RunResourceSample` rows are the sum of its spawned process tree's CPU/RAM at each tick (see Per-run aggregation, below) — but a transfer spawns no child process, so there's nothing to sum. Rather than leaving transfers with no resource series at all (which would make their history detail view inconsistent with every other run kind, and the dashboard would need a special case to hide the graph for one kind), each sampler tick that overlaps an in-flight transfer writes a `RunResourceSample` row for it using that tick's already-computed *host-level* total CPU%/RAM (the same figures already shown in the Status header), not a per-transfer-attributed figure — there is no way to isolate "CPU used specifically by this file copy" without kernel-level per-I/O-operation accounting, which is out of scope. This is a deliberate approximation: a transfer's graph shows "how busy was the host while this transfer ran," not "how much this transfer cost," and that distinction is documented rather than silently glossed over (see Risks).

**Resource sample persistence: new `RunResourceSamples` table, one row per run per tick, written by the same background sampler.**
`RunResourceSamples(RunId FK, Timestamp, CpuPercent, RamBytes)`, indexed on `(RunId, Timestamp)`. On every sampler tick, for each in-flight run, insert one row with that tick's aggregate CPU%/RAM (the same aggregate computed above) via EF Core — write volume is one row per in-flight run per tick (e.g. one run sampled every 3 seconds is ~20 rows/minute), which is low enough not to need batching given SQLite's WAL mode already in use. Samples for a run stop being written once it reaches a terminal state; the complete set of rows for that `RunId`, ordered by `Timestamp`, is the "full graph" data for history. No downsampling/compaction is applied (raw samples kept as-is) — simplest correct behavior for v1, revisited only if the table's growth (see Risks) becomes a real problem.

**Live rolling window: an in-memory circular buffer per series (host, each in-flight run), independent of the persisted series.**
The Status view's live graphs read from a small in-memory ring buffer (capacity = 10 minutes ÷ sample interval, e.g. 200 points at 3s) maintained alongside the sampler tick — not from SQLite. This keeps live rendering fast (no DB round trip per tick) and decouples "what the live graph shows" (bounded 10-minute window, discarding older in-memory points) from "what gets persisted" (the sampler still writes every tick to `RunResourceSamples` regardless of what's evicted from the live buffer). History's "full graph" reads the complete persisted series instead of this buffer.

**Charting: Chart.js, vendored locally in `Presentation`'s `wwwroot`, via a thin JS interop wrapper — not a CDN reference, not a Blazor-native charting library.**
Ship `chart.js` as a static asset under `Presentation`'s `wwwroot` (downloaded once at build time and committed/restored like any other static asset, not fetched from a CDN at runtime) — consistent with "self-contained" meaning no runtime dependency on internet access. Because `Presentation` is a Razor Class Library, ASP.NET Core's static web assets feature automatically composes its `wwwroot` into `Host`'s publish output at build/publish time (no manual copy step in the project itself) — but the physical files still end up as loose files alongside `Host`'s `.exe` in the publish output (`PublishSingleFile` bundles managed/native assemblies, not static web assets), so the install directory is a small folder, not literally one file, and the MSI's file component list must still cover the whole publish output, not just the exe. A minimal `IJSRuntime` wrapper creates one chart instance per graph and pushes new points via `chart.data.datasets[0].data.push(...); chart.update('none')` on each tick, rather than recreating the chart every tick. Chart.js is chosen over a hand-rolled SVG sparkline component for visual quality (gradients, tooltips, axis labels, smooth updates) at a fraction of the implementation effort "nice looking graphs" would otherwise take; a pure-Blazor charting NuGet package was also considered and rejected only because Chart.js is better documented and more broadly proven than the current crop of Blazor-native chart libraries.

**Chart rendering is lazy: only mounted for a run once its card is expanded (or its history detail is opened).**
To keep "don't overload the dashboard" true even with several concurrent in-flight runs, a run's live chart component isn't instantiated (no JS interop calls, no `IResourceEventBus` subscription for that run's series) until the operator expands that run's card. Host-level graphs (always visible in the Status header) are the only charts always live.

**Solution format: `.slnx`, not classic `.sln`.**
`.slnx` is the newer XML-based solution format; confirmed working in the operator's Rider (opens and builds cleanly). Alternative considered: classic `.sln` — works everywhere but wasn't what was asked for, and isn't needed as a fallback given Rider support is confirmed.

**Solution folders: only one, "Tests" — the five architecture projects sit unfoldered at the solution root; physical layout is flat, one level under `src/`/`tests/`, with no layer-name or test-type wrapper directories.**
`src/OutOfTheBox.Domain/`, `src/OutOfTheBox.Application/`, `src/OutOfTheBox.Infrastructure/`, `src/OutOfTheBox.Presentation/`, `src/OutOfTheBox.Host/` — each project sits directly under `src/`, not under an extra `src/<LayerName>/` grouping directory. The project's own name already says which layer it is (`OutOfTheBox.Domain`, not just `Domain`); a wrapping directory of the same name is pure duplication, and it's not what any of the common Clean Architecture reference layouts (Ardalis', Jason Taylor's templates) do — both keep `src/` flat. Same reasoning for `tests/`: `tests/OutOfTheBox.UnitTests/`, `tests/OutOfTheBox.BehaviorTests/`, `tests/OutOfTheBox.ArchitectureTests/` sit flat under `tests/`, grouped only in the `.slnx` under a single `Tests` solution folder (an IDE-only, virtual grouping — physical layout doesn't need to mirror it, which is the whole point of solution folders existing separately from directories). `tests/Fixtures/` keeps its own subdirectory since it's categorically different (external-repo simulators, not this project's own test projects) and was never solution-registered anyway. This corrects the original version of this decision, which said the physical layout "matches [the solution folders] 1:1" but was actually implemented one level deeper than that (`src/Domain/OutOfTheBox.Domain/`, `tests/UnitTests/OutOfTheBox.UnitTests/`) — flattened after review.

**Test project layout: `UnitTests` and `BehaviorTests`, plus checked-in fixture projects, all under the `.slnx`'s `Tests` folder — except the fixtures themselves, which are deliberately *not* registered in the `.slnx`.**
`UnitTests` targets Domain and Application logic almost exclusively (that's the whole point of the layering — most of what's worth unit-testing needs no EF Core/WMI/PerformanceCounter/Kestrel), organized internally into `Domain/`, `Application/`, and `Infrastructure/` folders mirroring the layer under test; a handful of Infrastructure-layer tests use a real SQLite `:memory:` connection (not EF Core's InMemory provider, which doesn't exercise real SQL/migrations) rather than a fake. Since `UnitTests` references `Infrastructure` (Windows-only), and `BehaviorTests`/`ArchitectureTests` reference `Host`/`Infrastructure` too, all three test projects target `net10.0-windows` like the projects they exercise — only `Domain`, `Application`, and `Presentation` themselves stay plain `net10.0`. `BehaviorTests` exercises the real ASP.NET Core pipeline through `WebApplicationFactory<Program>`/`TestServer` against `Host` (the executable with the actual `Program` entry point, now that composition lives there rather than in `Presentation`), including genuinely spawning `dotnet.exe` child processes (that's the behavior under test), but against small checked-in fixture projects (`Tests/Fixtures/`: one passing test, one failing test, one intentionally-hanging test) rather than large real repos, keeping the suite fast and deterministic. The fixtures are plain standalone `.csproj`s on disk, not added as `<Project>` entries in the `.slnx` — they're targets the service spawns `dotnet` against, not test projects of *this* repo, and a failing/hanging test inside one would otherwise break `dotnet test` on the main solution if it were solution-registered.

**Unit test framework: xUnit.** The de facto modern .NET default, first-class `dotnet test` support with no separate runner, and what the chosen BDD tooling (below) integrates with most smoothly. Alternative considered: NUnit/MSTest — no material advantage here, xUnit chosen for ecosystem consistency.

**BDD framework: Reqnroll (Gherkin `.feature` files, xUnit-backed), not SpecFlow.** Reqnroll is the actively-maintained open-source continuation of SpecFlow (SpecFlow's own governance/licensing shifted toward a commercial model) and works via plain `dotnet build`/`dotnet test` — no Visual Studio dependency, confirmed — which is a hard requirement here. Each capability gets one `.feature` file whose scenarios are transcribed directly from that capability's spec.md `#### Scenario:` (WHEN/THEN) blocks into Gherkin (Given/When/Then), giving direct, checkable traceability from an openspec requirement to an executable test rather than a parallel, potentially-drifting test-only description of the same behavior. Alternative considered: hand-rolled Given/When/Then extension methods over plain xUnit (no separate Gherkin layer) — rejected because it loses the plain-text scenario file that doubles as documentation and the direct spec-to-feature-file correspondence.

**Windows-only API surface: target `Infrastructure` and `Host` `net10.0-windows` (or annotate with `[SupportedOSPlatform("windows")]`); `Domain`, `Application`, and `Presentation` stay plain `net10.0`.**
`PerformanceCounter`, WMI, and `GlobalMemoryStatusEx` live entirely in `Infrastructure` (behind Application's ports); `UseWindowsService()` lives in `Host`. `Presentation` itself — Blazor components, endpoint-mapping extension methods, auth middleware — never calls a Windows-only API directly, so it has no reason to be platform-tagged. Tagging only the two projects that actually need it makes the CA1416 platform-compatibility analyzer meaningful there instead of blanket-suppressed everywhere, and keeps `Presentation` genuinely portable in principle even though this deployment will only ever run on Windows.

**Architecture enforcement: `OutOfTheBox.ArchitectureTests` using NetArchTest.Rules, part of `dotnet test`.**
Encodes the Architecture section's dependency rules as executable assertions instead of relying on code review to catch drift:
- `Domain` has no dependency on `Application`, `Infrastructure`, `Presentation`, or `Host`, and no dependency on any `Microsoft.AspNetCore.*`, `Microsoft.EntityFrameworkCore.*`, `System.Management`, or `System.Diagnostics.PerformanceCounter` namespace.
- `Application` has no dependency on `Infrastructure`, `Presentation`, or `Host`.
- `Infrastructure` has no dependency on `Presentation` or `Host`.
- `Presentation` has no dependency on `Infrastructure` or `Host` — no exception, since composition now lives entirely in `Host`.
Each rule is an ordinary xUnit `[Fact]` inside `ArchitectureTests`, so a violation fails `dotnet test` exactly like any other broken test — nothing extra to remember to run. `Host` itself is deliberately excluded from these rules — it's expected to reference everything, that's its entire purpose.

**Code-quality baseline: nullable reference types + `GenerateDocumentationFile` enabled solution-wide; missing public-API doc comments fail the build.**
Every project sets `<Nullable>enable</Nullable>`; `<GenerateDocumentationFile>true</GenerateDocumentationFile>` plus treating the missing-XML-doc-comment warning (`CS1591`) as an error means a public type or member without a `///` doc comment fails `dotnet build`, not just a linter suggestion someone can ignore — this is what makes "public APIs need to be fully documented" a build gate rather than a style guideline. Other "common clean code" concerns (small methods, single responsibility, meaningful names, no magic numbers) are enforced the ordinary way — code review plus the .NET SDK's own bundled analyzers/`.editorconfig` (see below) — rather than a bespoke tool, since a purpose-built service at this scale doesn't need much beyond what already ships in the box.

**`.editorconfig` at the repo root: formatting + a handful of C# style conventions, all at `:suggestion` severity.**
Charset/EOL/indentation/trailing-whitespace basics for every file type, plus C# conventions (`var` preference, file-scoped namespaces, expression-bodied members where they fit on one line, `_camelCase` private fields) that match what's already used throughout the codebase — codifying existing practice, not introducing new rules. Deliberately `:suggestion`, not `:error` or `:warning` promoted to build-breaking: `CS1591` (doc comments) is already a hard build gate via `Directory.Build.props`, and stacking a second unrelated style-enforcement mechanism on top would be redundant ceremony for a project this size: IDE-level nudges are enough for formatting/naming, only the doc-comment rule needed to be a build gate.

**Central Package Management (`Directory.Packages.props`): every package version pinned once at the repo root.**
All nine third-party package IDs used anywhere in the repo (`xunit`, `Microsoft.NET.Test.Sdk`, `Reqnroll.xUnit`, `NetArchTest.Rules`, `Microsoft.AspNetCore.Mvc.Testing`, `Microsoft.Extensions.Options`, `Microsoft.Extensions.Hosting.WindowsServices`, `coverlet.collector`, `xunit.runner.visualstudio`) are declared once as `<PackageVersion>` entries; every project's `<PackageReference>` drops its `Version` attribute and gets it from there. Applies repo-wide via MSBuild's directory-walk-up auto-import, including `tests/Fixtures/` even though those projects aren't solution-registered — CPM doesn't care about `.slnx` membership, only physical location under the repo root, so their `PackageReference`s needed the same `Version`-attribute removal too, once the shared versions were centralized. Chosen because three test projects (`UnitTests`, `BehaviorTests`, `ArchitectureTests`) plus three fixture projects were already redeclaring the identical `xunit`/`Microsoft.NET.Test.Sdk`/`coverlet.collector`/`xunit.runner.visualstudio` versions independently — a straightforward version-drift risk as more test projects get added in later sections, with no corresponding benefit (nothing here needs different test-infra versions per project).

**Centralized build output (`Directory.Build.props`: `UseArtifactsOutput` + a pinned `ArtifactsPath`), instead of a `bin/`/`obj/` pair inside every project directory.**
Every project's build output lands under one `artifacts/` directory at the repo root (`artifacts/bin/<ProjectName>/debug/`, `artifacts/obj/<ProjectName>/`, ...) via the .NET SDK's built-in centralized-output feature, rather than each of the eleven project directories (five `src/`, three `tests/`, three `tests/Fixtures/`) growing its own `bin/`/`obj/`. `ArtifactsPath` is set explicitly (`$(MSBuildThisFileDirectory)artifacts` in the root `Directory.Build.props`) rather than left to the feature's own default inference: `tests/Directory.Build.props` is itself a second `Directory.Build.props` file (it imports the root one, then adds the `CS1591` `NoWarn` for test projects), and the SDK's default `ArtifactsPath` computation anchors to the *nearest* `Directory.Build.props` it finds walking up from a project, not the one that actually sets `UseArtifactsOutput` — without the explicit pin, the three test projects ended up with their own separate `tests/artifacts/`, splitting output across two locations instead of unifying it. Applies to `tests/Fixtures/` too, the same way CPM already does (directory walk-up doesn't care about `.slnx` membership). One `rm -rf artifacts` now cleans every project's output at once, and the repo root itself stays free of eleven scattered `bin`/`obj` pairs. `bin/`/`obj/` stay in `.gitignore` alongside `artifacts/` as a safety net, not because anything is expected to still produce them.

**Claude Code skill: `skills/dotnet-command-service/SKILL.md`, authored in this repo, describing the full API from the caller's point of view — `dotnet`, `git`, and artifact transfer alike.**
The skill isn't service code and doesn't affect the running service at all — it's documentation-as-a-skill for whichever Claude Code instance (the sbx sandbox) needs to consume this API, so it doesn't have to reverse-engineer the SSE contract from the specs or trial-and-error against the live endpoint. Content: how to authenticate (bearer header, where the token comes from, and that it applies to every endpoint below); how to start a `dotnet` run (`POST /run`) and a `git` run (`POST /run/git`, explicitly noting no subcommand is restricted) — same request shape (argument list, working directory, optional timeout), reading the `X-Run-Id` response header, same SSE event framing for both; how to request an artifact transfer (`POST /artifacts`, repo + file path, the `X-Run-Id` header before the file body, and that a request for a path outside the named repo is rejected — the caller should not attempt path tricks and should expect a confinement error if it gets the path wrong); how to consume the SSE stream from a Bash-based agent specifically (the `curl -N` / background-process-and-poll pattern already established as this project's answer to "how will Claude Code consume streaming output" earlier in this change), what the `stdout`/`stderr`/`done`/`error` event types and `error` reasons (`validation`/`timeout`/`cancelled`/`not-found`) mean, and how to cancel any of the three (`POST /run/{runId}/cancel`, one shared endpoint) including what a 409 (repo busy, with the blocking run's id — `dotnet`/`git` only) and a 404 (unknown/already-finished run) mean. It deliberately does not cover the dashboard, resource monitoring, or install/upgrade — those are for the human operator, not the sbx caller. The skill's content is a restatement of `specs/dotnet-command-execution`, `specs/git-command-execution`, `specs/artifact-transfer`, and `specs/service-authentication` for a different audience (an LLM agent calling the API, not a developer implementing it) — it needs to be kept in sync with those specs whenever the API contract changes, the same way any client documentation would.

**Repo documentation: `README.md`, `BUILD.md`, `INSTALL.md`, `CHANGELOG.md` at the repo root, each with one job.**
Four separate files rather than one large README, so each has an obvious, narrow purpose and doesn't grow into a dumping ground: `README.md` is the entry point (what this is, links to the other three, current high-level status); `BUILD.md` covers building/testing today (`dotnet build`/`dotnet test` on `OutOfTheBox.slnx`, prerequisites, the unit/BDD/architecture split and why the BDD suite is slower); `INSTALL.md` covers deployment (today: run `Host` directly for development; once the Packaging section lands: running `OutOfTheBoxSetup.exe`, clearly separating what exists now from what's planned so the doc doesn't overclaim); `CHANGELOG.md` follows the Keep a Changelog convention with an `Unreleased` section, updated as each tasks.md section completes, giving a human-readable parallel to the git log. None of these duplicate `openspec/changes/.../design.md` or `tasks.md`, which remain the source of truth for *why* and *what's left* — the repo docs are oriented at someone opening the repo cold, not at the planning history.

## Risks / Trade-offs

- **[Risk]** Generic passthrough means any `dotnet` invocation the caller can construct — including MSBuild custom targets/tasks that execute arbitrary code at build time — runs on the host with the service's OS privileges. → **Mitigation**: this is accepted, not solved, in v1; the credential is the entire trust boundary. The MSI's `util:User` element creates a new, dedicated local Windows account for the service (not an existing/shared account, not local admin) scoped to exactly the rights the service needs — log on as a service, read/write the data directory, read/write the configured repo root, and "Performance Monitor Users" membership. Document this clearly for the operator.
- **[Risk]** Unrestricted `git` passthrough carries the same class of risk as unrestricted `dotnet` passthrough, plus its own variant: git hooks (`pre-commit`, `post-checkout`, etc.) checked into a repo can execute arbitrary code the moment a caller runs a `git` command that triggers them, and destructive operations (`reset --hard`, `clean -fdx`, `push --force`) are explicitly not blocked, by request. → **Mitigation**: accepted under the same trust boundary as the `dotnet` risk above — no allowlist/denylist is applied, per the explicit requirement; the same dedicated least-privilege service account limits blast radius the same way it does for `dotnet`.
- **[Risk]** Artifact transfer's two-level confinement (root→repo, then repo→file) is more surface for a path-handling bug than the single-level check `dotnet`/`git` working-directory resolution needs, since it's two containment checks that both have to be correct. → **Mitigation**: both checks reuse the exact same `PathConfinementPolicy.IsContained` Domain rule and the exact same symlink-resolution step already implemented and tested for working-directory confinement (§4) — no new confinement logic is written, only a second call site for existing, already-unit-tested logic, and the second call's root is the *resolved* repo directory from the first call, not a second independent user input.
- **[Trade-off]** Artifact transfer has no directory-listing endpoint (see Non-Goals) — a caller that guesses a build-output path wrong gets a not-found response with no way to discover the right one except already knowing the project's conventional output layout or having seen it in a prior command's stdout. → Accepted for v1: the caller (Claude Code) already runs the build commands and sees their output, so it's expected to know or infer the path it wants; a listing endpoint is a natural v2 if this proves to be a real friction point.
- **[Risk]** Repository clone accepts any git-reachable URL, unrestricted, the same trust model as unrestricted `git-command-execution` — an operator could clone a malicious or unexpectedly large repository, and its hooks/config carry the same arbitrary-code risk already accepted for `git` generally. → **Mitigation**: accepted under the same trust boundary; this is an operator-triggered dashboard action (not reachable by the sbx caller at all), so it's gated by whoever has the dashboard credential, a narrower exposure than the already-accepted `git-command-execution` risk.
- **[Risk]** Repository deletion is immediate, recursive, and permanent, with the dashboard's confirmation step being the only safeguard — a mis-click past that confirmation, or a future caller of `IRepositoryManager.DeleteAsync` that skips the UI entirely, has no server-side undo. → **Mitigation**: accepted per Non-Goals (no soft-delete/trash in v1); documented plainly rather than implying a safety net that doesn't exist; the confirmation step is UX, not a technical safeguard, and should be described as such wherever this is documented.
- **[Risk]** Repository size and git-status sampling walks every repository's full directory tree and shells out to `git` on a recurring background cadence — on a host with many/large repositories this is nontrivial background IO, distinct from (and additive to) the already-accepted WMI/PerformanceCounter sampling cost. → **Mitigation**: the slow (60s-class) cadence plus event-driven recompute (rather than sub-10-second polling) bounds this; if it proves too heavy in practice, the cadence is a single configuration value to adjust, not a structural change.
- **[Risk]** A single shared static credential means any leak (log capture, sbx compromise) grants full command execution. → **Mitigation**: credential is configuration-only (rotatable without redeploy); operator should treat it as a high-value secret and rotate on suspected leak.
- **[Risk]** Long-running or runaway `dotnet` processes could exhaust host resources (CPU/disk/memory) since there's no per-request resource quota. → **Mitigation**: execution timeout (above) bounds wall-clock time; resource quotas (CPU/memory limits) are left as a future job-object-based enhancement, not v1.
- **[Trade-off]** An SSE stream still ties up one open HTTP connection per in-flight command for its full duration (no detach-and-reconnect); if the sbx-side client drops the connection mid-run, it loses the ability to observe the rest of that run (the server-side process still finishes, but there's no reconnect-and-resume). → Accepted for v1 given a single caller and no concurrency limits yet; a job-submit + reconnectable-poll model is the natural v2 if disconnect resilience becomes a problem.
- **[Risk]** SSE requires the HTTP client to disable response buffering/support streaming reads; a client that buffers the whole response before returning (some HTTP libraries default to this) would see no benefit and effectively degrade to synchronous behavior. → **Mitigation**: document the required client behavior (e.g. `curl -N`, or an HttpClient configured for `HttpCompletionOption.ResponseHeadersRead`) alongside the endpoint.
- **[Risk]** The run registry is in-memory only: a service restart drops all lock/run-id state even though the underlying `dotnet.exe` processes may or may not still be running depending on process-tree lifetime relative to the service. → **Mitigation**: accepted for v1 (matches "no persistent state" migration/rollback story); a cancel call after a restart simply 404s (run id no longer known), and a repo whose lock was lost on restart becomes immediately available again — document this as a known gap, not silently hidden.
- **[Risk]** Reject-on-conflict (vs. queueing) pushes retry/backoff logic onto the caller for the same-repo case. → **Mitigation**: accepted — the caller (Claude Code) can trivially retry or cancel-then-retry; documented in the API contract, not hidden behavior.
- **[Risk]** SQLite has no built-in retention/rotation, and full stdout/stderr per run can be large (up to the output cap, e.g. 5 MB, per run) — the database file grows unbounded over the service's lifetime. → **Mitigation**: accepted for v1 per the Non-Goals; document the growth rate and that an operator can manually prune old rows; a size-based retention policy is a natural v2.
- **[Risk]** SQLite allows only one writer at a time; under this service's actual write pattern (at most one insert/update per run-start and per run-terminal-state, and runs across different repos already run in parallel meaning writes could overlap) concurrent writers could contend or, if misconfigured, fail. → **Mitigation**: use SQLite's WAL journal mode (allows concurrent readers with a single writer, less blocking) and keep each write a short, single-row operation — no long-running transactions.
- **[Risk]** A service crash between "process exited" and "SQLite row updated" would leave a run's DB row stuck at `Running` even though the process is no longer active, look identical to a true hang until the startup reconciliation step relabels it `Interrupted` on next start. → **Mitigation**: accepted — the startup reconciliation (above) bounds how long this lasts to "until next restart," not indefinitely; a live dashboard viewer would see the run as still in-flight until then, which is a known, documented limitation, not silent data loss.
- **[Trade-off]** Blazor Server ties dashboard "liveness" to an open SignalR connection per browser tab; a flaky network between the operator's browser and the host will visibly disconnect/reconnect the dashboard (Blazor shows its own reconnection UI). → Accepted — this only affects the human viewing experience, never the underlying command execution or persistence, which are independent of any dashboard connection.
- **[Risk]** A self-contained single-file publish is large (100+ MB) since it bundles the full .NET runtime; copying it for every upgrade is heavier than a framework-dependent DLL deploy. → **Mitigation**: accepted — a one-time file copy on an internal network is not a meaningful cost, and it's what buys "no separate runtime install" for the operator.
- **[Risk]** Upgrading while the service is still holding the exe file open (didn't stop in time) would fail the file replacement or leave a partially-written binary. → **Mitigation**: `ServiceControl`'s `Stop="both"`/`Start="install"` semantics make MSI itself respect the service lifecycle around file replacement during `MajorUpgrade`, which is exactly the class of problem native upgrade sequencing exists to handle instead of a hand-rolled script reimplementing it (and getting the wait/verify/timeout logic subtly wrong).
- **[Risk]** EF Core migrations applied automatically at startup mean a bad migration in a new build could corrupt or fail against existing data with no automatic rollback path (downgrade isn't supported, per Non-Goals). → **Mitigation**: accepted for v1 given a single operator and low deployment frequency; document that operators should keep a copy of the SQLite file before upgrading if they want a manual rollback option.
- **[Risk]** `PerformanceCounter` access to the `Processor` category can require the service account to be a member of the local "Performance Monitor Users" group (behavior varies by Windows configuration) — the least-privilege service account chosen for the process-execution risk above might not have this by default. → **Mitigation**: the MSI's `util:User`/`util:Group` authoring must grant this membership explicitly as part of service-account creation; document it as a specific, deliberate grant rather than defaulting to a broader account.
- **[Risk]** WMI (`Win32_Process`) queries every few seconds, even for a small number of processes, add a background CPU/IO cost that scales (mildly) with total host process count, since `Win32_Process` enumerates all processes to filter by `ParentProcessId`. → **Mitigation**: accepted at a "few seconds" cadence for a typical host process count; if this becomes measurable, the tree walk can be narrowed by caching each root's last-known descendant PID set and only re-querying for genuinely new/exited children.
- **[Risk]** Behavior tests that genuinely spawn `dotnet.exe` (build/test the fixture projects) are slow relative to pure unit tests, and running them from inside a `dotnet test` process could hit MSBuild/NuGet lock contention or environment-variable bleed from the outer test-runner process into the spawned child. → **Mitigation**: fixture projects are trivial (near-instant restore/build) to keep wall-clock cost low; behavior tests run in their own project (`OutOfTheBox.BehaviorTests`) separate from the fast unit project, so a tight dev loop can run just unit tests; spawned child processes get an explicit clean environment rather than inheriting the outer test runner's.
- **[Risk]** A killed mid-tree process might not immediately release resources its own children were using, or a targeted kill could race with that process's own natural exit (killing a PID that already exited and was reused by an unrelated process — a classic PID-reuse hazard). → **Mitigation**: re-verify the target process's identity (e.g. compare `Process.StartTime` captured at discovery time against the live process before killing) immediately before the kill call, not just at tree-discovery time, so a stale PID from an earlier snapshot can't be used to kill an unrelated, newer process that happens to reuse the same PID.
- **[Trade-off]** Grouping the spawned-process list per-run (rather than one global table) means an operator can't see "everything the host is running" at a glance from Status — only what the service itself spawned. → Accepted: that's the explicit scope given (service-spawned processes only, not a full Task Manager replacement), and it's what keeps the view uncluttered.
- **[Risk]** `RunResourceSamples` grows much faster than `Runs` (many rows per run instead of one), and long/frequent runs multiply that further — this is a bigger driver of the already-accepted "SQLite grows unbounded" risk than run history text ever was; artifact transfers add a third source of these rows on top of `dotnet`/`git` runs. → **Mitigation**: accepted per Non-Goals (no retention policy in v1); the `(RunId, Timestamp)` index keeps per-run graph queries cheap regardless of total table size; document the growth rate explicitly (roughly `points-per-run × concurrent/sequential run volume`) so the operator can judge when manual pruning is warranted.
- **[Trade-off]** An artifact transfer's resource-sample series records host-level CPU/RAM at each tick, not usage attributable specifically to that transfer (see the Decisions section) — its graph answers "how busy was the host during this transfer," not "how expensive was this transfer," which could be misread as the latter by an operator used to the per-process-tree figures a `dotnet`/`git` run's graph shows. → Accepted: attributing genuine per-transfer CPU/I/O cost would need kernel-level per-operation accounting well beyond this project's scope; the dashboard's transfer-detail view should label the graph accordingly (e.g. "host activity during transfer") rather than presenting it as if it were a per-process figure, so the distinction is visible to the operator, not just documented here.
- **[Risk]** If `wwwroot`/Chart.js (composed from `Presentation`'s Razor Class Library into `Host`'s publish output via static web assets) isn't included correctly in the MSI's file component list (e.g. someone only harvests the exe), the dashboard loses graphs (and possibly more of its static styling) silently rather than failing loudly. → **Mitigation**: the MSI's wildcard `<Files Include="...**">` authoring covers the whole publish output directory (not a hand-maintained file list), so a new static asset added later isn't silently missed structurally; an explicit post-install verification (a deferred custom action, or a manual smoke-test step per 19) that a known static asset exists at the expected installed path is not yet authored - currently relies on the manual smoke test alone.
- **[Risk]** Live chart updates over a Blazor Server SignalR circuit, even at a "few seconds" cadence, add per-tick JS interop calls for every currently-expanded run chart plus the always-on host chart; with many simultaneously expanded run cards this could add up. → **Mitigation**: lazy chart mounting (above) bounds this to what the operator actually has open; the sampler cadence itself is already coarse (seconds, not sub-second), keeping worst-case interop call frequency low.
- **[Risk]** Five-project Clean Architecture layering (four rings plus `Host`) adds real friction for a service this size — more project-reference bookkeeping, more places to route a single change through (a new field on `Run` touches Domain, its Application port/DTO, its Infrastructure EF Core mapping, and possibly a Presentation view), plus a genuinely separate composition-root project most ASP.NET Core Clean Architecture templates fold into the Web project. → **Mitigation**: accepted — this was explicitly requested, specifically including "no connection at all" between Presentation and Infrastructure, which is exactly what the separate `Host` project buys; the NetArchTest suite is what makes the extra structure pay for itself (drift becomes a failing test, not a slow accumulation of shortcuts).
- **[Risk]** `Host` itself is unconstrained by NetArchTest (it's expected to reference everything) — if implementers start putting real business or presentation logic in `Program.cs`/`Host` "because it's already referencing everything anyway," nothing mechanically stops that; only `Presentation`↔`Infrastructure` isolation is actually enforced. → **Mitigation**: keep `Host` to DI registration, config binding, and framework startup calls only, enforced by code review — the architectural guarantee that matters most (Presentation and Infrastructure genuinely can't couple to each other) is the one that's mechanically checked; `Host` staying thin is a discipline, not a test.
- **[Risk]** `CS1591`-as-error for missing public XML doc comments will flag every public member across all five projects immediately, including ASP.NET Core/EF Core-generated or framework-required public surface (e.g. minimal API handler classes, EF Core entity constructors) that a developer might not think of as "this service's public API." → **Mitigation**: accepted as a deliberate strict default; suppress narrowly (a targeted `#pragma`/`[SuppressMessage]`, not a project-wide disable) for the specific framework-mandated cases where a doc comment would be pure noise, so the rule stays meaningful for the actual intentional public API.
- **[Risk]** The Claude Code skill is prose describing the API, with no compiler or test to keep it in sync with the real contract — a future change to the SSE event shape, error reasons, or endpoints could silently leave the skill wrong while `dotnet test` stays green. → **Mitigation**: accepted for v1 (no automated skill-vs-spec consistency check); the skill explicitly cites which spec files it restates, and the manual verification task (running a real Claude Code instance through the skill against a live service) is the practical check, repeated whenever the API contract changes materially.
