## Context

Greenfield project (repo currently empty apart from openspec scaffold). Host is Windows with .NET 10 SDK installed. Caller is a Claude Code instance running in a remote sbx sandbox, reaching this host over the network — not localhost. A human operator also uses the same host's browser (or one on the local network) to view status/history. See proposal.md for motivation; specs/dotnet-command-execution, specs/service-authentication, specs/run-history, and specs/service-dashboard for required behavior.

## Goals / Non-Goals

**Goals:**
- Single Windows-hosted process that survives reboots and serves requests continuously.
- Execute arbitrary `dotnet` argument lists safely with respect to process-spawning (no shell interpretation), path confinement, and credential-gated access.
- Stream stdout/stderr back to the caller incrementally as the command runs, with a final event carrying the exit code, so a caller polling a long `dotnet test` run sees live progress instead of a multi-minute silent wait.
- Run commands against different repos in parallel; allow at most one in-flight `dotnet` command per repo at a time.
- Let the caller cancel an in-flight command by run id.
- Durably persist every run (command, repo, timestamps, outcome, full output) so history survives a restart.
- Give a human operator a live-updating, pleasant web view of current status and history — no manual refresh, no hand-crafted API calls.
- Package as a single self-contained deployable that needs nothing pre-installed on the host beyond the OS (no separate .NET runtime install, no separate database server).
- Make install a small number of scripted steps, and upgrade a binary swap that never touches configuration or persisted history.
- A full automated test suite (unit + BDD) that builds and runs with the plain .NET 10 SDK CLI (`dotnet build`, `dotnet test`) — no IDE, no separate test runner.
- Clean Architecture layering (Domain / Application / Infrastructure / Presentation) with the dependency direction mechanically enforced, not just documented, so the boundary can't silently erode over time.
- A Claude Code skill documenting the API contract for the sbx-side caller, so it doesn't need to reverse-engineer auth/streaming/cancellation from the specs or trial and error.

**Non-Goals (v1):**
- A job queue that auto-serializes a second command behind a busy repo's lock — a second request for a busy repo is rejected immediately, not queued/waited-on server-side.
- Multi-user auth (roles, per-caller keys) — single shared credential only, for both the API and the dashboard.
- Sandboxing `dotnet.exe` itself (e.g. restricted user, container) beyond path confinement and process-argument safety. MSBuild can run arbitrary build-time code (custom targets/tasks) — this service does not attempt to prevent that; it trusts the caller to the same degree the caller is trusted to run `dotnet` at all.
- History retention/archival policy (pruning old runs, size-based rotation, or downsampling old resource-sample series) — v1 keeps everything indefinitely, at full sample resolution, in the SQLite file.
- Horizontal scaling / multi-instance deployment — the in-memory run registry, SQLite file, and Blazor Server circuits all assume a single process on a single host.
- A GUI/MSI installer or downgrade support — install/upgrade are PowerShell scripts, and upgrading to an older version is not a supported path (schema migrations are forward-only).
- Automated installation of the Claude Code skill into the sbx sandbox's own environment — that's a separate machine this repo doesn't control; the skill is authored and shipped here, but installing it on the sbx side is a manual step for whoever sets that environment up.
- Fully automated coverage of real-deployment concerns (real Windows Service install, real firewall, real TLS cert, a real second machine acting as the sbx caller) — those remain a manual End-to-End Verification checklist; `dotnet test` covers everything short of an actual deployed instance.

## Architecture

Clean Architecture (Onion-style): `Domain` at the center, `Application` wrapping it, and an outer ring split into two independent slices — `Presentation` and `Infrastructure` — that each depend inward on `Application` but **never on each other, with no exception**. A fifth project, `Host`, sits outside all of the rings as the composition root: it's the only project allowed to reference both outer-ring slices, and its only job is wiring them together and running the process. `Presentation` and `Infrastructure` are otherwise unaware of each other's existence, including for DI registration.

- **`BuildAndTestService.Domain`** — entities (`Run`, `RunResourceSample`), the `Outcome` state (Running/Completed/TimedOut/Cancelled/ValidationFailed/Interrupted), and pure business rules with zero IO/framework dependency: CPU%/RAM aggregation math, and the "is this already-resolved path contained under that already-resolved root" decision (the actual filesystem canonicalization and symlink resolution is IO, so it's Infrastructure's job to resolve both paths and hand the two resolved strings to this Domain rule). No NuGet dependency beyond the BCL — nothing here can reference ASP.NET Core, EF Core, WMI, or `PerformanceCounter`.
- **`BuildAndTestService.Application`** — use-case orchestration and the ports (interfaces) Infrastructure implements: `IRunRepository`, `IRunResourceSampleRepository`, `IProcessRunner`, `IProcessMonitor`, `IResourceSampler`, `IRunEventBus`, `IResourceEventBus`, `IClock`. Also owns the services that coordinate them — run start/cancel orchestration, the in-memory per-repo lock registry (pure in-memory state, no external dependency, so it belongs here rather than Infrastructure), and kill-scope verification. Depends only on Domain.
- **`BuildAndTestService.Infrastructure`** — concrete implementations of every Application port: real `System.Diagnostics.Process` spawning, WMI process-tree discovery, `PerformanceCounter`/`GlobalMemoryStatusEx` sampling, EF Core + SQLite persistence and migrations, the in-memory event-bus implementations, the system clock. Depends on Application + Domain only.
- **`BuildAndTestService.Presentation`** — a Razor Class Library (so it can carry `.razor` components and its own `wwwroot`, e.g. Chart.js) plus plain classes: the minimal API endpoint definitions as `IEndpointRouteBuilder` extension methods (SSE run/cancel, `/version`), the Blazor Server dashboard components/pages, and auth-cookie/bearer middleware classes. Depends on Application + Domain only — it is not an executable and has no `Program.cs` of its own; it exposes extension methods (`MapCommandExecutionEndpoints(...)`, `AddDashboardServices(...)`) for `Host` to call.
- **`BuildAndTestService.Host`** — the actual executable: `Program.cs` builds the `WebApplication`, calls `Presentation`'s registration/mapping extension methods, registers `Infrastructure`'s concrete types against `Application`'s interfaces in the DI container, configures Kestrel/HTTPS, and calls `UseWindowsService()`. `Host` references all four other projects; no other project references `Host`. It contains no business or presentation logic of its own — if it's more than DI registration, config binding, and framework wiring, that code belongs in one of the four inner projects instead.

Splitting the composition root out as its own project (rather than letting `Presentation`'s `Program.cs` do double duty, as many ASP.NET Core Clean Architecture templates do) is what makes "`Presentation` and `Infrastructure` never reference each other" a literal, exception-free rule instead of one with a carved-out escape hatch — and it's what the operator asked for directly.

This is more structure than a service this size strictly needs, but it buys two concrete things beyond "looks clean": Domain/Application logic becomes unit-testable without spinning up EF Core, WMI, `PerformanceCounter`, or Kestrel at all, and the boundary is something a test suite checks on every build instead of something a code reviewer has to remember to look for.

## Decisions

**Framework: ASP.NET Core 10 minimal API, hosted as a Windows Service, from `Host`.**
`Host` calls `Microsoft.Extensions.Hosting.WindowsServices`' `UseWindowsService()` so the process runs under the Windows Service Control Manager, instead of relying on a logged-in console session or Task Scheduler. Alternative considered: run as a plain console app in a scheduled task — rejected because SCM doesn't depend on a user session existing and gives a place to configure restart-on-crash (see Packaging below — SCM does not restart on crash by default; it must be configured).

**Packaging: self-contained, single-file, win-x64 publish.**
`dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true` produces one `.exe` that bundles the .NET 10 runtime — the host needs nothing pre-installed beyond the OS itself, so "install" never depends on a separate runtime-version match. `IncludeNativeLibrariesForSelfExtract` is required because the SQLite provider ships a native library (`e_sqlite3.dll`); without it, single-file publishing would fail to resolve that native dependency at run time. Trimming (`PublishTrimmed`) is deliberately **not** enabled: Blazor Server and EF Core are reflection-heavy, and trimming them has a real risk of removing code that's only reached dynamically, causing runtime failures that are hard to catch pre-deployment — the resulting binary is larger (roughly 100+ MB) but reliable, which matters more for a service that's rarely redeployed. Native AOT was considered and rejected for the same reason as trimming, more severely: Blazor Server's interactive-server render mode has limited/immature Native AOT support as of .NET 10, so self-contained single-file is the practical ceiling for "self-contained" here, not full AOT.

**Data/config directory is separate from the install directory, so upgrade is a pure binary swap.**
The published `.exe` and its install directory (e.g. `C:\Program Files\BuildAndTestService`) are treated as disposable/replaceable. Configuration (`appsettings.json` overrides / env vars) and the SQLite database file both live under a fixed per-machine data directory (e.g. `C:\ProgramData\BuildAndTestService\`) created once at install time and never touched by upgrade. This is what makes "upgrade = replace the exe" true: the new binary starts up, reads the same config from the same data directory, runs any pending EF Core migrations against the same SQLite file, and continues where the old binary left off — no config re-entry, no data migration step for the operator to remember.

**Install/upgrade via PowerShell scripts, not an MSI/GUI installer.**
`install.ps1` creates a new dedicated local service account (see the generic-passthrough risk below for its exact rights), creates the install and data directories, copies the published exe, writes an initial config (prompting for or generating the bearer token), creates the Windows Service running as that account, explicitly configures SCM crash-recovery (`sc.exe failure <name> reset= 86400 actions= restart/60000/restart/60000/restart/60000` — SCM does not restart a crashed service by default, this has to be set), opens the firewall rule(s), and starts the service. `upgrade.ps1` stops the service, verifies it actually stopped, copies the new exe over the install directory (data directory untouched), starts the service, and polls a version/health endpoint to confirm the new build is actually running. Alternative considered: a WiX/MSI installer — rejected as disproportionate tooling for a single-operator internal service; it would add a second build toolchain to maintain for a UX benefit (double-click install, Control Panel uninstall) this deployment doesn't need, and cuts against the "as self-contained as possible" goal by adding an external packaging dependency.

**Process execution: `System.Diagnostics.Process` with `UseShellExecute = false`, arguments passed via `ArgumentList` (not a concatenated string).**
This guarantees the OS never invokes `cmd.exe`/shell parsing on the argument list — each array element becomes one literal argv entry to `dotnet.exe`, which is what the spec's "no shell interpretation" requirement depends on. Wire `OutputDataReceived`/`ErrorDataReceived` handlers so each line is forwarded to the output stream (below) as it is produced, instead of buffering to end-of-process.

**Output delivery: Server-Sent Events (SSE) over the same HTTPS connection.**
The command-execution endpoint responds with `Content-Type: text/event-stream` and writes one SSE event per stdout/stderr line as `Process.OutputDataReceived`/`ErrorDataReceived` fire, then a final `done` event carrying the exit code once the process exits. Chosen over WebSocket because the caller (Claude Code in the sbx sandbox) has no persistent WS client — it shells out to a plain HTTP client (`curl -N` or equivalent) and reads output as it's flushed; SSE is a normal chunked HTTP response, needs no handshake, and passes through ordinary HTTP infrastructure. The named event types (`stdout`, `stderr`, `done`, `error`) give the caller unambiguous framing to tell a data line apart from the terminal exit-code event, which is what the "distinguish never-executed from completed" requirement in spec.md depends on. Alternative considered: raw chunked `text/plain` — rejected because it has no event boundaries, so the caller would have to guess where stdout/stderr/exit-code fields start and end.

**Execution timeout with process-tree kill; caller-overridable, server-clamped.**
The default timeout is 10 minutes, configured on the host. The caller may include an optional timeout in the request, which is used instead of the default for that run — the caller (Claude Code in the sbx sandbox) knows the shape of the command it's issuing (a quick `dotnet --version` vs. a large `dotnet test` run) better than a single host-wide default can. Whatever value is used (caller-supplied or default), it's clamped to a configured maximum (e.g. 60 minutes) before being applied, so a caller can shorten its effective timeout freely but can never request an effectively-unbounded one — this keeps the "runaway process exhausts host resources" risk bounded regardless of what a caller asks for. On timeout, kill the process (and child processes `dotnet` may spawn, via `Process.Kill(entireProcessTree: true)`), emit an `error` event with reason `timeout`, and close the stream. Without a timeout at all, a hung `dotnet test` run ties up a server thread/handle and an open connection indefinitely.

**Per-stream output is still size-capped.**
Even though output streams incrementally rather than buffering fully, cap total bytes emitted per execution (e.g. 5 MB); beyond that, stop forwarding lines, emit a truncation flag on the `done`/`error` event, and let the process keep running to completion (or be killed by the timeout) without holding unbounded memory for already-sent lines.

**Path confinement via canonicalization, not string prefix checks alone.**
Resolve the caller-supplied relative path against the configured root with `Path.GetFullPath`, then verify the result's full path starts with the root's full path plus a trailing separator (not just a string prefix, which would let `C:\repos-evil` pass a naive check against root `C:\repos`). Reject symlink/junction traversal by resolving the final path (`Directory.ResolveLinkTarget` or equivalent) before the containment check.

**Auth: single shared bearer token from configuration, constant-time comparison.**
Read the expected token from an environment variable / configuration provider (never hardcoded). Compare using `CryptographicOperations.FixedTimeEquals` to avoid timing side-channels. Chosen over a full identity provider because there is exactly one trusted caller (the sbx sandbox) — a shared secret matches the actual trust model; anything heavier is unjustified complexity for v1.

**Transport: HTTPS required, bound to a specific interface/port.**
Because the credential and command arguments (and now, streamed output) cross a real network link between two machines (not loopback), the endpoint requires TLS — plain HTTP would leak the bearer token and command output to anyone on-path. Certificate can be a private/self-signed cert pinned by the sbx-side client for v1, since both endpoints are under the same operator's control (not public internet). Bind Kestrel to a specific port and, at the OS firewall level, restrict inbound connections on that port to the sbx sandbox's IP. Disable response buffering for the SSE endpoint so Kestrel flushes each event immediately rather than batching.

**Concurrency: parallel across repos, locked per repo via an in-memory registry.**
Maintain a `ConcurrentDictionary<string, RunInfo>` keyed by the canonicalized repo root (the same resolved path used for path confinement), where `RunInfo` holds the run id, the `Process` handle, and a `CancellationTokenSource`. On request start, atomically `TryAdd` the repo key; success acquires the lock and starts the process, failure means a run is already in flight for that repo and the new request is rejected immediately with 409-style conflict carrying the existing run's id. The entry is removed on any terminal state (completed, timed out, cancelled), releasing the repo for the next request. `TryAdd`'s atomicity is what prevents a race between two simultaneous requests for the same repo both believing they acquired the lock. Alternative considered: queue the second request and run it once the first finishes — rejected because it hides latency from the caller (a "run" call could silently block for an unrelated run's duration) and complicates cancellation semantics (cancel which one, the running or the queued?); an explicit reject-with-conflict keeps the caller in control, and the new cancellation API gives it a way to unblock a repo on purpose.

**Cancellation: run id assigned at start, cancel endpoint kills the process tree.**
Every accepted run is assigned a run id (e.g. a GUID) at the moment the repo lock is acquired, returned to the caller via an `X-Run-Id` response header emitted before the SSE body starts (headers can be flushed before a chunked body, so the caller has the id even though the body streams for the run's full duration). A separate authenticated `POST /run/{runId}/cancel` endpoint looks up the run id in the same registry used for locking; if found and still active, it calls `Process.Kill(entireProcessTree: true)` — the same mechanism the timeout path already uses — which causes the in-flight SSE stream to observe process exit and emit a terminal `error` event with reason `cancelled` (as opposed to `timeout` or a validation failure), and removes the registry entry, releasing the repo lock. If the run id is unknown or already terminal, the cancel endpoint returns 404 and touches nothing. Cancellation is therefore best-effort and reuses existing kill/terminal-event plumbing rather than introducing a second termination pathway.

**Persistence: SQLite via EF Core, one `Runs` table, write-through from the same start/terminal hooks as the registry.**
A single `Runs` table: `Id` (run id, PK), `RepoPath`, `Arguments` (JSON-encoded array), `StartedAt`, `CompletedAt` (nullable), `Outcome` (`Running`/`Completed`/`TimedOut`/`Cancelled`/`ValidationFailed`/`Interrupted`), `ExitCode` (nullable), `Stdout`, `Stderr`, `Truncated`. A row is inserted with `Outcome = Running` at the same point the in-memory registry entry is created (repo lock acquired, process started), and updated in place when the run reaches a terminal state — the same code path that removes the registry entry also writes the terminal row update, so there is one place that defines "a run is over," not two. EF Core (over raw `Microsoft.Data.Sqlite`/Dapper) is chosen for its migration story (schema changes as the run record shape evolves) and because write volume is low (two writes per run: insert + one update) — ORM overhead is irrelevant at this scale. SQLite itself (over a client-server DB) is chosen because it's a single embedded file needing no separate service to install, run, secure, or back up, matching a single-host, single-writer deployment — and matching the "self-contained" packaging goal (see Packaging decisions below), it lives in the same per-machine data directory as configuration, untouched by binary upgrades. On service startup, any row still `Outcome = Running` from before the restart is reconciled to `Interrupted` (the in-memory registry that would confirm it's still running was lost on restart, so its true state is unknown).

**Dashboard: Blazor Server, backed by an in-process run-event bus for live updates + SQLite for history queries.**
The dashboard is a Blazor Server app hosted in the same ASP.NET Core process (no separate frontend project/build step, no SPA framework). A singleton `IRunEventBus` (in-process pub/sub — e.g. a `Channel<RunEvent>` fanned out to subscribers, or a plain C# event) is published to from the same code paths that already touch the run registry: run started, output line produced, run reached terminal state. Blazor components for the current-status view subscribe to this bus on `OnInitialized`, call `InvokeAsync(StateHasChanged)` on relevant events, and unsubscribe on `Dispose` — this is what makes the dashboard "live" without polling. The history view instead queries the `Runs` table directly (via EF Core) since past runs don't change; it doesn't need the event bus. Chosen over a plain HTML+SSE dashboard (as sketched for command output) because Blazor Server's component model and built-in SignalR transport make a richer, multi-view UI (status list + history list + per-run detail) substantially less code than hand-rolling equivalent client-side JS/DOM updates, and the operator explicitly asked for "pleasant," which favors a real component-based UI over minimal hand-built HTML. Trade-off accepted: Blazor Server requires a persistent SignalR connection per open dashboard tab (WebSocket, or long-polling fallback) — acceptable given the same HTTPS port/firewall rule already carries the SSE traffic, and there's only ever one or a few operators, not many concurrent viewers.

**Dashboard auth: same shared bearer token, exchanged for an auth cookie via a login page.**
Blazor Server circuits don't naturally carry a bearer header per request the way the API does, so the dashboard has a small login page where the operator enters the same configured token; on success the server sets a standard ASP.NET Core auth cookie (validated the same way — `CryptographicOperations.FixedTimeEquals` against the configured value — just entered once per browser session instead of per request). This keeps a single credential as the entire trust boundary (per the existing auth decision) rather than introducing a second, separate dashboard credential.

**Dashboard theme: dark-only, no toggle.**
Ship a single dark CSS theme (no `prefers-color-scheme` branching, no toggle component) — the operator asked for dark-only, and skipping a light theme entirely removes a whole axis of UI work/testing for a one-operator internal tool.

**Dashboard layout: separate Status / History views, processes grouped under their owning run.**
To avoid one overloaded page, the dashboard has two top-level views: **Status** (default landing page — resource header, in-flight runs, each run's spawned-process sublist) and **History** (past runs list + detail). The spawned-process list is not one global flat table; each in-flight run's card/row expands to show only the processes in that run's own tree, keeping the per-run correspondence in the requirement obvious at a glance and keeping any single run's list short.

**Host CPU sampling: `System.Diagnostics.PerformanceCounter` against the `Processor` category.**
Read `\Processor(_Total)\% Processor Time` for the total figure and `\Processor(N)\% Processor Time` for each logical core (`N` from `0` to `Environment.ProcessorCount - 1`). `PerformanceCounter` is Windows-only, which is fine (this service is Windows-only throughout), and is the documented, supported way to read these counters without P/Invoke. Known quirk: a freshly-constructed `PerformanceCounter`'s first `NextValue()` call always returns `0` (no prior sample to diff against) — the background sampler must discard the first reading per counter rather than publish it as real data. Alternative considered: `NtQuerySystemInformation`/`GetSystemTimes` P/Invoke — more brittle (partly undocumented for per-core), rejected in favor of the supported counter API.

**Host RAM: `GlobalMemoryStatusEx` P/Invoke; service RAM: `Process.GetCurrentProcess().WorkingSet64`.**
`GlobalMemoryStatusEx` (a single Win32 call) returns total and available physical memory directly, cheaper and more immediate than a `PerformanceCounter` (no discard-first-sample quirk). The service's own memory figure is just its own `WorkingSet64` — no extra mechanism needed.

**Spawned-process tree discovery: WMI (`Win32_Process`) walked by `ParentProcessId`, rooted at each tracked run's `Process.Id`.**
`System.Diagnostics.Process` doesn't expose a process's parent or children directly. Query `Win32_Process` (via the `System.Management` package) for `ProcessId`/`ParentProcessId`/`Name`, and recursively collect descendants starting from each in-flight run's root PID (already known from the `RunInfo` registry entry) — the same tree this walk discovers is what `Process.Kill(entireProcessTree: true)` already tears down internally for the timeout/cancel paths, so the dashboard's tree view and the kill mechanics stay conceptually aligned. Alternative considered: `CreateToolhelp32Snapshot`/`Process32Next` P/Invoke — functionally similar, more code, rejected in favor of the managed WMI wrapper since polling every few seconds for a handful of processes is not performance-sensitive enough to justify avoiding WMI's overhead.

**Per-process CPU%: manual delta-sampling of `Process.TotalProcessorTime`, not a WMI perf class.**
For each PID in a discovered tree, keep the last-sampled `TotalProcessorTime` and timestamp; on the next tick, `CPU% = (ΔTotalProcessorTime / (Δwallclock × Environment.ProcessorCount)) × 100`. This is the standard .NET technique for per-process CPU and avoids WMI instance-name disambiguation problems that `Win32_PerfFormattedData_PerfProc_Process` has when multiple processes share a name (e.g. two `dotnet.exe`). RAM per process is `Process.GetProcessById(pid).WorkingSet64`, sampled at the same tick.

**Resource sampling cadence: a single background `PeriodicTimer`, fanned out through an `IResourceEventBus`, mirroring the run-event pattern.**
A hosted background service ticks every few seconds (configurable, default matches the requirement's "at least every few seconds"), samples host CPU/RAM, service RAM, and each tracked run's process tree in one pass, and publishes a snapshot to an `IResourceEventBus` that dashboard components subscribe to (same subscribe/`StateHasChanged`/unsubscribe pattern as `IRunEventBus`) — reusing the established live-update mechanism rather than inventing a second one, and keeping the sampling itself off the SignalR/request path.

**Kill action: in-process Blazor method call, not a REST endpoint.**
Unlike run cancellation (which must be reachable by the remote sbx caller, a non-browser HTTP client, and is therefore a real `POST /run/{runId}/cancel` endpoint), the process-kill button is only ever triggered by an operator already inside an authenticated Blazor circuit — the component's click handler calls an injected `IProcessMonitor.KillAsync(pid)` service method directly, server-side, with no additional network endpoint. This keeps the network-facing authenticated surface exactly as large as before (two endpoints: run + cancel) rather than adding a third.

**Kill scope enforcement: verify the target PID is inside a currently-tracked process tree before killing, always, server-side.**
`IProcessMonitor.KillAsync(pid)` re-walks (or checks against the last-sampled) tree membership for `pid` against the set of currently tracked run root PIDs before calling `Process.GetProcessById(pid).Kill(entireProcessTree: true)`; if `pid` isn't found under any tracked root, the call is rejected. This check happens in the server-side service method itself, not just in the UI (the UI simply shouldn't offer buttons for out-of-scope processes) — because the enforcement point spec.md requires ("SHALL reject a termination request for any other process id, regardless of what id is supplied") is about the action being scoped, not about hiding the button. Killing the target with `entireProcessTree: true` (not just the single PID) is what satisfies "terminate that process together with its own descendants."

**Per-run aggregation: sum already-sampled per-process figures across each run's tree, computed in the same sampler tick.**
Each `PeriodicTimer` tick already computes per-process CPU%/RAM for every PID in a run's discovered tree (for the process list). The run's aggregate CPU% and RAM are just the sum of those already-computed per-process values for that tick — no separate sampling mechanism, so aggregation is "free" given the process-level sampling already required for the process list.

**Resource sample persistence: new `RunResourceSamples` table, one row per run per tick, written by the same background sampler.**
`RunResourceSamples(RunId FK, Timestamp, CpuPercent, RamBytes)`, indexed on `(RunId, Timestamp)`. On every sampler tick, for each in-flight run, insert one row with that tick's aggregate CPU%/RAM (the same aggregate computed above) via EF Core — write volume is one row per in-flight run per tick (e.g. one run sampled every 3 seconds is ~20 rows/minute), which is low enough not to need batching given SQLite's WAL mode already in use. Samples for a run stop being written once it reaches a terminal state; the complete set of rows for that `RunId`, ordered by `Timestamp`, is the "full graph" data for history. No downsampling/compaction is applied (raw samples kept as-is) — simplest correct behavior for v1, revisited only if the table's growth (see Risks) becomes a real problem.

**Live rolling window: an in-memory circular buffer per series (host, each in-flight run), independent of the persisted series.**
The Status view's live graphs read from a small in-memory ring buffer (capacity = 10 minutes ÷ sample interval, e.g. 200 points at 3s) maintained alongside the sampler tick — not from SQLite. This keeps live rendering fast (no DB round trip per tick) and decouples "what the live graph shows" (bounded 10-minute window, discarding older in-memory points) from "what gets persisted" (the sampler still writes every tick to `RunResourceSamples` regardless of what's evicted from the live buffer). History's "full graph" reads the complete persisted series instead of this buffer.

**Charting: Chart.js, vendored locally in `Presentation`'s `wwwroot`, via a thin JS interop wrapper — not a CDN reference, not a Blazor-native charting library.**
Ship `chart.js` as a static asset under `Presentation`'s `wwwroot` (downloaded once at build time and committed/restored like any other static asset, not fetched from a CDN at runtime) — consistent with "self-contained" meaning no runtime dependency on internet access. Because `Presentation` is a Razor Class Library, ASP.NET Core's static web assets feature automatically composes its `wwwroot` into `Host`'s publish output at build/publish time (no manual copy step in the project itself) — but the physical files still end up as loose files alongside `Host`'s `.exe` in the publish output (`PublishSingleFile` bundles managed/native assemblies, not static web assets), so the install directory is a small folder, not literally one file, and `install.ps1`'s copy step must still include the whole publish output, not just the exe. A minimal `IJSRuntime` wrapper creates one chart instance per graph and pushes new points via `chart.data.datasets[0].data.push(...); chart.update('none')` on each tick, rather than recreating the chart every tick. Chart.js is chosen over a hand-rolled SVG sparkline component for visual quality (gradients, tooltips, axis labels, smooth updates) at a fraction of the implementation effort "nice looking graphs" would otherwise take; a pure-Blazor charting NuGet package was also considered and rejected only because Chart.js is better documented and more broadly proven than the current crop of Blazor-native chart libraries.

**Chart rendering is lazy: only mounted for a run once its card is expanded (or its history detail is opened).**
To keep "don't overload the dashboard" true even with several concurrent in-flight runs, a run's live chart component isn't instantiated (no JS interop calls, no `IResourceEventBus` subscription for that run's series) until the operator expands that run's card. Host-level graphs (always visible in the Status header) are the only charts always live.

**Solution format: `.slnx`, not classic `.sln`.**
`.slnx` is the newer XML-based solution format; confirmed working in the operator's Rider (opens and builds cleanly). Alternative considered: classic `.sln` — works everywhere but wasn't what was asked for, and isn't needed as a fallback given Rider support is confirmed.

**Solution folders: one per architecture project, all test projects grouped under a single "Tests" folder.**
Root-level solution folders: `Domain`, `Application`, `Infrastructure`, `Presentation`, `Host` (one project each), and `Tests` (containing `UnitTests`, `BehaviorTests`, `ArchitectureTests`, and a `Fixtures` subfolder holding the checked-in sample projects). Solution folders are an IDE-only grouping independent of physical directory layout, but here the physical `src/<ProjectName>/` and `tests/` layout matches 1:1 for simplicity — this is a direct implementation of "solution folders that make sense" plus "tests under one root Tests node, subfolders allowed."

**Test project layout: `UnitTests` and `BehaviorTests`, plus checked-in fixture projects, all under the `.slnx`'s `Tests` folder.**
`UnitTests` targets Domain and Application logic almost exclusively (that's the whole point of the layering — most of what's worth unit-testing needs no EF Core/WMI/PerformanceCounter/Kestrel), organized internally into `Domain/`, `Application/`, and `Infrastructure/` folders mirroring the layer under test; a handful of Infrastructure-layer tests use a real SQLite `:memory:` connection (not EF Core's InMemory provider, which doesn't exercise real SQL/migrations) rather than a fake. `BehaviorTests` exercises the real ASP.NET Core pipeline through `WebApplicationFactory<Program>`/`TestServer` against `Host` (the executable with the actual `Program` entry point, now that composition lives there rather than in `Presentation`), including genuinely spawning `dotnet.exe` child processes (that's the behavior under test), but against small checked-in fixture projects (`Tests/Fixtures/`: one passing test, one failing test, one intentionally-hanging test) rather than large real repos, keeping the suite fast and deterministic.

**Unit test framework: xUnit.** The de facto modern .NET default, first-class `dotnet test` support with no separate runner, and what the chosen BDD tooling (below) integrates with most smoothly. Alternative considered: NUnit/MSTest — no material advantage here, xUnit chosen for ecosystem consistency.

**BDD framework: Reqnroll (Gherkin `.feature` files, xUnit-backed), not SpecFlow.** Reqnroll is the actively-maintained open-source continuation of SpecFlow (SpecFlow's own governance/licensing shifted toward a commercial model) and works via plain `dotnet build`/`dotnet test` — no Visual Studio dependency, confirmed — which is a hard requirement here. Each capability gets one `.feature` file whose scenarios are transcribed directly from that capability's spec.md `#### Scenario:` (WHEN/THEN) blocks into Gherkin (Given/When/Then), giving direct, checkable traceability from an openspec requirement to an executable test rather than a parallel, potentially-drifting test-only description of the same behavior. Alternative considered: hand-rolled Given/When/Then extension methods over plain xUnit (no separate Gherkin layer) — rejected because it loses the plain-text scenario file that doubles as documentation and the direct spec-to-feature-file correspondence.

**Windows-only API surface: target `Infrastructure` and `Host` `net10.0-windows` (or annotate with `[SupportedOSPlatform("windows")]`); `Domain`, `Application`, and `Presentation` stay plain `net10.0`.**
`PerformanceCounter`, WMI, and `GlobalMemoryStatusEx` live entirely in `Infrastructure` (behind Application's ports); `UseWindowsService()` lives in `Host`. `Presentation` itself — Blazor components, endpoint-mapping extension methods, auth middleware — never calls a Windows-only API directly, so it has no reason to be platform-tagged. Tagging only the two projects that actually need it makes the CA1416 platform-compatibility analyzer meaningful there instead of blanket-suppressed everywhere, and keeps `Presentation` genuinely portable in principle even though this deployment will only ever run on Windows.

**Architecture enforcement: `BuildAndTestService.ArchitectureTests` using NetArchTest.Rules, part of `dotnet test`.**
Encodes the Architecture section's dependency rules as executable assertions instead of relying on code review to catch drift:
- `Domain` has no dependency on `Application`, `Infrastructure`, `Presentation`, or `Host`, and no dependency on any `Microsoft.AspNetCore.*`, `Microsoft.EntityFrameworkCore.*`, `System.Management`, or `System.Diagnostics.PerformanceCounter` namespace.
- `Application` has no dependency on `Infrastructure`, `Presentation`, or `Host`.
- `Infrastructure` has no dependency on `Presentation` or `Host`.
- `Presentation` has no dependency on `Infrastructure` or `Host` — no exception, since composition now lives entirely in `Host`.
Each rule is an ordinary xUnit `[Fact]` inside `ArchitectureTests`, so a violation fails `dotnet test` exactly like any other broken test — nothing extra to remember to run. `Host` itself is deliberately excluded from these rules — it's expected to reference everything, that's its entire purpose.

**Code-quality baseline: nullable reference types + `GenerateDocumentationFile` enabled solution-wide; missing public-API doc comments fail the build.**
Every project sets `<Nullable>enable</Nullable>`; `<GenerateDocumentationFile>true</GenerateDocumentationFile>` plus treating the missing-XML-doc-comment warning (`CS1591`) as an error means a public type or member without a `///` doc comment fails `dotnet build`, not just a linter suggestion someone can ignore — this is what makes "public APIs need to be fully documented" a build gate rather than a style guideline. Other "common clean code" concerns (small methods, single responsibility, meaningful names, no magic numbers) are enforced the ordinary way — code review plus the .NET SDK's own bundled analyzers/`.editorconfig` — rather than a bespoke tool, since a purpose-built service at this scale doesn't need much beyond what already ships in the box.

**Claude Code skill: `skills/dotnet-command-service/SKILL.md`, authored in this repo, describing the API from the caller's point of view.**
The skill isn't service code and doesn't affect the running service at all — it's documentation-as-a-skill for whichever Claude Code instance (the sbx sandbox) needs to consume this API, so it doesn't have to reverse-engineer the SSE contract from the specs or trial-and-error against the live endpoint. Content: how to authenticate (bearer header, where the token comes from), how to start a run (`POST /run`, the argument-list/working-directory/optional-timeout request shape, reading the `X-Run-Id` response header), how to consume the SSE stream from a Bash-based agent specifically (the `curl -N` / background-process-and-poll pattern already established as this project's answer to "how will Claude Code consume streaming output" earlier in this change), what the `stdout`/`stderr`/`done`/`error` event types and `error` reasons (`validation`/`timeout`/`cancelled`) mean, and how to cancel (`POST /run/{runId}/cancel`) including what a 409 (repo busy, with the blocking run's id) and a 404 (unknown/already-finished run) mean. It deliberately does not cover the dashboard, resource monitoring, or install/upgrade — those are for the human operator, not the sbx caller. The skill's content is a restatement of `specs/dotnet-command-execution` and `specs/service-authentication` for a different audience (an LLM agent calling the API, not a developer implementing it) — it needs to be kept in sync with those specs whenever the API contract changes, the same way any client documentation would.

## Risks / Trade-offs

- **[Risk]** Generic passthrough means any `dotnet` invocation the caller can construct — including MSBuild custom targets/tasks that execute arbitrary code at build time — runs on the host with the service's OS privileges. → **Mitigation**: this is accepted, not solved, in v1; the credential is the entire trust boundary. `install.ps1` creates a new, dedicated local Windows account for the service (not an existing/shared account, not local admin) scoped to exactly the rights the service needs — log on as a service, read/write the data directory, read/write the configured repo root, and "Performance Monitor Users" membership. Document this clearly for the operator.
- **[Risk]** A single shared static credential means any leak (log capture, sbx compromise) grants full command execution. → **Mitigation**: credential is configuration-only (rotatable without redeploy); operator should treat it as a high-value secret and rotate on suspected leak.
- **[Risk]** Long-running or runaway `dotnet` processes could exhaust host resources (CPU/disk/memory) since there's no per-request resource quota. → **Mitigation**: execution timeout (above) bounds wall-clock time; resource quotas (CPU/memory limits) are left as a future job-object-based enhancement, not v1.
- **[Trade-off]** An SSE stream still ties up one open HTTP connection per in-flight command for its full duration (no detach-and-reconnect); if the sbx-side client drops the connection mid-run, it loses the ability to observe the rest of that run (the server-side process still finishes, but there's no reconnect-and-resume). → Accepted for v1 given a single caller and no concurrency limits yet; a job-submit + reconnectable-poll model is the natural v2 if disconnect resilience becomes a problem.
- **[Risk]** SSE requires the HTTP client to disable response buffering/support streaming reads; a client that buffers the whole response before returning (some HTTP libraries default to this) would see no benefit and effectively degrade to synchronous behavior. → **Mitigation**: document the required client behavior (e.g. `curl -N`, or an HttpClient configured for `HttpCompletionOption.ResponseHeadersRead`) alongside the endpoint.
- **[Risk]** The run registry is in-memory only: a service restart drops all lock/run-id state even though the underlying `dotnet.exe` processes may or may not still be running depending on process-tree lifetime relative to the service. → **Mitigation**: accepted for v1 (matches "no persistent state" migration/rollback story); a cancel call after a restart simply 404s (run id no longer known), and a repo whose lock was lost on restart becomes immediately available again — document this as a known gap, not silently hidden.
- **[Risk]** Reject-on-conflict (vs. queueing) pushes retry/backoff logic onto the caller for the same-repo case. → **Mitigation**: accepted — the caller (Claude Code) can trivially retry or cancel-then-retry; documented in the API contract, not hidden behavior.
- **[Risk]** SQLite has no built-in retention/rotation, and full stdout/stderr per run can be large (up to the output cap, e.g. 5 MB, per run) — the database file grows unbounded over the service's lifetime. → **Mitigation**: accepted for v1 per the Non-Goals; document the growth rate and that an operator can manually prune old rows; a size-based retention policy is a natural v2.
- **[Risk]** SQLite allows only one writer at a time; under this service's actual write pattern (at most one insert/update per run-start and per run-terminal-state, and runs across different repos already run in parallel meaning writes could overlap) concurrent writers could contend or, if misconfigured, fail. → **Mitigation**: use SQLite's WAL journal mode (allows concurrent readers with a single writer, less blocking) and keep each write a short, single-row operation — no long-running transactions.
- **[Risk]** A service crash between "process exited" and "SQLite row updated" would leave a run's DB row stuck at `Running` even though the process is no longer active, look identical to a true hang until the startup reconciliation step relabels it `Interrupted` on next start. → **Mitigation**: accepted — the startup reconciliation (above) bounds how long this lasts to "until next restart," not indefinitely; a live dashboard viewer would see the run as still in-flight until then, which is a known, documented limitation, not silent data loss.
- **[Trade-off]** Blazor Server ties dashboard "liveness" to an open SignalR connection per browser tab; a flaky network between the operator's browser and the host will visibly disconnect/reconnect the dashboard (Blazor shows its own reconnection UI). → Accepted — this only affects the human viewing experience, never the underlying command execution or persistence, which are independent of any dashboard connection.
- **[Risk]** A self-contained single-file publish is large (100+ MB) since it bundles the full .NET runtime; copying it for every upgrade is heavier than a framework-dependent DLL deploy. → **Mitigation**: accepted — a one-time file copy on an internal network is not a meaningful cost, and it's what buys "no separate runtime install" for the operator.
- **[Risk]** `upgrade.ps1` swapping the exe while the service is still holding the file open (stop didn't fully release it, or stop timed out) would fail the copy or leave a partially-written binary. → **Mitigation**: the script must explicitly wait for and verify the service reaches the `Stopped` state (not just issue `Stop-Service` and move on) before copying, and abort the upgrade with a clear error if it doesn't stop within a timeout.
- **[Risk]** EF Core migrations applied automatically at startup mean a bad migration in a new build could corrupt or fail against existing data with no automatic rollback path (downgrade isn't supported, per Non-Goals). → **Mitigation**: accepted for v1 given a single operator and low deployment frequency; document that operators should keep a copy of the SQLite file before upgrading if they want a manual rollback option.
- **[Risk]** `PerformanceCounter` access to the `Processor` category can require the service account to be a member of the local "Performance Monitor Users" group (behavior varies by Windows configuration) — the least-privilege service account chosen for the process-execution risk above might not have this by default. → **Mitigation**: `install.ps1` must grant this membership explicitly as part of service-account setup; document it as a specific, deliberate grant rather than defaulting to a broader account.
- **[Risk]** WMI (`Win32_Process`) queries every few seconds, even for a small number of processes, add a background CPU/IO cost that scales (mildly) with total host process count, since `Win32_Process` enumerates all processes to filter by `ParentProcessId`. → **Mitigation**: accepted at a "few seconds" cadence for a typical host process count; if this becomes measurable, the tree walk can be narrowed by caching each root's last-known descendant PID set and only re-querying for genuinely new/exited children.
- **[Risk]** Behavior tests that genuinely spawn `dotnet.exe` (build/test the fixture projects) are slow relative to pure unit tests, and running them from inside a `dotnet test` process could hit MSBuild/NuGet lock contention or environment-variable bleed from the outer test-runner process into the spawned child. → **Mitigation**: fixture projects are trivial (near-instant restore/build) to keep wall-clock cost low; behavior tests run in their own project (`BuildAndTestService.BehaviorTests`) separate from the fast unit project, so a tight dev loop can run just unit tests; spawned child processes get an explicit clean environment rather than inheriting the outer test runner's.
- **[Risk]** A killed mid-tree process might not immediately release resources its own children were using, or a targeted kill could race with that process's own natural exit (killing a PID that already exited and was reused by an unrelated process — a classic PID-reuse hazard). → **Mitigation**: re-verify the target process's identity (e.g. compare `Process.StartTime` captured at discovery time against the live process before killing) immediately before the kill call, not just at tree-discovery time, so a stale PID from an earlier snapshot can't be used to kill an unrelated, newer process that happens to reuse the same PID.
- **[Trade-off]** Grouping the spawned-process list per-run (rather than one global table) means an operator can't see "everything the host is running" at a glance from Status — only what the service itself spawned. → Accepted: that's the explicit scope given (service-spawned processes only, not a full Task Manager replacement), and it's what keeps the view uncluttered.
- **[Risk]** `RunResourceSamples` grows much faster than `Runs` (many rows per run instead of one), and long/frequent runs multiply that further — this is a bigger driver of the already-accepted "SQLite grows unbounded" risk than run history text ever was. → **Mitigation**: accepted per Non-Goals (no retention policy in v1); the `(RunId, Timestamp)` index keeps per-run graph queries cheap regardless of total table size; document the growth rate explicitly (roughly `points-per-run × concurrent/sequential run volume`) so the operator can judge when manual pruning is warranted.
- **[Risk]** If `wwwroot`/Chart.js (composed from `Presentation`'s Razor Class Library into `Host`'s publish output via static web assets) isn't copied correctly by `install.ps1` or `upgrade.ps1` (e.g. someone copies only the `.exe`), the dashboard loses graphs (and possibly more of its static styling) silently rather than failing loudly. → **Mitigation**: `install.ps1`/`upgrade.ps1` copy the whole publish output directory, not just the exe; add an explicit post-install/upgrade check that a known static asset (e.g. `chart.js`) exists at the expected path, failing the script loudly if not.
- **[Risk]** Live chart updates over a Blazor Server SignalR circuit, even at a "few seconds" cadence, add per-tick JS interop calls for every currently-expanded run chart plus the always-on host chart; with many simultaneously expanded run cards this could add up. → **Mitigation**: lazy chart mounting (above) bounds this to what the operator actually has open; the sampler cadence itself is already coarse (seconds, not sub-second), keeping worst-case interop call frequency low.
- **[Risk]** Five-project Clean Architecture layering (four rings plus `Host`) adds real friction for a service this size — more project-reference bookkeeping, more places to route a single change through (a new field on `Run` touches Domain, its Application port/DTO, its Infrastructure EF Core mapping, and possibly a Presentation view), plus a genuinely separate composition-root project most ASP.NET Core Clean Architecture templates fold into the Web project. → **Mitigation**: accepted — this was explicitly requested, specifically including "no connection at all" between Presentation and Infrastructure, which is exactly what the separate `Host` project buys; the NetArchTest suite is what makes the extra structure pay for itself (drift becomes a failing test, not a slow accumulation of shortcuts).
- **[Risk]** `Host` itself is unconstrained by NetArchTest (it's expected to reference everything) — if implementers start putting real business or presentation logic in `Program.cs`/`Host` "because it's already referencing everything anyway," nothing mechanically stops that; only `Presentation`↔`Infrastructure` isolation is actually enforced. → **Mitigation**: keep `Host` to DI registration, config binding, and framework startup calls only, enforced by code review — the architectural guarantee that matters most (Presentation and Infrastructure genuinely can't couple to each other) is the one that's mechanically checked; `Host` staying thin is a discipline, not a test.
- **[Risk]** `CS1591`-as-error for missing public XML doc comments will flag every public member across all five projects immediately, including ASP.NET Core/EF Core-generated or framework-required public surface (e.g. minimal API handler classes, EF Core entity constructors) that a developer might not think of as "this service's public API." → **Mitigation**: accepted as a deliberate strict default; suppress narrowly (a targeted `#pragma`/`[SuppressMessage]`, not a project-wide disable) for the specific framework-mandated cases where a doc comment would be pure noise, so the rule stays meaningful for the actual intentional public API.
- **[Risk]** The Claude Code skill is prose describing the API, with no compiler or test to keep it in sync with the real contract — a future change to the SSE event shape, error reasons, or endpoints could silently leave the skill wrong while `dotnet test` stays green. → **Mitigation**: accepted for v1 (no automated skill-vs-spec consistency check); the skill explicitly cites which spec files it restates, and the manual verification task (running a real Claude Code instance through the skill against a live service) is the practical check, repeated whenever the API contract changes materially.

## Migration Plan

Greenfield — no existing users/data to migrate, except the new SQLite file this change itself introduces.

1. Scaffold the `.slnx` with solution folders (`Domain`, `Application`, `Infrastructure`, `Presentation`, `Host`, `Tests`) and all five architecture projects plus `Tests/UnitTests`, `Tests/BehaviorTests`, `Tests/ArchitectureTests`, `Tests/Fixtures`; enable nullable + `GenerateDocumentationFile`/`CS1591`-as-error solution-wide; write the initial NetArchTest rules against the (still-empty) projects, including that `Presentation` and `Infrastructure` have zero dependency on each other; add the Reqnroll packages and confirm a trivial scenario runs via plain `dotnet test` before writing real feature files.
2. Implement auth, path confinement, process execution, timeout/size-cap handling per Decisions above, split across Domain (pure rules)/Application (orchestration + ports)/Infrastructure (concrete process spawning)/Presentation (endpoint definitions, no Infrastructure reference) per the Architecture section, with `Host` wiring DI at each step, and unit tests and feature-file scenarios landing alongside each piece rather than bolted on afterward.
3. Add EF Core + SQLite provider; define the `Runs` and `RunResourceSamples` entities/migrations; apply migrations at startup against the configured database file path (under the data directory).
4. Wire the run-start/terminal-state code paths to also write through to the `Runs` table, and to publish to the `IRunEventBus`.
5. Build the Blazor Server dashboard (login page, dark-only theme, Status + History views) subscribing to the event bus and querying the `Runs` table.
6. Add the background resource sampler (`PeriodicTimer` + `IResourceEventBus`) and the process-tree/kill mechanics (WMI tree discovery, delta-sampled CPU%, scoped `IProcessMonitor.KillAsync`), per-run aggregation, and the `RunResourceSamples` write-through; wire the Status view's per-run process sublist to it.
7. Vendor Chart.js under `Presentation`'s `wwwroot`; build the JS interop wrapper and lazy-mounted chart components for host graphs, live per-run graphs (10-minute rolling buffer), and full-duration history graphs (reading `RunResourceSamples`).
8. Add a `/version` (or dashboard footer) endpoint exposing the running build's assembly version, for upgrade verification.
9. Publish `Host` as a self-contained single-file win-x64 executable per the Packaging decision, confirming `Presentation`'s `wwwroot` (including `chart.js`) is composed into the publish output and that publish targets only `Host`, not `Domain`/`Application`/`Infrastructure`/`Presentation`/the test projects individually.
10. Write `install.ps1`: create install + data directories, copy the exe and its accompanying publish-output files (including `wwwroot`), write initial config (root directory, bearer token, port, timeout, output cap, SQLite path), create the Windows Service, configure SCM crash-recovery actions, grant the service account Performance Monitor Users membership, open the firewall rule(s), start the service, and verify `chart.js` exists at its expected path.
11. Write `upgrade.ps1`: stop the service (wait/verify `Stopped`), copy the new exe and publish-output files over the install directory (data directory untouched), start the service, poll `/version` to confirm the new build is running.
12. Smoke test from the sbx sandbox: authenticated `dotnet --version` round-trip, then a real `build`/`test` against a sample repo; separately smoke test the dashboard by opening it in a browser during and after that run, including the resource/process view, live graphs, killing a spawned process, and a completed run's full-duration graph in history.
13. Smoke test the upgrade path itself: install an initial build, run a command, run `upgrade.ps1` with a newer build, confirm the service comes back up, `/version` reflects the new build, and prior history (including resource-sample series) is still present.
14. Rollback: run `install.ps1`'s service-creation step against a known-good previous exe (keep the last N published executables around), or simply stop the service — the data directory (config + SQLite file) is untouched by either path, so history survives.
